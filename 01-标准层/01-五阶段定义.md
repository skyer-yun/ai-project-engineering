# 五阶段定义

> **定位**：本文件是「需求/设计/开发/交付/复盘 五阶段定义」「阶段-工种覆盖矩阵」「阶段-逻辑角色映射」「阶段内字段结构」的**唯一权威源**。其他文档涉及阶段时一律引用本文件，不再重复定义。
>
> **核心模型**：五阶段 = **需求（D）/ 设计（S）/ 开发（B）/ 交付（Ship）/ 复盘（L）**，每阶段内嵌 Plan/Act/Observe/Reflect/Exit 五字段 Loop 微循环，阶段间通过 YAML 交接契约流转。
>
> **命名说明**：对外讲工种和中文阶段名；需求/设计/开发/交付/复盘 作为**内部代号**用于交接契约 schema 字段（YAML 枚举值）；方法论逻辑角色（需求规范师（Spec-Writer）/构建师（Builder）/审查师（Reviewer）/交付师（Shipper）/统筹师（Keeper））用于 handoff 签字角色，不对一线工种推广。

## 一、总览

```
需求(D)              设计(S)              开发(B)              交付(Ship)            复盘(L)
需求→结构化共识      方案/PRD/架构/详设   编码/审查/联调       测试/部署/验收/培训   复盘/沉淀
┌──────────┐        ┌──────────┐         ┌──────────┐         ┌──────────┐         ┌──────────┐
│ 商机理解  │──────→│ 技术方案  │────────→│ 编码实现  │────────→│ 测试策略  │────────→│ 项目复盘  │
│ 需求分析  │ QG    │ PRD      │  QG     │ 代码审查  │  QG     │ 测试执行  │  QG     │ 知识沉淀  │
│ 干系人识别│ -需求  │ 架构设计  │ -设计   │ 联调集成  │ -开发   │ 部署验收  │ -交付   │          │
│          │       │ 详细设计  │         │          │         │ 培训移交  │         │          │
└──────────┘       └──────────┘         └──────────┘         └──────────┘         └──────────┘
 售前+产品           产品+架构+研发        研发+测试             测试+交付             PM+全员
 HITL: In(L3)        HITL: In(L3)         HITL: In+Fb(L2)      HITL: In(L4)         HITL: In(L3)
```

**循环符号**：每条 `→` 都是阶段出口（QG 通过 + 交接契约签署才进下一阶段）；`↩` 表示阶段内回溯（Loop 未 Exit 则回到本阶段 Plan）。

## 二、设计原则（为什么是 5 阶段）

业界主流（AWS AI-DLC 三阶段、Anthropic Context Engineering、Spec-Driven Development）在 2025-2026 已收敛到「**前置规范→中间执行→后置验证**」三段范式。本体系在此基础上细化为 5 阶段：

1. **拆出需求与复盘**：需求理解和项目复盘是 AI 时代最容易失守的两端——AI 倾向于"跳过需求直接写代码"和"完成即遗忘"。单独成阶段强制约束。
2. **设计与开发分离**：规范（PRD/架构/详设）一旦写成可执行文件，开发才能真正闭环。混淆这两步是瀑布式项目失败的主因。
3. **交付含培训移交**：交付不仅是部署，含验收、培训、运维移交，覆盖完整价值闭环。
4. **不绑工种**：5 阶段只描述"做什么"，不规定"谁做"——工种 Playbook 见 [03-执行层/01-工种Playbook/](../03-执行层/01-工种Playbook/)，可由任意 AI 工具或人承担。

## 三、阶段-工种覆盖矩阵

> **主** = 主责执行，**协** = 协作支持，**审** = 跨阶段质量审查，**监** = 全程监督/上下文守护

| 工种 | 需求(D) | 设计(S) | 开发(B) | 交付(Ship) | 复盘(L) |
|------|:------:|:------:|:------:|:---------:|:------:|
| **售前工程师** | **主** | 协 | — | — | 参 |
| **产品经理** | **主** | **主** | 协 | — | 参 |
| **研发工程师**（含架构师） | 协 | **主** | **主** | 协 | 参 |
| **测试工程师** | — | 协 | 协（代码审查） | **主**（测试+验收） | 参 |
| **交付工程师** | — | — | — | **主**（部署+培训） | 参 |
| **项目经理** | 监 | 监 | 监 | 监 | **主** |

## 四、阶段-逻辑角色映射（对内约束用）

> 方法论逻辑层用 5 逻辑角色作为 handoff 契约的签字角色。**1 工种可跨多角色，1 角色可由多工种承担**。

| 逻辑角色 | 主要承担工种 | 主要覆盖阶段 |
|---------|------------|------------|
| **需求规范师（Spec-Writer）**（需求规范师） | 售前 + 产品 | 需求 + 设计前半 |
| **构建师（Builder）**（构建师） | 研发（含架构师） | 设计后半 + 开发 |
| **审查师（Reviewer）**（审查师） | 测试 + 研发交叉审查 | 设计 + 开发 + 交付 |
| **交付师（Shipper）**（交付师） | 测试 + 交付 | 交付 |
| **统筹师（Keeper）**（统筹师） | 项目经理 | 全程监督 + 复盘 |

**逻辑角色与工具解耦声明**：1 个角色可由多 AI 工具/人承担；1 个 AI 工具也可跨角色。具体映射见 [05-适配层/](../05-适配层/)。

## 五、阶段完整字段定义

每阶段必须明确以下 8 字段，否则不算"工程化定义"：

| # | 字段 | 含义 | 强制 |
|---|------|------|------|
| 1 | **使命** | 一句话回答"这阶段在解决什么问题" | ✅ |
| 2 | **主责工种** | 售前/产品/研发/测试/交付/PM 之一或多个 | ✅ |
| 3 | **逻辑角色**（签字用） | 需求规范师（Spec-Writer）/构建师（Builder）/审查师（Reviewer）/交付师（Shipper）/统筹师（Keeper） 之一 | ✅ |
| 4 | **HITL 模式** | In / On / Fallback（详见 [03-HITL规则表.md](../03-执行层/03-HITL规则表.md)） | ✅ |
| 5 | **不可逆等级** | L1-L4（详见 [00-理论层/03-HITL模式与不可逆性矩阵.md](../00-理论层/03-HITL模式与不可逆性矩阵.md)） | ✅ |
| 6 | **Loop 5 字段** | Plan/Act/Observe/Reflect/Exit（详见 [02-Loop微循环规范.md](./02-Loop微循环规范.md)） | ✅ |
| 7 | **输入/输出产物** | 上游交接 + 本阶段产出工件清单 | ✅ |
| 8 | **出口质量门禁** | QG-需求 / QG-设计 / QG-开发 / QG-交付（详见 [03-质量门禁QG-需求至QG-交付.md](./03-质量门禁QG-需求至QG-交付.md)） | ✅ |

### 阶段 1：需求（D，Discover）

| 字段 | 内容 |
|------|------|
| 使命 | 把模糊"客户想要"→结构化可执行共识（业务/角色/场景/约束/优先级 5 维全绿） |
| 主责工种 | **售前工程师** + **产品经理** |
| 逻辑角色（签字） | **需求规范师（Spec-Writer）** |
| HITL 模式 | **In**（客户面访+需求沟通） |

| Loop Schema | **Plan**: 列访谈对象+大纲+信息缺口 / **Act**: AI 整理纪要/招标书 → 结构化需求记录 / **Observe**: 5 维完整性检查 / **Reflect**: 客户+PM 确认需求点 / **Exit**: 5 维全绿 + 干系人签字 |
| 输入产物 | 客户原始诉求（招标书/邮件/口述/竞品截图） |
| 输出产物 | [需求调研记录](../02-产物层/需求/需求调研记录模板.md)（SRC-NNN 素材台账）/ [需求清单](../02-产物层/需求/需求清单模板.md)（REQ-NNN）/ [需求分析报告](../02-产物层/需求/需求分析报告模板.md) / [干系人清单](../02-产物层/需求/干系人清单模板.md) / [需求确认书](../02-产物层/需求/需求确认书模板.md)（基线冻结凭据） |

### 阶段 3：开发（B，Build）

| 字段 | 内容 |
|------|------|
| 使命 | 把可执行规范→可运行代码（编码 / 审查 / 联调 / 集成） |
| 主责工种 | **研发工程师**（主）+ **测试工程师**（协助审查） |
| 逻辑角色（签字） | **构建师（Builder）**（主）+ **审查师（Reviewer）**（跨阶段审查） |
| HITL 模式 | **In**（关键模块）+ **Fallback**（简单模块 AI 自动 + 抽检） |

| 输入产物 | 设计阶段输出（详设/接口契约/数据模型）+ QG-设计 通过的交接契约 |
| 输出产物 | [代码工程化产物](../02-产物层/开发/代码工程化规范.md)（源码 / 接口文档 / 联调报告） |
| 出口质量门禁 | **QG-开发** |

|------|------|

| 主责工种 | **测试工程师**（测试+验收）+ **交付工程师**（部署+培训） |

| Loop Schema | **Plan**: 测试策略+部署方案+培训计划 / **Act**: 执行测试+部署+培训 / **Observe**: 测试通过率+性能+安全自动校验 / **Reflect**: 客户验收+用户体验反馈 / **Exit**: 测试 P0/P1 清零 + 部署成功 + 客户签字验收 |

| 出口质量门禁 | **QG-交付** |

### 阶段 5：复盘（L，Learn）

| 字段 | 内容 |
|------|------|
| 使命 | 把单次项目经验→可复用知识资产（复盘 / 沉淀 / 反哺体系） |
| 主责工种 | **项目经理**（主）+ 全员参与 |
| 逻辑角色（签字） | **统筹师（Keeper）** |
| HITL 模式 | **In**（L3 复盘结论影响后续项目） |
| 不可逆等级 | L3（错误的复盘结论会误导后续项目） |
| Loop Schema | **Plan**: 列复盘维度（目标/过程/质量/团队/AI 协作） / **Act**: 整理数据+访谈+写复盘报告 / **Observe**: 数据对比（计划vs实际 / QG 通过率 / Loop 次数） / **Reflect**: 团队共识+改进项 / **Exit**: 复盘报告评审通过 + 改进项录入体系 |
| 输入产物 | 全程交接契约链 + QG 历史数据 + Loop 度量数据 |
| 输出产物 | [项目复盘报告](../02-产物层/复盘/项目复盘模板.md) / 体系改进项 |
| 出口质量门禁 | —（终态，无下一阶段；改进项追踪由 统筹师（Keeper） 持续） |

## 六、阶段间流转规则

1. **顺序原则**：需求→设计→开发→交付→复盘 主路径，但允许阶段内多次 Loop 回溯。
2. **跨阶段回溯**：仅当下游发现上游根本性问题时触发，必须更新上游产物 + 重新签 QG + 在交接契约 `risk_flags` 字段记录。
3. **并行约束**：设计阶段内部方案/PRD 与架构/详设可部分并行（前半完成后后半启动）；其他阶段建议串行。
4. **复盘阶段不可省略**：每个项目必须产出复盘报告，否则体系无法演化。

## 七、与外界模型对照

| 业界模型 | 与本体系五阶段的对应 |
|----------|--------------------|
| AWS AI-DLC 三阶段（Discover/Develop/Deploy） | 需求+设计前半 = Discover / 设计后半+开发 = Develop / 交付 = Deploy |
| Anthropic Context Engineering 四原则 | 跨五阶段全程应用（详见 [00-理论层/04-上下文工程四原则.md](../00-理论层/04-上下文工程四原则.md)） |
| Spec-Driven Development | 设计阶段是核心 |
| Loop Engineering（Anthropic agentic loop） | 每阶段内嵌 Loop 微循环 |

本体系不否认业界共识，而是把它们整合成可落地的工作流。
