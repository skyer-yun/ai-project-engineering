## §一 提示词设计五原则

| # | 原则 | 含义 | 反例 |
|---|------|------|------|
| 1 | **明确角色** | 告诉 AI 它是谁、做什么 | "帮我写点东西" |
| 2 | **上下文充足** | 给背景、约束、参考文档 | 无背景直接要结果 |
| 3 | **任务可验证** | 输出有验收标准 | "写好一点" |
| 4 | **示例引导** | Few-shot > Zero-shot | 只描述不给样例 |
| 5 | **拆解复杂任务** | 多步骤分开提问 | 一次塞 10 个需求 |

## §二 上下文工程四原则（深层依据）

> 详见 [00-理论层/04-上下文工程四原则.md](../00-理论层/04-上下文工程四原则.md)。

| 原则 | 在提示词中的体现 |
|------|----------------|
| **Write**（写满上下文） | 把 PRD/详设/规范写入 SYSTEM prompt |
| **Select**（精选上下文） | 长文档用 RAG / @文件 而非全量塞入 |
| **Compress**（压缩上下文） | 用表格、列表代替散文 |
| **Isolate**（隔离上下文） | 不同任务用不同 session / subagent |

## §三 三层提示词架构

> Layer（分层）是上下文工程四原则的落地形态。

```
┌─────────────────────────────────────────┐
│ 全局规范层（Global）                      │  ← SYSTEM prompt，跨项目复用
│   - 提示词五原则                          │
│   - 上下文工程四原则                      │
│   - 通用反模式（§十）                     │
├─────────────────────────────────────────┤
│ 项目规范层（Project）                     │  ← 项目级 CLAUDE.md / AGENTS.md
│   - 项目章程 / 干系人 / 技术栈            │
│   - 五阶段 × QG 出口标准                  │
│   - 命名/版本/目录规范                    │
├─────────────────────────────────────────┤
│ 任务规范层（Task）                        │  ← 单次会话/任务
│   - 6 段模板（§四）                       │
│   - 角色/工种/阶段定位                    │
│   - 阶段交接契约引用（§九）               │
└─────────────────────────────────────────┘
```

**落地建议**：全局层走工具 SYSTEM 配置；项目层落地为仓库 `CLAUDE.md` / `AGENTS.md` / `.cursorrules`；任务层每轮动态拼装。

## §四 统一 6 段模板结构

所有任务层提示词模板必须含 6 段：

```markdown
## 1. 角色
你是 {角色 + 工种}，负责 {职责}。

## 2. 上下文
- 项目：{名称}
- 阶段：{D/S/B/Ship/L}
- 输入产物：{列出，含路径}
- 约束：{技术栈 / 规范 / QG}

## 3. 任务
{具体任务描述，可量化}

## 4. 输出格式
{markdown / yaml / 代码 / 表格}

## 5. 验收标准
- {标准 1，对齐 QG}
- {标准 2}

## 6. 示例（可选）
{参考样例}

## 7. HITL 与交接契约引用（强制）
- HITL 模式：{In / On / Fallback}（不可逆性 L{1-4}）
- 输出末尾附 handoff_ref YAML 块（见 §九）
```

## §五 角色维度（5 逻辑角色基座）

> 给方法论内部和 handoff 契约用。1 工种可跨多角色，1 角色可由多工种承担。

### 5.1 需求规范师（Spec-Writer）

```markdown
## 1. 角色
你是 **需求规范师（Spec-Writer）**，工种背景：售前 / 产品。负责把商机/痛点转化为可执行规范。

## 2. 上下文
- 阶段：D-需求（部分延伸至 S-设计 PRD）
- 输入：客户原始需求 / RFP / 干系人访谈纪要
- 约束：QG-需求（需求覆盖率 ≥ 0.9、干系人签字 1.0）

## 3. 任务
输出需求分析报告 + 干系人清单 + 场景库 + （进入 S 阶段时）PRD 12 部分。

## 4. 输出格式
Markdown 报告 + 干系人矩阵 + 用例图（PlantUML/Mermaid）。

## 5. 验收标准
- QG-需求 全部 🔴 项通过
- 投标应答覆盖率 1.0（投标场景）
- AC 可测试率 ≥ 0.9（PRD 场景）

## 6. 示例
{粘贴历史项目的优秀需求分析报告片段}

## 7. HITL 与交接契约
- HITL 模式：**In**（L3 共识不可逆，per-key 审批）
- handoff_ref YAML 块见 §九
```

### 5.2 构建师（Builder）

```markdown
## 1. 角色
你是 **构建师（Builder）**，工种背景：研发（含架构师）。负责把规范转化为可运行代码。

## 2. 上下文
- 阶段：S-设计（架构/详设）→ B-开发（编码/联调）
- 输入：PRD + 需求分析报告 + 架构设计
- 约束：开发阶段必须先 Plan 后 Execute（Plan Mode）

## 3. 任务
{具体模块} 架构设计 + 详细设计 + 编码 + 单测 + 联调 + atomic commit。

## 4. 输出格式
设计文档（Markdown）+ 代码 + 单测 + ADR（架构决策记录）。

## 5. 验收标准
- QG-设计：架构评审通过率 ≥ 0.95
- QG-开发：核心代码单测 ≥ 0.9 / 一般 ≥ 0.7 / Lint Critical = 0
- Plan Mode 遵守率 1.0、Atomic Commit ≥ 0.9

## 6. 示例
{粘贴 ADR 模板与优秀单测样例}

## 7. HITL 与交接契约
- HITL 模式：S 阶段 **In**（L3）；B 阶段 **In + Fallback**（L2 可逆）
```

### 5.3 审查师（Reviewer）

```markdown
## 1. 角色
你是 **审查师（Reviewer）**，工种背景：测试 + 研发交叉审查。负责跨阶段质量守门。

## 2. 上下文
- 阶段：跨阶段（D 评审需求 / S 评审架构 / B 代码审查 / Ship 评审用例与验收标准）
- 输入：当前阶段产物 + QG checklist
- 约束：审查独立于作者，不得自审自批

## 3. 任务
对当前阶段产物做评审，输出 Issue 清单（按 🔴/🟡/🟢 分级）+ 评审结论（通过/有条件通过/返工）。

## 4. 输出格式
Markdown 评审报告 + Issue 表（编号、定位、严重度、建议）。

## 5. 验收标准
- 代码审查覆盖率 1.0
- 缺陷逃逸率 ≤ 5%（B→Ship）
- QG 一次通过率 ≥ 0.9

## 6. 示例
{粘贴优秀代码审查 checklist}

## 7. HITL 与交接契约
- HITL 模式：**In**（评审 = L3 不可逆决策）
```

### 5.4 交付师（Shipper）

```markdown
## 1. 角色
你是 **交付师（Shipper）**，工种背景：测试 + 交付。负责测试 → 部署 → 验收 → 培训全链路。

## 2. 上下文
- 阶段：Ship-交付
- 输入：测试报告 Pass + 源码 + 运维手册 + 培训素材
- 约束：部署 HITL=In（L4 生产不可逆），必须 Checkpoint 已打

## 3. 任务
测试策略执行 → 部署到生产 → 客户验收 → 培训考核。

## 4. 输出格式
部署文档 + 验收报告 + 培训材料 + 考核题库。

## 5. 验收标准
- QG-交付：用例通过率 ≥ 0.95 / P0/P1 清零 / 一次部署成功率 ≥ 0.95
- 客户满意度 ≥ 4.5/5 / 培训考核通过率 ≥ 0.8
- 部署前 Checkpoint 打点 1.0（snapshot.sh）

## 6. 示例
{粘贴部署 Runbook + 回滚剧本}

## 7. HITL 与交接契约
- HITL 模式：**In**（L4 不可逆，per-key + 双签）
```

### 5.5 统筹师（Keeper）

```markdown
## 1. 角色
你是 **统筹师（Keeper）**，工种背景：项目经理。负责上下文/记忆/复盘/契约校验，五阶段全程稳定角色。

## 2. 上下文
- 阶段：全程（D/S/B/Ship/L），L 阶段主责
- 输入：项目章程 + 干系人清单 + 各阶段契约 + 周报
- 约束：handoff 契约的最终签字人之一；记忆库维护者

## 3. 任务
制定 WBS + 排期 + 风险登记册 + 周报 + QG 评审组织 + 项目复盘 + 经验入库。

## 4. 输出格式
Markdown + Mermaid 甘特图 + 风险登记册表格 + 阶段交接契约 YAML。

## 5. 验收标准
- 计划偏差率 ≤ 10%、关键路径零延误 1.0
- 质量门禁通过率 ≥ 0.9
- 复盘改进项闭环率 ≥ 0.8、经验沉淀入库 ≥ 3/项目

## 6. 示例
{粘贴周报模板 + 复盘报告片段}

## 7. HITL 与交接契约
- HITL 模式：全程 **In**（监督者）；L 阶段 **In**（L3 复盘共识）
```

## §六 工种维度（6 工种实务基座）

> 6 工种按组织真实岗位组织（Playbook 同源）。每个工种 ↔ 1-3 个逻辑角色，交叉索引见下表。

| 工种 | 主要承担角色 | 实务提示词要点 |
|------|------------|--------------|
| **售前工程师** | Spec-Writer | 客户/行业/预算约束；输出 11/7/8 章技术方案（Word）；QG-需求 |
| **产品经理** | Spec-Writer（主）+ Keeper（协） | PRD 12 Part + HTML Demo；用户访谈；QG-需求/QG-设计 |
| **研发工程师**（含架构师） | Builder + Reviewer（交叉审查） | 架构/详设/编码/单测/联调；Plan Mode；atomic commit；QG-设计/QG-开发 |
| **测试工程师** | Reviewer + Shipper | 测试策略/用例/执行/缺陷；用例设计 ≥ 4 种方法；QG-交付前半 |
| **交付工程师** | Shipper | 部署/验收/培训；HITL=In L4；Checkpoint；QG-交付后半 |
| **项目经理** | Keeper（唯一）+ 跨工种协调 | WBS/排期/风险/周报/QG 评审组织；五阶段全程 |

> 工种实务提示词完整模板：见 [03-执行层/01-工种Playbook/](../03-执行层/01-工种Playbook/) 6 份 Playbook 第 6 节。

## §七 阶段维度（D/S/B/Ship/L 各阶段典型提示词）

### 7.1 D-需求

| 场景 | 提示词要点 | 出口 |
|------|----------|------|
| 需求收集 | 角色=Spec-Writer；输入=客户原始需求/RFP；输出=结构化需求列表 | QG-需求 |

| 需求确认书 | 角色=Spec-Writer + Keeper；输出=需求分析报告 + 签字版 | QG-需求（签字 1.0） |

### 7.2 S-设计

| 场景 | 提示词要点 | 出口 |
|------|----------|------|
| PRD | 角色=Spec-Writer（产品工种）；输出=PRD 12 Part | QG-设计 |
| 架构设计 | 角色=Builder（研发工种）；输出=架构文档 + ADR | QG-设计 |
| 详细设计 | 角色=Builder；输出=接口/数据模型/时序图/状态机 | QG-设计 |
| UI 评审 | 角色=Reviewer；输出=评审 Issue 清单 | QG-设计 |

### 7.3 B-开发

| 场景 | 提示词要点 | 出口 |
|------|----------|------|
| Plan Mode | 角色=Builder；输出=实施计划（先 Plan 后 Execute 强制） | QG-开发 |
| 编码 | 角色=Builder；输出=代码 + atomic commit（说为什么） | QG-开发 |
| 代码审查 | 角色=Reviewer；输出=Issue 清单 + 评审结论 | QG-开发 |
| 联调排障 | 角色=Builder + Reviewer；输出=联调报告 + 接口 Pass 率 ≥ 0.95 | QG-开发 |

### 7.4 Ship-交付

| 场景 | 提示词要点 | 出口 |
|------|----------|------|

| 改进项 | 角色=Keeper；输出=改进项 OKR + 跟踪表 | L 终态 |

## §八 场景库（≥ 12 场景）

> 每个场景给出最小可用提示词骨架，按"角色 / 阶段 / 任务 / 出口"四元组描述。

### 需求类

**S1 模糊需求澄清**
- 角色：Spec-Writer | 阶段：D | 出口：QG-需求
- 提示词骨架：「客户说"{原话}"。请按 5W2H 拆解，列出 3-5 个澄清问题；客户答后再生成结构化需求。」

**S2 RFP 解析**
- 角色：Spec-Writer | 阶段：D | 出口：QG-需求（投标应答覆盖率 1.0）
- 提示词骨架：「逐条解析 RFP（{路径}），输出应答矩阵：条款/响应（完全/部分/偏离）/证据出处/缺口。」

**S3 干系人冲突调停**
- 角色：Spec-Writer + Keeper | 阶段：D | 出口：QG-需求（签字 1.0）
- 提示词骨架：「干系人 A 要 X，干系人 B 要 Y（互斥）。请输出：①冲突根因 ②3 个折中方案 ③推荐 + 理由。」

### 设计类

**S4 架构 trade-off**
- 角色：Builder | 阶段：S | 出口：QG-设计（架构评审通过率 ≥ 0.95）
- 提示词骨架：「需求={X}；候选方案=A/B/C；维度=性能/成本/可维护/安全/扩展。请输出评分矩阵 + 推荐 + ADR。」

**S5 技术选型**
- 角色：Builder | 阶段：S | 出口：QG-设计
- 提示词骨架：「场景={描述}；候选={框架/产品列表}；评估维度={...}；输出选型报告 + POC 建议。」

**S6 设计评审**
- 角色：Reviewer | 阶段：S | 出口：QG-设计
- 提示词骨架：「详设文档={路径}；按 {checklist} 评审；输出 Issue 表（🔴/🟡/🟢）+ 结论。」

### 开发类

**S7 Bug 复现**
- 角色：Builder | 阶段：B | 出口：QG-开发
- 提示词骨架：「现象={描述}；环境={...}；请按 systematic-debugging：①最小复现 ②假设 ③验证 ④根因 ⑤修复。」

**S8 重构**
- 角色：Builder | 阶段：B | 出口：QG-开发（单测不降）
- 提示词骨架：「目标模块={路径}；坏味={...}；约束=行为不变 + 单测全绿；输出重构计划 + diff。」

**S9 性能优化**
- 角色：Builder | 阶段：B | 出口：QG-开发
- 提示词骨架：「瓶颈={描述/火焰图}；目标={P95 ≤ 200ms 等}；输出优化方案 + before/after 指标。」

**S10 联调排障**
- 角色：Builder + Reviewer | 阶段：B | 出口：QG-开发（接口 Pass ≥ 0.95）
- 提示词骨架：「接口={spec}；现象={...}；输出排查路径 + 抓包/日志证据 + 修复。」

### 交付类

**S11 生产回滚**
- 角色：Shipper | 阶段：Ship | 出口：QG-交付（HITL=In L4）
- 提示词骨架：「现象={故障}；影响={...}；按 Runbook：①Checkpoint 回滚 ②验证 ③根因 ④预防。每步等人确认。」

**S12 客户培训**
- 角色：Shipper | 阶段：Ship | 出口：QG-交付（考核通过率 ≥ 0.8）
- 提示词骨架：「受众={角色/水平}；输出操作手册 + PPT + 考核题库（≥ 20 题）。」

**S13 验收答辩**
- 角色：Shipper + Keeper | 阶段：Ship | 出口：QG-交付（客户签字 1.0）
- 提示词骨架：「合同条款={...}；交付物={清单}；输出验收对照表 + 答辩 Q&A 预案。」

### 复盘类

**S14 根因分析**
- 角色：Keeper + Reviewer | 阶段：L | 出口：L 终态
- 提示词骨架：「事件={描述}；按 5 Whys + 鱼骨图；输出根因 + 改进项（OKR 化）。」

**S15 改进项 OKR 化**
- 角色：Keeper | 阶段：L | 出口：L 终态（改进项闭环率 ≥ 0.8）
- 提示词骨架：「经验条目={...}；输出 O-KR-Key Results-Owner-截止时间。」

## §九 HITL × 不可逆性 在提示词中的强制标注

> 详见 [00-理论层/03-HITL模式与不可逆性矩阵.md](../00-理论层/03-HITL模式与不可逆性矩阵.md)。

| HITL 模式 | 不可逆性 | 提示词约束 | 典型阶段 |
|----------|---------|----------|---------|
| **In**（per-key 审批） | L3/L4 | 「⚠ 每个文件改动需用户确认」 | D 共识、S 方案、Ship 部署 |
| **On**（监督） | L2 | 「⚠ 完成一批后暂停等用户审阅」 | B 编码、测试执行 |
| **Fallback**（兜底） | L1-L2 | 「⚠ 遇异常/超时/不确定 立即上报」 | B 联调、自动化任务 |

**强制规则**：每段任务提示词的输出末尾，必须含 `handoff_ref` YAML 块（对齐 [04-阶段交接契约Schema.md](./04-阶段交接契约Schema.md)）：

```yaml
handoff_ref:
  from_stage: D              # D / S / B / Ship / L
  to_stage: S
  quality_gate: QG-D         # QG-D / QG-S / QG-B / QG-Ship / -
  gate_status: passed        # passed / failed / escalated
  loop_iteration: 3          # 本阶段 Loop 微循环迭代次数
  eval_scores:               # 出口 QG 量化分数
    requirement_completeness: 0.92
    scenario_coverage: 0.96
    stakeholder_signed: 1.0
  loop_signs:                # Loop 5 字段签名
    - stage: D
      iterations: 3
      reflect_passed: true
      exit_met: true
  hitl_signature:
    mode: In                 # In / On / Fallback
    irreversibility: L3      # L1-L4
    approved_by:
      - {role: "客户代表", name: "张三"}
      - {role: "Spec-Writer", name: "李四"}
  handoff:
    from_role: Spec-Writer
    to_role: Builder
```

## §十 反模式（禁止）

| 反模式 | 问题 | 改进 |
|--------|------|------|
| 一次塞 10 个需求 | 上下文爆炸，质量下降 | 拆 10 次提问 |
| 不给约束 | AI 自由发挥不可控 | 明确技术栈/规范/QG |
| 不给示例 | 输出格式漂移 | Few-shot 给样例 |
| 不说验收标准 | 无所谓好坏 | 量化标准（≥ 90% / ≤ 200ms） |
| 不区分任务类型 | 单次想全做 | 隔离上下文，不同 session（Isolate） |
| 不标 HITL 模式 | 不可逆操作无人审 | 任务必含 §7 HITL 标注 |
| 不附 handoff_ref | 不可追溯 | 输出末尾必含 YAML 块 |
| 全文塞入长文档 | token 浪费 + 漂移 | Select（RAG / @文件） |
| 角色与工种混淆 | 责任不清 | 5 角色 = 方法论；6 工种 = 组织实务 |
| 自审自批 | 审查失效 | Reviewer 独立于作者 |
