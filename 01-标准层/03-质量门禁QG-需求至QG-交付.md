# 质量门禁 QG-需求 至 QG-交付

> **定位**：本文件是「阶段出口质量门禁 checklist」的**唯一权威源**。每阶段 Exit 前必须跑对应 QG，全绿才签交接契约。
>
> **关联**：阶段定义见 [01-五阶段定义.md](./01-五阶段定义.md)；硬指标阈值见 [06-产物质量硬指标库.md](./06-产物质量硬指标库.md)。

---

## 一、QG 总览

| 门禁 | 阶段 | 主审工种 | 逻辑签字角色 | 通过则 | 不通过则 |
|------|------|---------|------------|--------|---------|
| **QG-需求** | 需求（D） | 售前 + 产品 + PM | 需求规范师（Spec-Writer） + 统筹师（Keeper） | 进设计 | 回 Loop / 升级 |
| **QG-设计** | 设计（S） | 产品 + 研发 + 测试 | 需求规范师（Spec-Writer） + 构建师（Builder） + 审查师（Reviewer） | 进开发 | 回 Loop / 升级 |
| **QG-开发** | 开发（B） | 研发 + 测试 | 构建师（Builder） + 审查师（Reviewer） | 进交付 | 回 Loop / 升级 |
| **QG-交付** | 交付（Ship） | 测试 + 交付 + **客户** | 交付师（Shipper） + 审查师（Reviewer） | 项目交付 → 进复盘 | 回 Loop / 升级 |

**核心原则**：
- QG 是"门"不是"评分"——通过/不通过，二元判定。
- 任一项 🔴 则整门禁不通过，禁止进下一阶段。
- 🟡 是警戒项，需记录但不阻塞。

## 二、QG-需求：需求→设计前置门禁

**触发时机**：需求阶段 Exit 前。
**主审工种**：售前工程师 + 产品经理（主）+ 客户代表（必签）+ 项目经理。
**逻辑签字角色**：需求规范师（Spec-Writer） + 统筹师（Keeper）。

### Checklist

| # | 检查项 | 类别 | 通过标准 |
|---|--------|------|---------|
| 1 | 需求 5 维完整性 | 🔴 | 业务/角色/场景/约束/优先级 全部明确，无 TBD |
| 2 | 干系人清单签署 | 🔴 | 所有关键干系人签字（含反对意见已记录） |
| 3 | 业务场景闭环 | 🔴 | 核心场景端到端走通（输入→处理→输出→验收） |
| 4 | 约束清单（合规/预算/时间/技术） | 🔴 | 4 类约束逐条标注 |
| 5 | 优先级矩阵 | 🟡 | MoSCoW 或 KANO 标注完成 |
| 6 | 风险登记 | 🟡 | 已识别风险进入风险登记册 |
| 7 | Loop 次数 ≤5 | 🔴 | 需求阶段 Loop 不超过 5 次 |
| 8 | Reflect 签名齐全 | 🔴 | 需求规范师（Spec-Writer）（售前/产品）+ 客户代表 + 统筹师（Keeper）（PM）签字 |
| 9 | 需求可溯源 | 🔴 | 需求清单中每条 REQ-NNN 需求引用 ≥1 条调研素材（SRC-NNN），溯源率 100%（硬指标见 [06-产物质量硬指标库.md](./06-产物质量硬指标库.md)） |
| 10 | 需求基线冻结 | 🔴 | [需求确认书](../02-产物层/需求/需求确认书模板.md) 已签署：基线版本明确 + 范围外事项逐条列明 + 变更约定成立 |

### QG-需求 通过后产物

- [需求调研记录](../02-产物层/需求/需求调研记录模板.md)（原始素材台账，SRC-NNN）
- [需求清单](../02-产物层/需求/需求清单模板.md)（REQ-NNN 结构化台账，追溯主键）
- [需求分析报告](../02-产物层/需求/需求分析报告模板.md) v1.0+
- [干系人清单](../02-产物层/需求/干系人清单模板.md)（已签）
- [需求确认书](../02-产物层/需求/需求确认书模板.md)（已签，需求基线冻结凭据）
- **交接契约 需求→设计**（详见 [04-阶段交接契约Schema.md](./04-阶段交接契约Schema.md)）

## 三、QG-设计：设计→开发前置门禁

**触发时机**：设计阶段 Exit 前。
**主审工种**：产品经理（前半）→ 研发工程师/架构师（后半）+ 测试工程师（必签）。
**逻辑签字角色**：需求规范师（Spec-Writer）（前半）→ 构建师（Builder）（后半）+ 审查师（Reviewer）。

### Checklist

| # | 检查项 | 类别 | 通过标准 |
|---|--------|------|---------|
| 1 | 技术方案评审通过 | 🔴 | 售前评审会签字，方案符合客户约束 |
| 2 | PRD 评审通过 | 🔴 | 产品评审会签字，需求覆盖需求阶段 100% |
| 3 | 架构设计评审通过 | 🔴 | 架构评审会签字，技术选型有依据 |
| 4 | 详细设计覆盖关键模块 | 🔴 | 关键模块 100% 有详设，含接口/数据模型/时序 |
| 5 | UI-UX 设计客户确认 | 🔴 | 关键页面客户确认（线框或高保真） |
| 6 | 接口契约上下游一致 | 🔴 | 前后端接口契约签字 |
| 7 | 测试策略对齐 | 🟡 | 测试工程师提前介入，测试策略与方案对齐 |
| 8 | 风险更新 | 🟡 | 新增风险录入登记册 |
| 9 | Loop 次数 ≤5 | 🔴 | 设计阶段 Loop 不超过 5 次 |
| 10 | Reflect 签名齐全 | 🔴 | 需求规范师（Spec-Writer） + 构建师（Builder） + 审查师（Reviewer） 签字 |
| 11 | 产品方案覆盖矩阵 | 🔴 | [产品方案](../02-产物层/设计/产品方案模板.md) §二 覆盖矩阵双向核对：每条 REQ-NNN 有方案项，无无源方案项（覆盖率 100%） |
| 12 | 原型完整性 | 🔴 | [原型四件套](../02-产物层/设计/产品原型设计规范.md)达标：页面树校验 5 项全过；核心流程可点击走通；每条需求（全量，含 P0/P1/P2）≥1 条标注（ANN-NNN）挂接到具体页面元素；全包单一设计系统；原型包纯净 |
| 13 | PRD 原型引用一致 | 🔴 | PRD 功能总览/交互章节引用的页面 ID 与 ANN 编号，与页面树、标注数据一致（一致率 100%） |

### QG-设计 通过后产物

- [产品方案](../02-产物层/设计/产品方案模板.md)（产品侧解决路径，含需求-方案覆盖矩阵）
- [原型四件套](../02-产物层/设计/产品原型设计规范.md)：页面树 YAML / 高保真原型包 / 标注数据 JSON / [原型说明](../02-产物层/设计/原型说明模板.md)

## 四、QG-开发：开发→交付前置门禁

**触发时机**：开发阶段 Exit 前。
**主审工种**：研发工程师（主）+ 测试工程师（必签）。
**逻辑签字角色**：构建师（Builder） + 审查师（Reviewer）。

### Checklist

| # | 检查项 | 类别 | 通过标准 |
|---|--------|------|---------|
| 1 | 单测覆盖率 | 🔴 | 行覆盖 ≥80% / 分支覆盖 ≥70%（详见 [06-产物质量硬指标库.md](./06-产物质量硬指标库.md)） |
| 2 | Lint 严重问题 | 🔴 | 严重级 = 0 |
| 3 | 类型检查 | 🔴 | TypeScript/强类型语言零类型错误 |
| 4 | 代码审查通过 | 🔴 | 审查师（Reviewer） 在 PR 签字，无未解决 🔴 意见 |
| 5 | 联调集成通过 | 🔴 | 前后端/E2E 关键路径走通 |
| 6 | 接口契约一致性 | 🔴 | 实现与设计阶段契约一致 |
| 7 | 性能基线 | 🟡 | 关键场景性能达约定基线 |
| 8 | 安全扫描 | 🟡 | 无 Critical/High 漏洞（或已确认接受） |
| 9 | 文档同步 | 🟡 | README / 接口文档 / 部署文档更新 |
| 10 | Loop 次数 ≤5 | 🔴 | 开发阶段 Loop 不超过 5 次 |

## 五、QG-交付：交付验收门禁（L4 不可逆）

**触发时机**：交付阶段 Exit 前。
**主审工种**：测试工程师 + 交付工程师（主）+ **客户代表**（必签）。
**逻辑签字角色**：交付师（Shipper） + 审查师（Reviewer）。

### Checklist

| # | 检查项 | 类别 | 通过标准 |
|---|--------|------|---------|
| 1 | 测试用例执行率 | 🔴 | 100%（已写用例全跑） |
| 2 | P0 缺陷 | 🔴 | **0 未解决** |
| 3 | P1 缺陷 | 🔴 | **0 未解决** |
| 4 | P2 缺陷 | 🟡 | 已评估，遗留项有计划 |
| 5 | 性能压测 | 🔴 | 关键场景达 SLO（详见 [质量标准与验收模板](../02-产物层/交付/质量标准与验收模板.md)） |

| 11 | Loop 次数 ≤5 | 🔴 | 交付阶段 Loop 不超过 5 次 |
| 12 | Reflect 签名齐全 | 🔴 | 交付师（Shipper） + 审查师（Reviewer） + 客户代表签字 |

## 六、QG 失败处理

| 失败类型 | 处理 |
|---------|------|
| 单项 🔴 不通过 | 回当前阶段 Loop，重做相关任务 |
| 多项 🔴 不通过 | 评估是否 Exit-Escalate（升级到 统筹师（Keeper）/客户决策） |
| 根本性失败（如需求错） | 跨阶段回溯，更新上游产物 + 重新签 QG + 风险登记 |
