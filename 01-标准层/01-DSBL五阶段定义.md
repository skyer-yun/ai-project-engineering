# DSBL 五阶段定义

> **定位**：本文件是「D/S/B/Ship/L 五阶段定义」「阶段-角色覆盖矩阵」「阶段内字段结构」的**唯一权威源**。其他文档涉及阶段时一律引用本文件，不再重复定义。
>
> **核心模型**：DSBL = Discover / Spec / Build / Ship / Learn，每阶段内嵌 Plan/Act/Observe/Reflect/Exit 五字段 Loop 微循环，阶段间通过 YAML 交接契约流转。

---

## 一、总览

```
D-Discover         S-Spec              B-Build            S-Ship             L-Learn
需求→结构化共识     方案/PRD/架构/详设    编码/审查/联调      测试/部署/验收/培训   复盘/沉淀
┌──────────┐      ┌──────────┐         ┌──────────┐       ┌──────────┐       ┌──────────┐
│ 需求收集  │─────→│ 技术方案  │────────→│ 编码实现  │──────→│ 测试策略  │──────→│ 项目复盘  │
│ 需求分析  │  QG  │ PRD      │   QG    │ 代码审查  │  QG   │ 测试执行  │  QG   │ 知识沉淀  │
│          │  -D  │ 架构设计  │   -S    │ 联调集成  │  -B   │ 部署验收  │  -S   │          │
│          │      │ 详细设计  │         │          │       │ 培训移交  │  hip │          │
└──────────┘      └──────────┘         └──────────┘       └──────────┘       └──────────┘
  Spec-Writer     Spec-Writer→Builder   Builder+Reviewer    Shipper+Reviewer    Keeper
  HITL: In(L3)    HITL: In(L3)          HITL: In+Fb(L2)     HITL: In(L4)        HITL: In(L3)
```

**循环符号**：每条 `→` 都是阶段出口（QG 通过 + 交接契约签署才进下一阶段）；`↩` 表示阶段内回溯（Loop 未 Exit 则回到本阶段 Plan）。

---

## 二、设计原则（为什么是 5 阶段）

业界主流（AWS AI-DLC 三阶段、Anthropic Context Engineering、Spec-Driven Development）在 2025-2026 已收敛到「**前置规范→中间执行→后置验证**」三段范式。DSBL 在此基础上：

1. **拆出 D 与 L**：发现（Discover）与复盘（Learn）是 AI 时代最容易失守的两端——AI 倾向于"跳过需求直接写代码"和"完成即遗忘"。单独成阶段强制约束。
2. **S 与 B 分离**：规范（Spec）一旦写成可执行文件，Build 才能真正闭环。混淆这两步是瀑布式项目失败的主因。
3. **Ship 含培训移交**：交付不仅是部署，含验收、培训、运维移交，覆盖完整价值闭环。
4. **不绑工种**：5 阶段只描述"做什么"，不规定"谁做"——角色由 [03-执行层/01-角色Playbook/](../03-执行层/01-角色Playbook/) 定义，可由任意 AI 工具或人承担。

## 三、阶段-角色覆盖矩阵

| 角色 | D | S | B | Ship | L |
|------|---|---|---|------|---|
| **Spec-Writer** | **主** | 前（方案/PRD/架构） | | | |
| **Builder** | 参 | 后（详设） | **主** | | |
| **Reviewer** | | 评 | 评 | 评 | |
| **Shipper** | | | | **主** | |
| **Keeper** | 监督全程 | 监督全程 | 监督全程 | 监督全程 | **主** |

> **主** = 主责执行，**参** = 参与协作，**评** = 跨阶段质量审查，**监督全程** = 上下文/记忆/契约守护

**角色与工具解耦声明**：1 个角色可由多 AI 工具/人承担（如 Spec-Writer 同时用多种 AI 工具）；1 个 AI 工具也可跨角色（如同一 AI 工具既做 Spec-Writer 又做 Builder）。具体映射见 [05-适配层/](../05-适配层/)。

## 四、阶段完整字段定义

每阶段必须明确以下 8 字段，否则不算"工程化定义"：

| # | 字段 | 含义 | 强制 |
|---|------|------|------|
| 1 | **使命** | 一句话回答"这阶段在解决什么问题" | ✅ |
| 2 | **主责角色** | 五角色之一 | ✅ |
| 3 | **HITL 模式** | In / On / Fallback（详见 [03-HITL规则表.md](../03-执行层/03-HITL规则表.md)） | ✅ |
| 4 | **不可逆等级** | L1-L4（详见 [00-理论层/03-HITL模式与不可逆性矩阵.md](../00-理论层/03-HITL模式与不可逆性矩阵.md)） | ✅ |
| 5 | **Loop 5 字段** | Plan/Act/Observe/Reflect/Exit（详见 [02-Loop微循环规范.md](./02-Loop微循环规范.md)） | ✅ |
| 6 | **输入产物** | 上游交接的工件清单 | ✅ |
| 7 | **输出产物** | 本阶段产出的工件清单 | ✅ |
| 8 | **出口质量门禁** | QG-D / QG-S / QG-B / QG-Ship（详见 [03-质量门禁QG-D至QG-Ship.md](./03-质量门禁QG-D至QG-Ship.md)） | ✅ |

---

### D - Discover（发现）

| 字段 | 内容 |
|------|------|
| 使命 | 把模糊"客户想要"→结构化可执行共识（业务/角色/场景/约束/优先级 5 维全绿） |
| 主责角色 | **Spec-Writer** |
| HITL 模式 | **In**（客户面访必须人在场） |
| 不可逆等级 | L3（影响后续所有阶段方向） |
| Loop Schema | **Plan**: 列访谈对象+大纲+信息缺口 / **Act**: AI 整理纪要/招标书 → 结构化需求记录 / **Observe**: 5 维完整性检查 / **Reflect**: 客户+PM 确认需求点 / **Exit**: 5 维全绿 + 干系人签字 |
| 输入产物 | 客户原始诉求（招标书/邮件/口述/竞品截图） |
| 输出产物 | [需求分析报告](../02-产物层/D-Discover/需求分析报告模板.md) / [干系人清单](../02-产物层/D-Discover/干系人清单模板.md) |
| 出口质量门禁 | **QG-D** |

---

### S - Spec（规范）

| 字段 | 内容 |
|------|------|
| 使命 | 把需求共识→可执行规范（技术方案 / PRD / 架构 / 详细设计 / UI-UX 全集） |
| 主责角色 | **Spec-Writer**（前半：方案/PRD）→ **Builder**（后半：架构/详设） |
| HITL 模式 | **In**（方案评审、架构评审必须人拍板） |
| 不可逆等级 | L3（架构定调后修改成本指数级上升） |
| Loop Schema | **Plan**: 拆方案/PRD/架构/详设子任务 + 依赖 / **Act**: 各角色 AI 产出对应规范文档 / **Observe**: 完整性+一致性+可执行性自动校验 / **Reflect**: 跨角色评审（售前↔研发↔测试） / **Exit**: 所有规范文档评审通过 + 客户确认方案 |
| 输入产物 | D 阶段输出 + QG-D 通过的交接契约 |
| 输出产物 | [技术方案](../02-产物层/S-Spec/技术方案模板.md) / [PRD](../02-产物层/S-Spec/PRD模板.md) / [架构设计](../02-产物层/S-Spec/架构设计模板.md) / [详细设计](../02-产物层/S-Spec/详细设计模板.md) / [UI-UX 设计](../02-产物层/S-Spec/UI-UX设计规范模板.md) |
| 出口质量门禁 | **QG-S** |

---

### B - Build（构建）

| 字段 | 内容 |
|------|------|
| 使命 | 把可执行规范→可运行代码（编码 / 审查 / 联调 / 集成） |
| 主责角色 | **Builder**（主）+ **Reviewer**（跨阶段审查） |
| HITL 模式 | **In**（关键模块）+ **Fallback**（简单模块 AI 自动 + 抽检） |
| 不可逆等级 | L2（代码可重构，但合并到主干后回滚成本上升） |
| Loop Schema | **Plan**: 拆任务到 PR 颗粒度 + 风险点标注 / **Act**: AI 主导生成代码 / **Observe**: 单测+lint+Eval+自评（客观） / **Reflect**: 资深工程师审 diff + 跨工种反馈（主观） / **Exit**: 单测覆盖率达标 + Reviewer 通过 + 联调集成通过 |
| 输入产物 | S 阶段输出（详设/接口契约/数据模型） + QG-S 通过的交接契约 |
| 输出产物 | [代码工程化产物](../02-产物层/B-Build/代码工程化规范.md)（源码 / 接口文档 / 联调报告） |
| 出口质量门禁 | **QG-B** |

---

### Ship - 交付（发布）

| 字段 | 内容 |
|------|------|
| 使命 | 把可运行代码→生产可用价值（测试 / 部署 / 验收 / 培训 / 移交） |
| 主责角色 | **Shipper**（主）+ **Reviewer**（验收评审） |
| HITL 模式 | **In**（L4 生产/验收：部署、客户验收必须人拍板） |
| 不可逆等级 | **L4**（生产部署、客户验收、对外承诺不可逆） |
| Loop Schema | **Plan**: 测试策略+部署方案+培训计划 / **Act**: 执行测试+部署+培训 / **Observe**: 测试通过率+性能+安全自动校验 / **Reflect**: 客户验收+用户体验反馈 / **Exit**: 测试 P0/P1 清零 + 部署成功 + 客户签字验收 |
| 输入产物 | B 阶段输出（源码/联调报告） + QG-B 通过的交接契约 |
| 输出产物 | [质量标准与验收报告](../02-产物层/S-Ship/质量标准与验收模板.md) / [部署与验收文档](../02-产物层/S-Ship/部署与验收文档模板.md) / 培训材料 / 运维手册 |
| 出口质量门禁 | **QG-Ship** |

---

### L - Learn（学习/复盘）

| 字段 | 内容 |
|------|------|
| 使命 | 把单次项目经验→可复用知识资产（复盘 / 沉淀 / 反哺体系） |
| 主责角色 | **Keeper** |
| HITL 模式 | **In**（L3 复盘结论影响后续项目） |
| 不可逆等级 | L3（错误的复盘结论会误导后续项目） |
| Loop Schema | **Plan**: 列复盘维度（目标/过程/质量/团队/AI 协作） / **Act**: 整理数据+访谈+写复盘报告 / **Observe**: 数据对比（计划vs实际 / QG 通过率 / Loop 次数） / **Reflect**: 团队共识+改进项 / **Exit**: 复盘报告评审通过 + 改进项录入体系 |
| 输入产物 | 全程交接契约链 + QG 历史数据 + Loop 度量数据 |
| 输出产物 | [项目复盘报告](../02-产物层/L-Learn/项目复盘模板.md) / 体系改进项 |
| 出口质量门禁 | —（终态，无下一阶段；改进项追踪由 Keeper 持续） |

## 五、阶段间流转规则

1. **顺序原则**：D→S→B→Ship→L 主路径，但允许阶段内多次 Loop 回溯。
2. **跨阶段回溯**：仅当下游发现上游根本性问题时触发，必须更新上游产物 + 重新签 QG + 在交接契约 `risk_flags` 字段记录。
3. **并行约束**：S 阶段内部方案/PRD 与架构/详设可部分并行（前半完成后后半启动）；其他阶段建议串行。
4. **L 阶段不可省略**：每个项目必须产出复盘报告，否则体系无法演化。

## 六、与外界模型对照

| 业界模型 | 与 DSBL 的对应 |
|----------|---------------|
| AWS AI-DLC 三阶段（Discover/Develop/Deploy） | D=S 前 / S+B / Ship |
| Anthropic Context Engineering 四原则 | 跨 DSBL 全程应用（详见 [00-理论层/04-上下文工程四原则.md](../00-理论层/04-上下文工程四原则.md)） |
| Spec-Driven Development | S 阶段是核心 |
| Loop Engineering（Anthropic agentic loop） | 每阶段内嵌 Loop 微循环 |

本体系不否认业界共识，而是把它们整合成可落地的工作流。
