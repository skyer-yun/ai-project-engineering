## 正文

### 一、Git 规范

#### 1.1 分支策略

- `main`：生产分支，受保护
- `develop`：开发主干
- `feature/{N}`：特性分支（一个特性一个分支）
- `fix/{N}`：修复分支
- `release/{N}`：发布分支

#### 1.2 Commit 规范（**atomic commit per feature**）

**铁律**：一个特性一个 commit。message 说**为什么**，不说**做了什么**。

```bash
# 格式
<type>(<scope>): <subject>

<body 说明为什么>

<footer 关联 issue/PRD>

# 类型 type
feat:     新功能
fix:      bug 修复
refactor: 重构（不影响功能）
perf:     性能优化
test:     测试相关
docs:     文档
chore:    构建/工具
style:    格式
ci:       CI/CD
```

**正确示例**：

```bash
git commit -m "feat(auth): 添加用户登录模块，支持 JWT 签发

响应 PRD Part 7 认证模块需求。采用 bcrypt 防 timing attack。
单测覆盖率 95%（4/4 用例：正常登录/密码错误/账号锁定/输入校验）。

Refs: PRD-XX-2026-001 Part 7"
```

**错误示例**：

```bash
# ❌ 多特性混一个 commit
git commit -m "update: 登录 + 注册 + 工单 + 报表"

# ❌ message 说做了什么不说为什么
git commit -m "add login.ts"

# ❌ 没说原因的重构
git commit -m "refactor: 改了一些代码"
```

#### 1.3 Code Review 规范

- 所有 PR 必须 ≥ 1 reviewer 批准
- 关键模块（认证/支付/订单）≥ 2 reviewer
- **审查不只看跑过，看实现合理性**（详见 §三 Gate 2）

### 二、Plan Mode 强制使用（B 核心）

> **铁律**：先 Plan 后 Execute，Plan 不通过不写代码。

#### 2.1 强制场景

| 场景 | Plan 要求 |
|------|----------|
| 新增模块 | 列出全部新文件 + 职责 + 依赖 |
| 修改现有代码 | 列出每处改动 + 原因 |
| 数据库变更 | DDL + 迁移脚本 + **回滚 DDL** |
| 接口变更 | 新接口标注 + 旧接口兼容性 |
| 重构 | ≥ 2 重构方案 + 影响范围 |

#### 2.2 Plan Mode 工作流

```
1. 输入需求（精确引用 PRD 章节 + 详设章节）
2. Plan Mode 输出：新增/修改文件清单 + 职责 + 依赖 + 单测计划 + 风险点
3. 人审 Plan → 批准/修改/拒绝
4. 批准后 Execute → 逐文件按 Plan 实现
5. ExitPlanMode Hook：Plan 审批记录写入 ADR
```

#### 2.3 Plan 禁止行为

| 禁止 | 后果 |
|------|------|
| 不写 Plan 直接开干 | 改动范围失控，返工率高 |
| "改一下"说不清改什么 | Plan 无效，回退重写 |
| 直接改表不写迁移 | 部署失败，数据丢失风险 |
| 破坏性变更不通知下游 | 联调阶段接口不一致 |

### 三、Human Gate（资深 Review Diff）

> B 编码完成 + 自测通过后，必须过 Gate 2 资深 Review。
>
> **73% HITL** 在代码审查场景体现得最典型——AI 跑过 ≠ 通过。

#### Gate 2 检查清单

| # | 检查项 | 通过标准 |
|---|--------|---------|
| 1 | 实现合理性 | 不只看跑过，看架构一致性 |
| 2 | 安全漏洞 | 注入/XSS/越权 = 0 |
| 3 | 性能隐患 | N+1/大循环/内存泄漏 = 0 |
| 4 | 单测有效 | 覆盖异常分支，非"覆盖率空壳" |
| 5 | 命名规范 | 团队 ESLint 通过 |
| 6 | ADR 一致 | 实现与架构决策一致 |

**通过标准**：无 P0/P1 缺陷 + reviewer 批准 merge。**不通过**：↩ B 修正。

### 四、代码质量规范

#### 4.1 命名

| 类型 | 规范 | 示例 |
|------|------|------|
| 变量/函数 | camelCase | `getUserInfo` |
| 类/接口 | PascalCase | `UserService` |
| 常量 | UPPER_SNAKE | `MAX_RETRY` |
| 文件 | kebab-case | `user-service.ts` |
| 私有 | 前缀 `_` | `_internalCache` |
| 布尔 | is/has/can 前缀 | `isLoading` / `hasPermission` |

#### 4.2 函数

- 单一职责（一个函数做一件事）
- 行数 ≤ 50 行（推荐 ≤ 30）
- 参数 ≤ 4 个（多了用对象）
- 副作用显式（不偷改全局）

#### 4.3 注释

- **What**：代码已说清，不重复
- **Why**：注释说原因，不说做了什么
- 接口必注释（JSDoc / JavaDoc）
- TODO 必带责任人和日期：`// TODO(zhang, 2026-07-01): xxx`

```typescript
/**
 * 用户登录
 * @param phone 手机号
 * @param password 明文密码（内部 bcrypt 校验）
 * @returns token + refreshToken
 * @throws {AuthError} 账号锁定/密码错误
 */
async function login(phone: string, password: string): Promise<TokenPair>
```

### 五、测试规范

#### 5.1 单测覆盖率（**QG-B.1/3.2 硬阻塞**）

| 模块类型 | 阈值 |
|---------|------|
| 核心模块（认证/支付/订单） | ≥ 90% |
| 一般模块 | ≥ 70% |
| 工具/纯函数 | ≥ 90% |
| UI 组件 | ≥ 50%（手动测试补充） |

#### 5.2 单测质量（防"覆盖率空壳"）

每个单测必须：
- ✅ 覆盖正常路径
- ✅ 覆盖异常路径（错误码/边界）
- ✅ 验证业务逻辑（不只是"没抛错"）
- ❌ 不要写"测试通过 = 跑了 1 次"的空壳

```typescript
// ✅ 好的单测
describe('login', () => {
  it('密码错误应返回 401', async () => {
    await expect(login('13800138000', 'wrong'))
      .rejects.toThrow(AuthError);
    // 验证具体错误码
  });

  it('账号锁定应返回 423', async () => { ... });
  it('连续 5 次失败应锁定账号', async () => { ... });
});

// ❌ 空壳单测
it('login works', () => {
  expect(typeof login).toBe('function');  // 这就是"覆盖率空壳"
});
```

#### 5.3 测试类型

| 类型 | 工具 | 频率 |
|------|------|------|
| 单元测试 | Jest/Vitest/PyTest | 每次提交 |
| 集成测试 | Jest + Supertest | 每日 |
| E2E 测试 | Playwright/Cypress | 每周 |
| 性能测试 | JMeter/k6 | 发布前 |
| 安全测试 | SonarQube/Snyk | 发布前 |

### 六、错误处理规范

#### 6.1 错误分类

| 类型 | 例子 | 处理 |
|------|------|------|
| 输入错误 | 参数校验失败 | 返回 400 + 友好提示 |
| 业务错误 | 余额不足 | 返回 4xx + 错误码 |
| 鉴权错误 | 未登录/无权限 | 返回 401/403 |
| 系统错误 | DB 异常 | 返回 5xx + 日志 + 告警 |

#### 6.2 错误码规范

格式：`{MODULE}_{NUMBER}`，如 `AUTH_001` / `ORDER_002`

详见 [02-设计阶段/详细设计模板.md](../02-设计阶段/详细设计模板.md) §1.3。

#### 6.3 异常处理原则

- 不要静默吞异常（catch + 不处理 = 禁止）
- 不要返回 raw stack 给客户端
- 必有全局异常处理器
- 错误日志要带 traceId

### 七、日志规范

#### 7.1 日志级别

| 级别 | 用途 | 示例 |
|------|------|------|
| ERROR | 系统错误，需立即处理 | DB 连接失败 |
| WARN | 潜在风险 | 重试 3 次才成功 |
| INFO | 关键业务节点 | 用户登录成功 |
| DEBUG | 调试信息（生产关闭） | 入参出参 |

#### 7.2 日志内容

必含：
- timestamp（ISO 8601）
- level
- traceId（链路追踪）
- userId（如有）
- message
- context（结构化字段）

```typescript
logger.info({
  userId: '12345',
  action: 'login',
  ip: '1.2.3.4',
  duration: 234,
}, 'user logged in');
```

#### 7.3 日志禁忌

- ❌ 不要日志密码/token/身份证（脱敏）
- ❌ 不要在高频循环打 INFO（性能）
- ❌ 不要日志内容用拼字符串（用结构化）

## Loop 微循环 字段（B 编码详细 Loop）

```
Plan     → Claude Code Plan Mode：文件改动清单 + 依赖分析 + 单测目标
Act      → 按 Plan 逐文件实现，每特性写完立即跑单测
Observe  → 单测覆盖达标？lint 零严重？编译通过？
Reflect  → 资深工程师审 diff（不只看跑过，看实现合理性）
Exit     → 审查通过 → atomic commit；↩ 不通过 → 回 Plan 修正
```

详见 [01-标准层/02-Loop 微循环规范.md](../../01-标准层/02-Loop%20Schema规范.md) §四。
