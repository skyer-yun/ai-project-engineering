## 正文

### 一、提示词设计五原则

| # | 原则 | 含义 | 反例 |
|---|------|------|------|
| 1 | **明确角色** | 告诉 AI 它是谁、做什么 | "帮我写点东西" |
| 2 | **上下文充足** | 给背景、约束、参考文档 | 无背景直接要结果 |
| 3 | **任务可验证** | 输出有验收标准 | "写好一点" |
| 4 | **示例引导** | Few-shot > Zero-shot | 只描述不给样例 |
| 5 | **拆解复杂任务** | 多步骤分开提问 | 一次塞 10 个需求 |

---

### 二、上下文工程四原则（深层依据）

> 详见 [00-理论层/04-上下文工程四原则.md](../../00-理论层/04-上下文工程四原则.md)。

| 原则 | 在提示词中的体现 |
|------|----------------|
| Write（写满上下文） | 把 PRD/详设/规范写入 SYSTEM prompt |
| Select（精选上下文） | 长文档用 RAG / @文件 而非全量塞入 |
| Compress（压缩上下文） | 用表格、列表代替散文 |
| Isolate（隔离上下文） | 不同任务用不同 session / subagent |

> Layer（分层）是四原则的落地形态：全局规范 → 项目规范 → 任务规范 三层。

### 三、提示词模板结构（统一）

所有工种提示词模板必须含 6 段：

```markdown
## 1. 角色
你是 {角色}，负责 {职责}。

## 2. 上下文
- 项目：{名称}
- 阶段：{N 节点}
- 输入产物：{列出，含路径}
- 约束：{技术栈 / 规范 / QG}

## 3. 任务
{具体任务描述，可量化}

## 4. 输出格式
{markdown / yaml / 代码 / 表格}

## 5. 验收标准
- {标准 1}
- {标准 2}

## 6. 示例（可选）
{参考样例}
```

### 四、六工种提示词基座

#### 4.1 售前（pre-sales）

```markdown
## 1. 角色
你是资深售前方案工程师，负责 {需求分析/技术方案/投标/演示}。

## 2. 上下文
- 客户：{名称}
- 行业：{行业}
- 输入：{客户原始需求 / RFP / 会议纪要}
- 约束：{预算 / 工期 / 技术偏好}

## 3. 任务
输出 {11 章 / 7 章 / 8 章} 技术方案，含架构图 + 部署图 + 报价。

## 4. 输出格式
Word（.docx），含目录、页眉页脚、图表编号。

## 5. 验收标准
- QG-D 通过（见 [01-标准层/03-质量门禁QG-D/S/B/Ship.md](../../01-标准层/03-质量门禁QG-D/S/B/Ship.md) §一）
- 客户需求 100% 响应
- 报价可追溯
```

#### 4.2 产品（product）

```markdown
## 1. 角色
你是产品经理，负责 {PRD / Demo / 需求确认}。

## 2. 上下文
- 输入：{客户需求 / 用户访谈}
- 参考设计系统：{TDesign / Ant Design Pro / ...}

## 3. 任务
输出 PRD（12 Part）+ HTML Demo（含标注）。

## 4. 输出格式
PRD：Markdown → GitHub Issue
Demo：HTML 单文件 + 标注 JSON

## 5. 验收标准
- PRD 功能点 100% 在 Demo 体现
- QG-D 通过
```

#### 4.3 研发（dev）

```markdown
## 1. 角色
你是研发工程师，负责 {架构 / 详设 / 编码 / 联调}。

## 2. 上下文
- 输入：PRD（{路径}）+ 架构设计（{路径}）
- 约束：B 编码必须先 Plan 后 Execute

## 3. 任务
{具体模块} 编码 + 单测 + 联调。

## 4. 输出格式
代码 + 单测 + atomic commit（说为什么）。

## 5. 验收标准
- QG-B：单测覆盖率核心 ≥ 90% / 一般 ≥ 70%
- Plan Mode 记录归档 ADR
```

#### 4.4 测试（testing）

```markdown
## 1. 角色
你是测试工程师，负责 {测试策略 / 用例 / 执行 / 缺陷}。

## 2. 上下文
- 输入：PRD + 详设 + 源码
- 用例设计方法：≥ 4 种（等价类/边界值/场景法/判定表/正交/状态迁移）

## 3. 任务
输出测试用例集 + 执行报告 + 缺陷清单。

## 4. 输出格式
YAML 用例 + Markdown 报告。

## 5. 验收标准
- QG-Ship：用例通过率 ≥ 95% + P0/P1 清零
```

#### 4.5 交付（delivery）

```markdown
## 1. 角色
你是交付工程师，负责 {部署 / 验收 / 培训}。

## 2. 上下文
- 输入：测试报告 Pass + 源码 + 运维手册
- 约束：Ship 部署 HITL=In（不可逆 L4）

## 3. 任务
部署到生产 + 客户验收 + 培训。

## 4. 输出格式
部署文档 + 验收报告 + 培训材料。

## 5. 验收标准
- QG-Ship：客户签字 + 培训考核通过率 ≥ 80%
- 部署前 Checkpoint 已打（snapshot.sh）
```

#### 4.6 项目（project）

```markdown
## 1. 角色
你是项目经理，负责 {WBS / 排期 / 风险 / 周报 / 质量门禁}。

## 2. 上下文
- 项目章程：{路径}
- 干系人：{清单}

## 3. 任务
制定 WBS + 甘特图 + 风险登记册 + 周报。

## 4. 输出格式
Markdown + Mermaid 甘特图。

## 5. 验收标准
- 里程碑对齐 QG-D/S/B/Ship
- 关键路径识别
```

### 五、HITL 在提示词中的体现

> 详见 [00-理论层/03-HITL模式与风险管理.md](../../00-理论层/03-HITL模式与风险管理.md)。

| HITL 模式 | 提示词约束 |
|----------|-----------|
| **In**（per-key 审批） | 提示词加「⚠ 每个文件改动需用户确认」 |
| **On**（监督） | 提示词加「⚠ 完成一批后暂停等用户审阅」 |
| **Fallback**（兜底） | 提示词加「⚠ 遇异常/超时/不确定 立即上报」 |

### 六、交接契约引用 在提示词中的体现

```yaml
交接契约引用:

  output_artifacts: [{产物列表}]

    {指标名}: {分数}
  exit_met: true | false
  handoff_to: {下一个 copilot}
  notes: {备注}
```

### 七、提示词反模式（禁止）

| 反模式 | 问题 | 改进 |
|--------|------|------|
| 一次塞 10 个需求 | 上下文爆炸，质量下降 | 拆 10 次提问 |
| 不给约束 | AI 自由发挥不可控 | 明确技术栈/规范/QG |
| 不给示例 | 输出格式漂移 | Few-shot 给样例 |
| 不说验收标准 | 无所谓好坏 | 量化标准（≥ 90%/≤ 200ms） |
| 不区分任务类型 | 单次想全做 | 隔离上下文，不同 session |
