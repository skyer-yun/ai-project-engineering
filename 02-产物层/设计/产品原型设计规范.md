## 一、定位与价值

原型不是「画个样子」，而是**可评审、可反向生成 PRD 的结构化资产**。本规范要求原型以「四件套」产出，使页面、需求、标注三者机器可校验、双向可追溯：

```text
REQ-NNN（需求清单）
   ↕ 双向核对
页面 ID（页面树）+ ANN-NNN（标注数据）
   ↕ 反向引用
PRD 功能总览 + 原型引用章节
```

**四件套清单**：

| # | 产物 | 格式 | 作用 |
|---|------|------|------|
| 1 | 页面树 | YAML | 页面清单与层级结构（类站点地图），机器可校验 |
| 2 | 高保真原型包 | HTML（index.html + pages/**） | 可点击走查的可视化原型 |
| 3 | 标注数据 | JSON | 需求点到页面元素的挂接（PRD 反向引用的锚点） |
| 4 | 原型说明 | MD | 走查路径 + 跳转关系 + 覆盖矩阵（人工评审入口） |

存储位置：`项目文档/{项目}/设计/原型/`，结构如下：

```text
项目文档/{项目}/设计/原型/
├── 页面树.yaml
├── 标注数据.json
├── 原型说明-v1.0.md
└── 原型包/
    ├── index.html              # 导航入口
    └── pages/
        ├── 01-登录.html
        ├── 01-登录/
        │   └── 01-短信登录.html
        └── 02-工作台.html
```

## 二、产物一：页面树（页面树.yaml）

### 2.1 结构约定

- 任意层级树；**每页一个独立画布（独立 HTML 文件）**；
- **同页多状态/相似场景在同一画布铺开**（`states` 描述，不拆节点）——避免节点爆炸；
- 跳转/热区目标页（`links.to`）**必须在树中有原始页**——目标页不藏在别的页面里。

### 2.2 Schema

```yaml
design_system: ant-design-pro        # 选定的设计系统（全树唯一，不得混用）
pages:
  - id: login                        # 页面 ID，全局唯一，kebab-case
    title: 登录页
    path: pages/01-登录.html         # 原型包内相对路径
    responsibility: 用户身份认证入口   # 一句话页面职责
    states:                          # 同画布铺开的多状态（可选）
      - name: 默认
      - name: 错误提示
        area: "右侧第二屏"           # 画布内位置描述（可选）
    children:                        # 子页面，任意层级，递归同构（可选）
      - id: login-sms
        title: 短信登录
        path: pages/01-登录/01-短信登录.html
        responsibility: 手机号+验证码登录
    links:                           # 跳转/热区（可选）
      - to: home                     # 目标必须是树中存在的页面 ID
        trigger: 登录成功
```

### 2.3 校验规则（工具侧强制，5 项）

| # | 规则 | 说明 |
|---|------|------|
| 1 | `id` 全局唯一 | 含所有层级，不得重复 |
| 2 | `path` 唯一且文件存在 | 原型包内可定位到实际 HTML 文件 |
| 3 | `links.to` 必须命中某 `id` | 悬空跳转 = 校验失败 |
| 4 | `children` 递归同构 | 子节点结构与父节点相同 |
| 5 | 父页文件与子页目录同名并存 | `pages/01-登录.html` + `pages/01-登录/` 同时存在，是有意约定（父页是子页组的入口） |

## 三、产物二：高保真原型包

### 3.1 结构约定

- `index.html` 为唯一导航入口，按页面树层级组织链接；
- 页面目录结构与页面树 `path` 一一对应（见 §一 存储结构示例）；
- 使用选定设计系统的 Token 与组件规范，**全包只用一套设计系统，不得混用**（`页面树.yaml` 顶部 `design_system` 字段声明）。

### 3.2 纯净度要求（QG-设计.12 检查项）

原型包是**交付级资产**，必须纯净：

- ❌ 无编辑器残留代码（调试面板/临时 console/注释掉的实验代码）；
- ❌ 无运行时外部依赖泄漏（开发服务地址、本机绝对路径）；
- ❌ 无增强态功能混入（演示用高亮、批注浮层等放在增强版本，不进原型包本体）；
- ✅ 浏览器直接打开 `index.html` 即可完整走查。

> 若需面向评审的「带标注版」，由原型包 + 标注数据**合成生成**为独立文件（如 `原型包-带标注.html`），原型包本体保持纯净。

## 四、产物三：标注数据（标注数据.json）

### 4.1 Schema

```json
{
  "version": 3,
  "items": [
    {
      "id": "ANN-001",
      "page": "login",
      "selector": "#login-form .submit-btn",
      "req": "REQ-001",
      "note": "连续点击防抖，提交后按钮置灰",
      "author": "zhangsan",
      "status": "open"
    },
    {
      "id": "ANN-002",
      "page": "login-sms",
      "selector": ".sms-countdown",
      "req": "REQ-002",
      "note": "验证码 60s 倒计时，倒计时中禁用重发",
      "author": "zhangsan",
      "status": "resolved"
    }
  ]
}
```

### 4.2 字段约定

| 字段 | 约定 |
|------|------|
| `id` | 格式 `ANN-NNN`，全局唯一，只追加不重用；PRD 引用标注时使用 ANN 编号 |
| `page` | 必须存在于页面树（`pages[].id`） |
| `selector` | 原型包对应页面内可定位的 CSS 选择器 |
| `req` | 必须存在于需求清单（`REQ-NNN`）——**每条 P0 需求至少 1 条标注挂接到具体页面元素** |
| `note` | 需求点描述：写给研发看的实现指令，不是给自己看的备忘 |
| `status` | `open`（待处理）/ `resolved`（已落实到 PRD） |

### 4.3 校验规则

1. `id` 全局唯一；2. `page` 必须命中页面树；3. `req` 必须命中需求清单；4. P0 需求标注覆盖率 100%（硬指标见 [01-标准层/06-产物质量硬指标库.md](../01-标准层/06-产物质量硬指标库.md) §三）。

## 六、原型 → PRD 反向引用机制

PRD 不重写需求，**反向引用原型资产**。S 阶段内部（原型→PRD）交接时，在 PRD 文档信息区登记 `prototype_ref`：

```yaml
prototype_ref:
  page_tree_snapshot: "设计/原型/页面树.yaml@v1.2"     # 页面树快照版本
  annotation_version: "设计/原型/标注数据.json@v3"      # 标注数据版本
  requirement_coverage: "设计/原型/原型说明-v1.0.md#七需求页面覆盖矩阵"
  design_system: "ant-design-pro"
```

PRD 中的引用规则：

- PRD 功能总览表：每行功能点带「需求 ID」与「原型页面 ID」两列；
- PRD 交互章节：引用页面 ID + ANN 编号（如 `login 页面 ANN-001`），不复制标注内容；
- 原型后续演化（页面树 major 版本变更）→ PRD 同步 minor 版本 + diff 记录。

## 七、QG 映射与验收

本规范对应 QG-设计.12「原型完整性」，核对项：

| 检查项 | 通过标准 | 状态 |
|--------|---------|------|
| 页面树覆盖需求 | 需求↔页面覆盖矩阵双向核对：每条 P0 需求 ≥1 个承载页面 | ☐ |
| 页面树校验 5 项 | §2.3 全过（工具侧校验） | ☐ |
| 核心流程可走通 | 原型说明 §三 走查路径在原型包中可点击走通 | ☐ |
| 标注挂接 | 每条 P0 需求 ≥1 条标注（ANN-NNN）挂接到具体页面元素 | ☐ |
| 设计系统一致 | 全包单一设计系统，与页面树声明一致 | ☐ |
| 纯净度 | §3.2 全过 | ☐ |

完整 QG-设计 checklist 见 [01-标准层/03-质量门禁QG-需求至QG-交付.md](../01-标准层/03-质量门禁QG-需求至QG-交付.md) §三。
