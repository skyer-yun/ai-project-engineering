# HITL 模式与不可逆性矩阵

> **定位**：本文件是「3 种 HITL 模式」「不可逆性矩阵」「风险分级」的**唯一权威源**。其他文档涉及 HITL 时一律引用本文件。
> **业界锚**：Anthropic *Measuring AI Agent Autonomy in Practice*（2026-02 论文）；业界主流 AI 工具的 Checkpoint/Plan Mode 设计共识。

---

## 一、73% 实证——为什么"全自动"是营销幻觉

Anthropic 2026-02 论文《Measuring AI Agent Autonomy in Practice》给出的业界实测数据：

| 模式 | 占比 | 含义 |
|------|------|------|
| **HITL-In**（每关键阶段审批） | **73%** | 高风险/不可逆/客户面向 |
| **HITL-On**（监督不干预，可回滚） | **26.2%** | 中风险/可回滚/内部协作 |
| **全自主** | **0.8%** | 低风险/完全可逆/重复劳动 |

**结论**：**给团队推广时不要卖"AI 全自动"幻觉**。73% + 26.2% = 99.2% 的任务都需要人在环上，只是参与方式不同。

## 二、3 种 HITL 模式（按风险分级）

不同角色/不同任务用不同 HITL 模式，**不是一刀切**：

### 模式 1：HITL-In（Human-in-the-Loop，每关键阶段审批）

- **何时用**：高风险 / 不可逆 / 客户面向 / 合规要求
- **行为**：AI 完成关键阶段后**必须人工审批**，不批不准 Exit
- **典型 DSBL 场景**：
  - D 阶段：需求确认（客户面向，错则全错）
  - S 阶段：技术方案评审 / 架构评审（决定后续方向）
  - B 阶段：关键模块编码（核心业务逻辑）
  - Ship 阶段：生产部署 / 客户验收签字（不可逆）
  - L 阶段：项目复盘报告（影响后续项目）
- **工具支撑**：Plan Mode 强制审批 + ExitPlanMode Hook + 签字单

### 模式 2：HITL-On（Human-on-the-Loop，监督不干预）

- **何时用**：中风险 / 可回滚 / 内部协作
- **行为**：AI 自主推进，人**监督但不打断**；有问题用回滚而非阻止
- **典型 DSBL 场景**：
  - D 阶段：需求分析整理（内部产物，可重做）
  - S 阶段：详细设计 / UI-UX 设计（开发负责人审）
  - B 阶段：一般模块编码 / 联调集成（开发+测试联合评审）
  - Ship 阶段：测试执行 / 培训移交（反馈驱动）
- **工具支撑**：Checkpoint 一键回滚 + Review 评审会

### 模式 3：HITL-Fallback（Human-as-Fallback，默认自动，失败兜底）

- **何时用**：低风险 / 完全可逆 / 重复劳动
- **行为**：AI 默认全自动，**失败时人工兜底**
- **典型场景**：
  - 单元测试生成（CRUD 模板代码）
  - 文档格式化（markdown lint）
  - 日志分析（重复模式识别）
  - B 阶段编码的 CRUD/重复部分
  - Ship 阶段的自动化回归测试
- **工具支撑**：Eval 自动卡 + 失败时通知人

## 三、不可逆性矩阵——选 HITL 模式的根本依据

选哪种 HITL 模式，本质上看**这个动作不可逆到什么程度**：

| 不可逆等级 | 含义 | 典型动作 | HITL 模式 |
|-----------|------|---------|----------|
| **L4 不可逆** | 客户侧已发生，无法撤回 | 客户验收签字、生产部署上线、合同签订 | **In**（必须审批） |
| **L3 高成本可逆** | 撤回需重大返工 | 架构定稿、PRD 评审通过、需求确认、复盘结论 | **In**（评审会必备） |
| **L2 中成本可逆** | 撤回需局部返工 | 详细设计、一般模块编码、测试策略 | **On**（监督可回滚） |
| **L1 低成本可逆** | 撤回几乎无成本 | 单测代码、文档格式、CRUD 模板 | **Fallback**（自动） |

**铁律**：HITL 模式不是按"角色偏好"选，是按**动作不可逆等级**选。同一个角色在不同阶段可能用不同模式（如 Builder：B 关键模块用 In，CRUD 用 Fallback）。

> 本体系用 L1-L4 描述**不可逆等级**。AI 参与度另用 In/On/Fallback 三模式描述（不再单独分级），详见 [03-执行层/03-HITL规则表.md](../03-执行层/03-HITL规则表.md)。

> 完整阶段定义见 [01-标准层/01-DSBL五阶段定义.md](../01-标准层/01-DSBL五阶段定义.md)。本表是 HITL 维度的**权威摘要**。

| 阶段 | 主责角色 | HITL 模式 | 不可逆等级 | 人工 Gate 形态 |
|------|---------|----------|-----------|--------------|
| **D** Discover | Spec-Writer | **In** | L3 | 客户面访必须人在场 + 干系人签字 |
| **S** Spec | Spec-Writer → Builder | **In** | L3 | 方案评审 + 架构评审 + 客户确认 |
| **B** Build | Builder + Reviewer | **In + Fallback**（关键 In，CRUD F） | L2 | Plan Mode 审批 + atomic commit + Reviewer review |
| **Ship** | Shipper + Reviewer | **In** | **L4** | **部署前快照 + 业务签字 + 客户验收** |
| **L** Learn | Keeper | **In** | L3 | **复盘报告必备签字** |

## 五、风险分级与升级路径

### 5.1 风险分级（按影响范围）

| 等级 | 含义 | 触发条件 | 应对 |
|------|------|---------|------|
| **R1 阻塞** | 项目无法继续 | QG 多次不过 / 客户重大变更 / 关键人员离场 | **立即升级**：Keeper 通知 PM，启动应急预案 |
| **R2 严重** | 影响交付质量或周期 | Loop 超 5 轮 / 缺陷逃脱率高 / Eval 分持续低 | 24h 内升级：技术负责人介入 |
| **R3 一般** | 局部返工 | 单阶段 Loop 2-3 轮 / 个别缺陷 | 角色内消化 |
| **R4 轻微** | 几乎无影响 | 单次修正 | 自动闭环 |

### 5.2 Loop 异常的升级路径

交接契约每阶段记录 `iterations` 字段。**异常判定**：

| 信号 | 含义 | 应对 |
|------|------|------|
| `iteration > 5` | Loop 卡死 | 升级到 R2，技术负责人介入 |
| `iteration > 8` | 严重卡死 | 升级到 R1，启动根因分析 |
| `eval_score` 持续低于阈值 | Eval 不过 | ↩ 上游阶段（按 QG 映射） |
| `reflect_passed: false` 多次 | 人审不通过 | 暂停 Loop，组织评审会 |

## 六、Plan Mode + Checkpoint——HITL 的工具落地

### 6.1 Plan Mode 强制使用场景

> Plan Mode 是工具中立概念——业界主流 AI 工具都支持类似机制，体系只约定"先 Plan 后 Act"的规则，不绑定具体工具。

| 场景 | Plan Mode 要求 |
|------|--------------|
| B 阶段关键模块编码 | **强制**：先 Plan 列文件改动+单测计划，人审批后 Execute |
| S 阶段架构/详设文档 | **强制**：先列章节大纲，评审通过后写正文 |
| Ship 阶段部署脚本 | **强制**：先列步骤+回滚预案，运维审批后执行 |
| S 阶段 PRD 编写 | **强制**：先列 12 部分大纲 + 用户故事 |
| 其他场景 | 推荐 |

> 详见各角色 Playbook「入场姿势」节。

### 6.2 Checkpoint 协议

**业界共识**（多款主流 AI 编码工具）：**每次有意义状态变更前快照 + 一键回滚 + 人工 review**。

落到本体系：

| 阶段 | Checkpoint 形态 |
|------|----------------|
| S 阶段评审通过 | Git commit / 文档版本号 / Diff 记录 |
| B 阶段编码 | Git atomic commit + Plan Mode 审批 |
| Ship 阶段测试 | 测试报告版本 + 缺陷清单版本 |
| Ship 阶段部署 | **部署前完整快照（含 DB + 配置 + AI context）** |
| 全程 | 交接契约带 Loop 签名 |

工具：[04-工具层/03-Checkpoint脚本/](../04-工具层/03-Checkpoint脚本/)。

**团队收益**：AI 写错了不怕——一键回滚到上个 checkpoint。这是破"AI 不靠谱"心理障碍的最直接武器。

## 七、推广时的 HITL 沟通策略

| 团队角色 | 关注点 | 沟通话术 |
|---------|--------|---------|
| 管理层 | AI 替代多少人 | "Anthropic 2026-02 论文实证：73% HITL / 0.8% 全自主。AI 自动化的是回路里的重复劳动，不是替代人。" |
| 资深工程师 | AI 代码不靠谱 | "B 阶段关键模块强制 Plan Mode + Reviewer review diff + atomic commit 一键回滚。AI 跑过 ≠ 通过。" |
| 客户 | 数据安全/合规 | "Ship 阶段部署前完整快照 + 业务签字 + 客户验收签字。所有客户面向阶段 HITL-In。" |
| 新人 | 不会用 AI | "打开任意 AI 工具按 Playbook 第一句话开场，剩下按 5 字段 Loop 推进。Checkpoint 兜底，错了回滚。" |
