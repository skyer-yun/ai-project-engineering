## 一、为什么需要 DSBL——单 Loop 或单敏捷都不够

| 模式 | 长处 | 致命短板 |
|------|------|---------|
| 纯敏捷（Scrum/Kanban） | 节奏清晰、人主导、风险可控 | AI 介入后没有微观执行约束；"完成"定义模糊；产物参差 |
| 纯 Agentic Loop（Anthropic） | AI 自主+工具循环、可观测 | 单层 Loop 缺节奏与方向；不知道什么时候该让 AI 干、什么时候该让人审 |
| 纯瀑布（阶段瀑布式接力） | 阶段清晰、产物标准齐全 | 单向接力，回溯困难；不适应需求变更 |
| **DSBL × Loop × HITL（本体系）** | 阶段定方向、Loop 定节拍、任务定动作；**人始终在环上** | — |

**核心主张**：把项目宏观节奏（Discover/Spec/Build/Ship/Learn 五阶段）和 Agentic Loop 的**微循环结构**（Plan/Act/Observe/Reflect/Exit 五字段）拼起来——**阶段来自业界共识，循环来自 Anthropic Loop，监督来自 HITL**。

## 二、三层嵌套模型

```
                         ┌─────────────────────────────────────────────┐
                         │  外环 · 项目环（Sprint 级，DSBL 主线）         │
                         │  分 Sprint → 每 Sprint 走一组 DSBL 阶段 →     │
                         │  Review/Retrospective → 下个 Sprint           │
                         └────────────────────┬────────────────────────┘
                                              │ 每个阶段内部
                                              ▼
                ┌─────────────────────────────────────────────────────┐
                │  中环 · 阶段环（Loop 微循环，5 字段强制结构）          │
                │  Plan → Act → Observe → Reflect → Exit                │
                │  不达标 ↩ Plan 重循环；达标 → 进入下一阶段             │
                └────────────────────────────┬────────────────────────┘
                                              │ 每个角色任务内部
                                              ▼
                ┌─────────────────────────────────────────────────────┐
                │  内环 · 任务环（最小粒度，4 步微循环）                  │
                │  指令 → 执行 → 审阅 → 修正                             │
                │  配 Checkpoint（状态变更前快照，可一键回滚）            │
                └─────────────────────────────────────────────────────┘
```

**三层关系**：外环定**方向**（这个 Sprint 走哪些阶段）、中环定**节拍**（每阶段何时 Exit）、内环定**动作**（每个原子任务怎么落地）。**人始终在环上**，不在环外。

## 三、迭代骨架 × Loop 微循环——核心模型

### 3.1 外环（项目级 Sprint）

**敏捷骨架**：把整个项目切成若干 Sprint（通常 2-4 周/Sprint）。每个 Sprint 不是"全流程一遍"，而是**有目标地走一组 DSBL 阶段**：

| 项目类型 | Sprint 切法 | 典型路径 |
|---------|------------|---------|
| **瀑布型**（合规重、需求稳定） | 1 Sprint = 1 阶段 | Sprint 1 = D / Sprint 2 = S / Sprint 3 = B / Sprint 4 = Ship / Sprint 5 = L |
| **迭代型 MVP**（创业/新产品） | 1 Sprint = 1 端到端薄片 | Sprint 1 = D 关键需求 + S 核心 PRD + B 关键编码 + Ship 关键测试；后续 Sprint 补回 |
| **敏捷型**（成熟产品迭代） | 1 Sprint = 1 完整 S+B+Ship 闭环 | 每 Sprint 走完整 规范→编码→测试；Ship 季度发布 |

> **决策点**：D-Discover 阶段必须明示项目类型，决定外环节奏。**Keeper 负责声明**，写入项目章程。

### 3.2 中环（阶段级 Loop）

每个阶段内部强制 **5 字段 Loop**（详见 [01-标准层/02-Loop微循环规范.md](../01-标准层/02-Loop微循环规范.md)）：

```
Plan     → 列任务 + 风险 + 依赖
Act      → AI 主导生成产物
Observe  → 跑 Eval + 自评 + 工具反馈（客观）
Reflect  → 人审阅 + 跨角色反馈（主观）
Exit     → 达阈值 → 进下一阶段；不达标 ↩ Plan
```

**铁律**：Observe（客观 Eval）与 Reflect（主观人评）**必须分离**。两者都过才能 Exit。这是破"AI 跑过 = 通过"幻觉的根本约束。

### 3.3 内环（任务级 4 步）

最细粒度的微循环，对应角色 Playbook 里每一个具体任务：

```
指令（用户/AI 一句话触发语）
  ↓
执行（AI 工具产出，工具中立）
  ↓
审阅（人/AI Review）
  ↓
修正（按 Review 返工）→ 完成 → 下一个任务
```

**Checkpoint 协议**：每次内环状态变更前打 snapshot，可一键回滚。详见 [04-工具层/03-Checkpoint脚本/](../04-工具层/03-Checkpoint脚本/)。

## 四、项目类型路由——破"该走瀑布还是敏捷"的争议

不同项目类型走不同外环路径，**DSBL 五阶段名不变**，只是组合方式不同：

```
瀑布型：    D → S → B → Ship → L（顺序走）

迭代型 MVP：Sprint 1 = D + S核心 + B关键编码 + Ship关键测试 + L回顾（端到端薄片）
            Sprint 2..N 补回各阶段剩余

敏捷型：    每 Sprint = S + B + Ship（完整闭环，对应一个特性）
            D 在季度规划，L 在年度复盘
```

**核心**：DSBL 是**地图**，不是**路径**。Sprint 节奏决定怎么走这张地图。

## 五、人始终在环上——HITL 实证

业界主流说法是"AI 全自动"，但 Anthropic *Measuring AI Agent Autonomy in Practice*（2026-02 论文）实证数据是：

| 模式 | 占比 | 含义 |
|------|------|------|
| HITL-In（每关键阶段审批） | **73%** | 高风险/不可逆/客户面向 |
| HITL-On（监督不干预） | **26.2%** | 中风险/可回滚/内部协作 |
| 全自主 | **0.8%** | 低风险/完全可逆/重复劳动 |

**结论**：不要给团队卖"AI 全自动"幻觉。本体系所有阶段都标注 HITL 模式，详见 [03-HITL模式与不可逆性矩阵.md](./03-HITL模式与不可逆性矩阵.md)。

## 六、工具中立——AI 工具是武器，不是体系

本体系不绑定任何具体 AI 工具（任意 AI 工具 / 用户自带工具）。体系只约定：

- **阶段定义**（D/S/B/Ship/L）
- **微循环结构**（Plan/Act/Observe/Reflect/Exit）
- **质量门禁**（QG-D/S/B/Ship）
- **交接契约**（YAML Schema）
- **HITL 模式**（In/On/Fallback）

具体 AI 工具通过 [05-适配层/](../05-适配层/) 接入：每份适配指南说明"如何用 XX 工具执行本体系"。1 个角色可由多工具承担，1 个工具也可跨角色。
