## 一、业界共识（2024-12 ~ 2026-02）

本体系不是空想，是下面业界共识的**合成**：

### 共识 1：Anthropic Agentic Loop（Agent 的本质是循环）

**出处**：Anthropic *Building Effective Agents* (2024-12)

**核心论断**：
> "LLMs autonomously using tools in a loop" —— Agent 的本质是「LLM 自主使用工具的循环」。

**对本体系的意义**：
- 五阶段 每阶段内嵌 5 字段 Loop（Plan/Act/Observe/Reflect/Exit）
- Loop 不是营销词，是 Anthropic 官方定义的 Agent 本质

### 共识 2：Context Engineering（上下文工程是 2025 年新范式）

**出处**：
- Tobi Lütke (Shopify CEO) *Context Engineering* 系列 (2025-06)
- Karpathy *Context Engineering* 演讲
- Philipp Schmid (LangChain) *Context Engineering for AI Agents*
- Anthropic *Effective Context Engineering for AI Agents* (2025-09)

**核心论断**：
> "Prompt Engineering 已死，Context Engineering 当立。" —— 2025 年下半年共识。
>
> "LLM 是 CPU，context window 是 RAM。你不会'写好一行字'给 RAM，你要管理整个地址空间。" —— Karpathy 类比。

**对本体系的意义**：
- 跨角色对齐机制升级为「上下文工程层」
- 四原则：Write / Select / Compress / Isolate（详见 [04-上下文工程四原则.md](./04-上下文工程四原则.md)）

### 共识 3：Eval-Driven Development（评测驱动开发）

**出处**：
- OpenAI Evals 框架
- Anthropic *Demystifying evals for AI agents*
- Cursor / Replit 实践文章

**核心论断**：
> 不要靠"感觉 AI 写得好"，要用**可量化的 Eval**（覆盖率/通过率/响应时间/缺陷数）驱动开发。

**对本体系的意义**：
- QG-需求 / QG-设计 / QG-开发 / QG-交付 是「Eval 反馈点」
- 每阶段 Loop 的 Observe 字段强制跑 Eval
- 详见 [01-标准层/03-质量门禁QG-需求至QG-交付.md](../01-标准层/03-质量门禁QG-需求至QG-交付.md)

### 共识 4：HITL 三件套（Checkpoint + Plan Gate + Human Review）

**出处**：
- Anthropic *Measuring AI Agent Autonomy in Practice*（2026-02 论文，73% HITL 数据）
- Cursor Checkpoints + Specs 设计
- Cognition Devin ACI（Agent-Computer Interface）
- Replit AI 协作设计
- Claude Code Plan Mode + ExitPlanMode Hook

**核心论断**：
> 业界主流 AI 编程工具都标配 **三件套**：① 状态变更前快照（Checkpoint）② Plan 先审后执行（Plan Gate）③ 关键阶段人工 Review。
>
> Anthropic 2026-02 论文实证数据：73% 任务 HITL-In / 26.2% HITL-On / 仅 0.8% 全自主。

**对本体系的意义**：
- 每阶段标注 HITL 模式（In/On/Fallback）
- Checkpoint 协议 + Plan Mode 强制 + 资深 Review 制度
- 详见 [03-HITL模式与不可逆性矩阵.md](./03-HITL模式与不可逆性矩阵.md)

### 共识 5：AWS AI-DLC 三阶段模型

**出处**：AWS AI-Driven Development Lifecycle（AI-DLC）

**核心论断**：
> AI 时代软件生命周期分三段：Discover（发现）→ Develop（开发）→ Deploy（部署）。

**对本体系的意义**：
- 五阶段在 AWS 三段基础上**拆出需求与复盘**（防止 AI 跳过需求/完成即遗忘），**设计与开发分离**（规范与编码解耦）。
- 业界依据：五阶段 不是凭空造，是 AWS AI-DLC 的细化。

### 共识 6：Spec-Driven Development

**出处**：Spec-Driven Development 运动（2025 下半年业界博客合集）

**核心论断**：
> AI 编码质量取决于规范的精确度。先把需求/PRD/架构写成"AI 可执行"的规范，再让 AI 写代码。

**对本体系的意义**：
- 设计阶段是核心，spec 必须可被 AI 工具读取执行。
- 五角色中 需求规范师（Spec-Writer） 占主导地位。

### 共识 7：MCP + A2A 双层协议栈

**出处**：Anthropic MCP（Model Context Protocol）+ Google A2A（Agent-to-Agent）

**核心论断**：
> AI 工具间通信通过 MCP（工具上下文）+ A2A（智能体协作）双层协议栈，业界已成标准。

**对本体系的意义**：
- 体系工具中立——任何支持 MCP/A2A 的工具都可接入。
- 适配层 [05-适配层/](../05-适配层/) 是协议落地点。

### 共识 8：五角色趋势

**出处**：2025-2026 业界博客 + Anthropic 工程实践

**核心论断**：
> AI 时代软件项目角色收敛到五类：需求规范师（Spec-Writer） / 构建师（Builder） / 审查师（Reviewer） / 交付师（Shipper） / 统筹师（Keeper）。传统六工种（售前/产品/研发/测试/交付/PM）按职责重组。

**对本体系的意义**：
- 体系按五角色组织 Playbook（详见 [03-执行层/01-工种Playbook/](../03-执行层/01-工种Playbook/)）。
- 角色与工具解耦：1 角色可由多 AI 工具/人承担。
