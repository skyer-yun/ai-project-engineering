## 一、核心理念与目标

### 1.1 时代变革

| 维度 | 传统模式 | AI时代模式 |
|------|----------|-----------|
| 人的核心工作 | 写实现（HOW） | 定义意图（WHAT & WHY） |
| AI核心工作 | 无 | 生成实现（HOW） |
| 人对AI产出 | 无 | 验证 & 校准（VERIFY） |
| 文档作用 | 给人看 | 给人看 + 给AI当上下文 |
| 知识传递 | 人→人 | 人→AI→人，人↔AI循环 |
| 质量保障 | 过程中控制 | 意图定义（前置）+ 输出校验（后置） |

### 1.2 体系目标

- 定义人机协作边界：明确哪些工作AI做、哪些必须人做
- 统一输入输出标准：每个工作节点有明确的输入输出格式
- 建立协作工作流：人与人、人与AI、跨角色协作的标准流程
- 沉淀知识资产：可复用的提示词、模板、规范
- 保障质量底线：AI输出有校验、有门禁、有回滚

### 1.3 适用对象

| 角色 | 主要关注章节 |
|------|-------------|
| 项目经理 | 全文、协作流程、质量管理 |
| 产品经理 | 需求阶段节点、提示词规范 |
| 设计师 | 设计阶段节点、设计提示词 |
| 开发工程师 | 开发阶段节点、代码提示词 |
| 测试工程师 | 测试阶段节点、测试提示词 |
| 运维工程师 | 上线阶段节点、运维提示词 |
| 技术负责人 | 架构设计、AI参与度决策 |

## 二、全生命周期工作节点

### 2.1 工作节点全景图

```
阶段一：需求              阶段二：设计              阶段三：开发
┌────────────────┐      ┌────────────────┐      ┌────────────────┐
│ N1  需求调研    │─────→│ N4  架构设计    │─────→│ N7  编码实现    │
│ N2  需求分析    │─────→│ N5  详细设计    │─────→│ N8  代码审查    │
│ N3  PRD产出     │─────→│ N6  UI/UX设计   │─────→│ N9  单元测试    │
└────────────────┘      └────────────────┘      └────────────────┘
        ↓                       ↓                       ↓
阶段四：测试              阶段五：上线              阶段六：运营
┌────────────────┐      ┌────────────────┐      ┌────────────────┐
│ N10 集成测试    │─────→│ N13 部署发布    │─────→│ N15 运维监控    │
│ N11 系统测试    │─────→│ N14 验收交付    │─────→│ N16 迭代优化    │
│ N12 验收测试    │      └────────────────┘      └────────────────┘
└────────────────┘
```

### 2.2 节点标准定义结构

每个工作节点必须定义以下7个要素：

```
┌─────────────────────────────────────────────────────────┐
│  工作节点 N{x}：{名称}                                    │
│                                                           │
│  输入    ：前序节点交付物 + 格式要求 + 质量要求             │
│  处理-人 ：人工必须执行的工作 + 决策点                     │
│  处理-AI ：AI执行的工作 + 参与度                           │
│  输出    ：本节点交付物 + 格式要求 + 验收标准               │
│  AI参与度：L1-L5分级                                      │
│  质量门禁：通过标准 + 校验方法 + 责任人                     │
│  交接标准：下游节点接收条件 + 签字确认要求                   │
└─────────────────────────────────────────────────────────┘
```

### 2.3 阶段一：需求（N1-N3）

#### N1 需求调研

| 要素 | 定义 |
|------|------|
| 输入 | 客户原始资料（文档/访谈录音/会议纪要/竞品资料） |
| 处理-人 | 客户访谈、业务观察、竞品分析、行业调研、需求确认 |
| 处理-AI | 访谈录音→文字转录、竞品资料结构化提取、调研问卷生成、调研报告初稿生成 |
| 输出 | 需求调研报告（Markdown）、业务流程草图（Mermaid）、待确认问题清单 |
| AI参与度 | L2（AI生成80%，人审核确认） |
| 质量门禁 | 覆盖全部业务场景、客户签字确认、待确认问题清零 |
| 交接标准 | 调研报告经客户确认签字 |

#### N2 需求分析

| 要素 | 定义 |
|------|------|
| 输入 | N1需求调研报告（已确认） |
| 处理-人 | 需求拆解、优先级排序、依赖关系梳理、可行性评估、评审决策 |
| 处理-AI | 功能清单生成、依赖关系分析、优先级建议、需求完整性检查 |
| 输出 | 功能清单（含编号/优先级/依赖/复杂度）、需求问题清单（待确认项） |
| AI参与度 | L3（AI辅助30%，人主导决策） |
| 质量门禁 | 功能覆盖调研报告100%、优先级经团队评审、依赖关系明确 |
| 交接标准 | 功能清单评审通过、问题清单清零 |

#### N3 PRD产出

| 要素 | 定义 |
|------|------|
| 输入 | N1调研报告 + N2功能清单（评审通过） |
| 处理-人 | PRD结构审核、业务逻辑校验、场景完整性确认、评审通过 |
| 处理-AI | PRD初稿生成（按模板填充）、补充数据流/状态机/异常处理、格式校验 |
| 输出 | PRD文档（Markdown，按PRD规范模板12章节） |
| AI参与度 | L2（AI生成80%初稿，人审核修改） |
| 质量门禁 | 12项检查点全部通过（见PRD规范） |
| 交接标准 | 三方评审通过签字（建设方/运营方/实施方） |

### 2.4 阶段二：设计（N4-N6）

#### N4 架构设计

| 要素 | 定义 |
|------|------|
| 输入 | PRD（评审通过）+ 技术约束条件 + 现有系统架构（如有） |
| 处理-人 | 技术选型决策、架构方案评审、微服务拆分决策、风险评审 |
| 处理-AI | 架构方案建议、技术选型对比表、容量预估计算、架构图生成 |
| 输出 | 系统概要设计文档（Markdown，10章节） |
| AI参与度 | L3（AI辅助30%，架构师主导决策） |
| 质量门禁 | 6项检查点通过、架构评审会通过、技术委员会签字 |
| 交接标准 | 架构评审签字确认 |

#### N5 详细设计

| 要素 | 定义 |
|------|------|
| 输入 | 概要设计（评审通过）+ PRD功能模块 |
| 处理-人 | 核心类设计审核、API接口确认、数据库设计确认、技术难点攻关 |
| 处理-AI | 类图生成、API定义生成、DDL生成、状态机图生成、缓存策略建议、消息队列设计 |
| 输出 | 详细设计文档（类图/API定义/DDL/状态机/缓存/消息队列） |
| AI参与度 | L2（AI生成70%，人审核校准） |
| 质量门禁 | 接口定义与PRD一致、DDL可执行、状态机覆盖完整 |
| 交接标准 | 技术负责人审核签字 |

#### N6 UI/UX设计

| 要素 | 定义 |
|------|------|
| 输入 | PRD + 原型需求 + 品牌规范（如有） |
| 处理-人 | 品牌调性把控、设计方案评审、用户体验决策、最终确认签字 |
| 处理-AI | 原型结构生成、UI设计稿生成、Design Tokens生成、组件规范生成、交互规则生成 |
| 输出 | UI/UX设计规范 + 设计稿 + Design Tokens（YAML） + 组件规范 |
| AI参与度 | L2（AI生成70%，人审核校准+品牌把控） |
| 质量门禁 | 5项检查点通过、设计评审通过、前端确认可还原 |
| 交接标准 | 设计稿交付、Tokens文件交付、前端确认签字 |

### 2.5 阶段三：开发（N7-N9）

#### N7 编码实现

| 要素 | 定义 |
|------|------|
| 输入 | 详细设计 + 代码工程化规范 + UI设计稿 + Design Tokens |
| 处理-人 | 核心逻辑实现、AI输出审核、业务规则校验、边界条件补充 |
| 处理-AI | 代码生成（Controller/Service/Mapper/前端页面）、注释生成、基础单元测试生成 |
| 输出 | 功能代码 + 单元测试代码 + 代码说明文档 |
| AI参与度 | L1（AI生成100%，人抽检10%+核心逻辑全检） |
| 质量门禁 | 编译通过 + 规范扫描通过 + 单元测试通过 |
| 交接标准 | 提交Merge Request，关联Issue |

#### N8 代码审查

| 要素 | 定义 |
|------|------|
| 输入 | N7提交的Merge Request |
| 处理-人 | 核心逻辑审核、安全审查、性能审查、架构符合性审查 |
| 处理-AI | 规范扫描、安全扫描、性能建议、代码优化建议、重复代码检测 |
| 输出 | 审查意见（通过/修改建议/拒绝）+ 审查报告 |
| AI参与度 | L1（AI扫描100%，人审核关键项） |
| 质量门禁 | 8项审查清单通过、无阻断问题 |
| 交接标准 | 审查通过后合并代码 |

#### N9 单元测试

| 要素 | 定义 |
|------|------|
| 输入 | N7功能代码 + 详细设计中的业务规则 |
| 处理-人 | 测试策略确认、边界条件补充、覆盖率审核 |
| 处理-AI | 测试用例生成、Mock数据生成、断言生成、覆盖率报告生成 |
| 输出 | 单元测试代码 + 覆盖率报告 |
| AI参与度 | L1（AI生成100%，人审核边界条件） |
| 质量门禁 | 覆盖率>=80%、通过率100% |
| 交接标准 | 覆盖率报告达标，提交测试环境 |

### 2.6 阶段四：测试（N10-N12）

#### N10 集成测试

| 要素 | 定义 |
|------|------|
| 输入 | N7-N9开发完成的模块 + API接口文档 + 测试环境 |
| 处理-人 | 接口联调、跨模块流程验证、问题定位修复协调 |
| 处理-AI | 接口测试脚本生成、自动化测试框架搭建、测试报告生成 |
| 输出 | 集成测试报告 + 自动化测试脚本 |
| AI参与度 | L1（AI生成测试脚本100%，人执行验证） |
| 质量门禁 | 接口通过率>=99%、跨模块流程跑通 |
| 交接标准 | 全模块联通，进入系统测试 |

#### N11 系统测试

| 要素 | 定义 |
|------|------|
| 输入 | 集成通过的系统 + 测试方案 + 测试用例 + 验收标准 |
| 处理-人 | 功能测试执行、性能测试执行、安全测试执行、兼容性测试执行、缺陷管理 |
| 处理-AI | 测试用例生成、性能测试脚本、缺陷分析报告、回归测试建议 |
| 输出 | 系统测试报告（功能/性能/安全/兼容性）+ 缺陷清单 |
| AI参与度 | L2（AI生成用例80%，人执行+补充） |
| 质量门禁 | S1/S2缺陷100%关闭、S3缺陷关闭率>=90% |
| 交接标准 | 测试报告确认，进入验收测试 |

#### N12 验收测试

| 要素 | 定义 |
|------|------|
| 输入 | 系统测试通过的系统 + 验收标准 + 验收用例 |
| 处理-人 | 客户验收确认、问题记录、验收签字 |
| 处理-AI | 验收报告生成、问题清单整理、演示材料生成 |
| 输出 | 验收确认书 + 验收报告 |
| AI参与度 | L4（AI辅助20%，客户主导） |
| 质量门禁 | 客户签字确认 |
| 交接标准 | 验收通过，进入部署阶段 |

### 2.7 阶段五：上线（N13-N14）

#### N13 部署发布

| 要素 | 定义 |
|------|------|
| 输入 | 验收通过的代码 + 部署手册 + 环境配置 + 变更审批单 |
| 处理-人 | 部署方案审批、灰度发布决策、上线确认、回滚决策 |
| 处理-AI | Dockerfile生成、K8s配置生成、CI/CD脚本生成、监控告警配置 |
| 输出 | 生产环境运行系统 + 部署记录 |
| AI参与度 | L3（AI生成配置30%，人审批执行） |
| 质量门禁 | 冒烟测试通过、监控无异常、回滚预案就绪 |
| 交接标准 | 系统稳定运行，进入交付阶段 |

#### N14 验收交付

| 要素 | 定义 |
|------|------|
| 输入 | 上线系统 + 全部交付物清单 |
| 处理-人 | 交付物审核、培训执行、文档归档、客户签收 |
| 处理-AI | 操作手册生成、培训材料生成、API文档整理、交付清单校验 |
| 输出 | 完整交付包（文档+代码+培训材料）+ 交付确认书 |
| AI参与度 | L2（AI生成80%，人审核确认） |
| 质量门禁 | 20项交付物清单全齐 |
| 交接标准 | 客户签收确认，项目结项 |

### 2.8 阶段六：运营（N15-N16）

#### N15 运维监控

| 要素 | 定义 |
|------|------|
| 输入 | 生产系统 + 监控配置 + SLA要求 |
| 处理-人 | 告警处理、故障排查、容量规划、安全运维 |
| 处理-AI | 日志分析、异常检测、根因分析建议、容量预测 |
| 输出 | 运维报告 + 故障处理记录 |
| AI参与度 | L2（AI分析80%，人决策执行） |
| 质量门禁 | SLA达标、无P0/P1故障 |
| 交接标准 | 系统稳定运行 |

#### N16 迭代优化

| 要素 | 定义 |
|------|------|
| 输入 | 运维数据 + 用户反馈 + 新需求 |
| 处理-人 | 需求评估、迭代规划、优先级决策 |
| 处理-AI | 数据分析报告、优化建议、迭代计划草案 |
| 输出 | 迭代计划 + 优化方案 |
| AI参与度 | L3（AI辅助30%，人主导决策） |
| 质量门禁 | 评审通过 |
| 交接标准 | 进入下一迭代周期 |

## 三、AI参与度分级标准

### 3.1 五级定义

| 等级 | AI参与度 | 人工审核 | 适用场景 | 典型节点 |
|------|---------|---------|---------|---------|
| L1 全面生成 | AI完成100% | 抽检10%+核心全检 | 代码生成、测试生成 | N7编码、N8审查、N9测试 |
| L2 辅助生成 | AI完成70-80% | 全量审核 | 文档编写、用例生成、设计生成 | N1调研、N3PRD、N5详细设计、N6设计 |
| L3 辅助建议 | AI完成30% | 全量审核+决策 | 架构设计、技术决策、部署配置 | N2分析、N4架构、N13部署 |
| L4 轻微辅助 | AI完成20% | 全量确认 | 客户验收、需求确认 | N12验收、客户沟通 |
| L5 纯人工 | AI完成0% | 人工执行 | 决策审批、签字、合同 | 上线审批、合同签署 |

### 3.3 AI参与度选择原则

| 团队成熟度 | 建议基线 | 说明 |
|-----------|---------|------|
| 初期（0-3个月） | L2-L3起步 | 团队需要适应AI协作，建立审核习惯 |
| 中期（3-6个月） | L1-L2为主 | 流程成熟，可提高AI参与度 |
| 成熟期（6个月+） | L1为主 | AI深度融入，人专注决策和审核 |

## 四、跨角色协作工作流

### 4.1 人与人协作流

```
产品经理 ──PRD──→ 设计师 ──设计稿──→ 前端开发
    │                                    │
    └──PRD──→ 后端开发 ──API──→ 前端开发 ←┘
                    │
                    └──接口文档──→ 测试工程师
```

### 4.2 人与AI协作流

```
人（定义意图）──Prompt──→ AI（生成实现）──初稿──→ 人（审核校准）
      ↑                                              │
      └────────修正Prompt←──反馈──←──不满意──────────┘
                                                       │
                                                   满意↓
                                              提交/合入/发布
```

### 4.3 三方协作流（人-AI-人）

```
角色A ──上下文+意图──→ AI ──生成物──→ 角色B
  │                       ↑↓              │
  └──定义输入标准          校验            └──定义输出标准
                          ↑↓
                       质量门禁
```

关键原则：每个交接点必须有明确的输入/输出标准定义。

## 六、关键决策结论

### 6.1 文档格式决策

| 决策项 | 结论 |
|--------|------|
| 主要格式 | Markdown为主 |
| 正式交付 | 导出Word/PDF签字归档 |
| 理由 | AI可直接消费Markdown，正式交付需要Word/PDF |

### 6.2 Prompt管理决策

| 决策项 | 结论 |
|--------|------|
| 管理方式 | 集中在一份文档 |
| 组织方式 | 按阶段/角色分章节 |
| 理由 | 便于查找、维护、版本管理 |

### 6.3 AI参与度基线决策

| 决策项 | 结论 |
|--------|------|
| 起步基线 | L2起步 |
| 提升路径 | 团队成熟后逐步向L1提升 |
| 理由 | 团队需要适应期，L2（AI生成70%）是安全起点 |

### 6.4 知识库载体决策

| 决策项 | 结论 |
|--------|------|
| 载体方案 | 双轨制 |
| 飞书知识空间 | 给人看（协作友好） |
| Git仓库 | 给AI消费（结构化、可编程） |
| 同步机制 | 定期同步，保持一致 |

### 6.5 文档颗粒度决策

| 决策项 | 结论 |
|--------|------|
| 模板颗粒度 | 详细 |
| 使用方式 | 使用时按需裁剪 |
| 理由 | 宁可详细，太粗会导致AI输出不稳定 |

## 七、文档格式规范

### 7.1 格式选择建议

| 格式 | 适用场景 | AI友好度 | 人友好度 |
|------|---------|---------|---------|
| Markdown | 技术文档、规范、PRD、提示词 | 5/5 | 5/5 |
| YAML | 配置文件、数据结构、Design Tokens | 5/5 | 3/5 |
| JSON | API定义、数据交换 | 5/5 | 3/5 |
| Mermaid | 流程图、时序图、状态图 | 5/5 | 4/5 |
| OpenAPI/Swagger | 接口文档 | 5/5 | 3/5 |
| Word/PDF | 正式交付、签字归档 | 2/5 | 5/5 |

### 7.2 推荐组合

| 场景 | 推荐格式 |
|------|---------|
| 内部协作 | Markdown + Mermaid |
| 正式交付 | 导出Word/PDF |
| AI输入 | Markdown + YAML + JSON |
| 设计交付 | Figma + YAML(Design Tokens) |
| 接口文档 | OpenAPI + Markdown |
