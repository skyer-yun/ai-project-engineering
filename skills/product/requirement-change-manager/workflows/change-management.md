# 变更管理工作流

## 工作流概览

```
变更申请(1) → 影响分析(2) → 变更评审(3) → 变更执行(4) → 变更验证(5) → 变更关闭(6)
```

---

## Step 1: 变更申请

### 目标
收集并登记变更请求，创建变更申请单。

### 输入
- 变更描述（必填）
- 变更原因（必填）
- 变更发起人（必填）
- 期望完成时间（选填）
- 优先级（选填，默认中）
- 关联需求编号（选填）

### 处理步骤
1. 接收变更描述，提取关键信息
2. 为变更分配唯一编号（格式：CR-YYYYMMDD-NNN）
3. 确认变更分类：
   - 功能新增（Feature）
   - 功能修改（Modification）
   - 功能删除（Removal）
   - 需求澄清（Clarification）
4. 记录当前需求基线版本
5. 创建变更申请单

### 输出
- 变更申请单（含编号、分类、状态=待分析）

### 变更申请单模板
```markdown
## 变更申请单

| 字段 | 内容 |
|------|------|
| 编号 | CR-YYYYMMDD-NNN |
| 标题 | {变更标题} |
| 分类 | 功能新增/功能修改/功能删除/需求澄清 |
| 发起人 | {发起人} |
| 申请日期 | {日期} |
| 期望完成 | {日期} |
| 优先级 | 高/中/低 |
| 状态 | 待分析 |

### 变更描述
{详细描述变更内容}

### 变更原因
{为什么要变更}

### 当前基线
- PRD版本：vX.X
- 设计版本：vX.X
- 代码分支：{branch}
```

---

## Step 2: 影响分析

### 目标
从 6 个维度量化评估变更影响，输出影响分析报告。

### 输入
- 变更申请单
- 当前需求基线（PRD、设计、代码、测试）
- 项目排期表

### 处理步骤
1. **功能影响分析**
   - 识别受影响的模块和功能点
   - 评估功能关联关系变化
   - 标记新增/修改/删除的功能点

2. **技术影响分析**
   - 评估技术架构是否需要调整
   - 识别需要修改的接口和数据结构
   - 分析技术债务影响

3. **测试影响分析**
   - 识别需要新增的测试用例
   - 识别需要修改的现有用例
   - 评估回归测试范围

4. **排期影响分析**
   - 估算各环节新增工作量（人天）
   - 计算对关键路径的影响
   - 评估里程碑偏移

5. **资源影响分析**
   - 评估是否需要新增人员
   - 识别跨团队协作需求
   - 分析资源冲突

6. **文档影响分析**
   - 列出需要更新的文档清单
   - 评估文档更新工作量

### 评分标准
每个维度按 1-5 分评估：

| 分值 | 含义 | 描述 |
|------|------|------|
| 1 | 极低 | 几乎无影响，局部微调 |
| 2 | 低 | 小范围影响，可快速处理 |
| 3 | 中 | 中等影响，需要一定工作量 |
| 4 | 高 | 大范围影响，需要较多工作量 |
| 5 | 极高 | 核心架构/功能变化，影响全局 |

### 权重配置
| 维度 | 权重 | 说明 |
|------|------|------|
| 功能影响 | 0.25 | 核心维度 |
| 技术影响 | 0.20 | 技术复杂度 |
| 测试影响 | 0.15 | 质量保障 |
| 排期影响 | 0.20 | 项目进度 |
| 资源影响 | 0.10 | 人力投入 |
| 文档影响 | 0.10 | 文档维护 |

### 综合评分计算
```
综合评分 = SUM(维度评分 x 维度权重)
最高分 = 5分
风险等级：
  1.0-2.0 = 低风险
  2.1-3.0 = 中风险
  3.1-4.0 = 高风险
  4.1-5.0 = 极高风险
```

### 输出
- 变更影响分析报告（含 6 维度评分 + 综合评分 + 风险等级）

---

## Step 3: 变更评审

### 目标
组织变更评审，形成审批结论。

### 输入
- 变更申请单
- 变更影响分析报告

### 处理步骤
1. 根据风险等级确定审批流程：
   - L1（低风险）：项目经理审批
   - L2（中风险）：项目经理 + 技术负责人审批
   - L3（高风险）：变更控制委员会(CCB)评审
   - L4（极高风险）：CCB + 高层审批
2. 准备评审材料：
   - 变更概述（1分钟可读完）
   - 影响分析摘要
   - 建议方案
   - 风险缓解措施
3. 记录评审结论：
   - 批准
   - 有条件批准（附带条件列表）
   - 驳回（附原因）
   - 延期（附重新评审时间）

### 输出
- 评审记录（含结论、审批人、日期、附加条件）

---

## Step 4: 变更执行

### 目标
按评审结论执行变更，同步更新所有关联产物。

### 输入
- 评审通过的变更申请
- 变更影响分析报告
- 需要更新的产物清单

### 处理步骤
1. 制定变更执行计划：
   - 按优先级排序更新任务
   - 确定执行顺序和依赖关系
   - 分配责任人

2. 执行产物更新（按顺序）：
   - PRD 文档更新（调用 write-a-prd）
   - 设计稿/原型更新
   - 接口文档更新
   - 测试用例更新
   - 代码变更
   - 用户文档更新

3. 每完成一项更新，记录执行状态

### 产物更新检查清单
```markdown
### 变更执行检查清单
- [ ] PRD 文档已更新
- [ ] 设计稿/原型已更新
- [ ] 接口文档已更新
- [ ] 数据库设计已更新（如涉及）
- [ ] 测试用例已更新
- [ ] 代码已修改
- [ ] 用户文档已更新
- [ ] 发布说明已更新
```

### 输出
- 更新后的各产物
- 变更执行记录

---

## Step 5: 变更验证

### 目标
验证变更是否正确执行，关联产物是否一致。

### 输入
- 变更执行记录
- 更新后的各产物

### 处理步骤
1. **一致性检查**
   - PRD 描述与代码实现是否一致
   - 设计稿与实际界面是否一致
   - 测试用例是否覆盖变更内容
   - 接口文档与实际接口是否一致

2. **完整性检查**
   - 影响分析中识别的所有模块是否都已更新
   - 关联产物是否全部同步
   - 文档版本号是否已更新

3. **质量检查**
   - 变更是否引入新的问题
   - 回归测试是否通过
   - 性能是否受影响

### 输出
- 变更验证报告（通过/不通过 + 问题清单）

---

## Step 6: 变更关闭

### 目标
完成变更归档，更新基线版本。

### 输入
- 变更验证通过的报告

### 处理步骤
1. 更新需求基线版本号
2. 标记变更状态为"已关闭"
3. 归档变更全流程文档：
   - 变更申请单
   - 影响分析报告
   - 评审记录
   - 执行记录
   - 验证报告
4. 通知相关干系人变更已完成
5. 更新项目 memory 记录

### 输出
- 变更归档记录
- 更新后的基线版本

### 归档模板
```markdown
## 变更归档记录

| 字段 | 内容 |
|------|------|
| 变更编号 | CR-YYYYMMDD-NNN |
| 变更标题 | {标题} |
| 变更分类 | {分类} |
| 综合评分 | {X.X}/5.0 |
| 风险等级 | {等级} |
| 审批人 | {审批人} |
| 执行人 | {执行人} |
| 创建日期 | {日期} |
| 关闭日期 | {日期} |
| 基线版本 | v{X.X} → v{X.X+1} |

### 变更摘要
{一句话总结变更内容}

### 影响范围
- 模块：{受影响模块列表}
- 产物：{更新产物列表}
- 工作量：{总人天数}
```

---

## 流程状态流转

```
待分析 ──→ 分析中 ──→ 待评审 ──→ 评审中 ──→ 待执行 ──→ 执行中 ──→ 待验证 ──→ 验证中 ──→ 已关闭
  │                      │           │                      │           │
  └── 驳回 ←─────────────┘           └── 驳回 ←─────────────┘           └── 不通过 → 回到执行中
```
