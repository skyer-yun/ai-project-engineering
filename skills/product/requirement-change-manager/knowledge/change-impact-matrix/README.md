# 变更影响评估矩阵

## 概述

变更影响评估矩阵是需求变更管理的核心工具，用于从 6 个维度量化评估需求变更对项目的影响范围和程度。通过标准化的评分体系和权重计算，为变更审批提供客观、可量化的决策依据。

---

## 一、评估维度

### 1. 功能影响（权重：0.25）

**评估目标**：衡量变更对产品功能范围的影响程度。

| 评分 | 等级 | 判定标准 |
|------|------|----------|
| 1 | 极低 | 仅影响单一页面的非核心展示元素（如文案、图标） |
| 2 | 低 | 影响单一模块内的局部功能，不影响其他模块 |
| 3 | 中 | 影响一个完整模块，或涉及 2-3 个关联模块的部分功能 |
| 4 | 高 | 影响核心业务流程，涉及 4 个以上模块的功能调整 |
| 5 | 极高 | 变更核心业务模型或数据结构，影响系统全局功能 |

**评估要点**：
- 受影响的模块数量和层级
- 核心业务流程是否涉及
- 数据模型是否需要变更
- 前后端是否都需要修改
- 是否引入新的功能实体

### 2. 技术影响（权重：0.20）

**评估目标**：衡量变更对技术架构和实现复杂度的影响。

| 评分 | 等级 | 判定标准 |
|------|------|----------|
| 1 | 极低 | 纯前端展示调整，无需后端配合 |
| 2 | 低 | 简单的接口参数调整或新增非核心接口 |
| 3 | 中 | 需要新增或修改 1-3 个接口，数据表结构小范围调整 |
| 4 | 高 | 需要引入新的技术组件或中间件，接口变更涉及 5 个以上 |
| 5 | 极高 | 需要调整系统架构，涉及数据库重构或核心技术组件替换 |

**评估要点**：
- 后端接口新增/修改数量
- 数据库表结构变更范围
- 是否引入新技术/组件/依赖
- 技术方案复杂度
- 对现有技术架构的影响

### 3. 测试影响（权重：0.15）

**评估目标**：衡量变更对测试工作量和测试范围的影响。

| 评分 | 等级 | 判定标准 |
|------|------|----------|
| 1 | 极低 | 无需新增测试用例，仅需验证修改点本身 |
| 2 | 低 | 新增 1-5 个测试用例，回归测试范围小 |
| 3 | 中 | 新增 6-20 个测试用例，需要中等范围的回归测试 |
| 4 | 高 | 新增 20+ 测试用例，需要大范围回归测试，涉及多环境验证 |
| 5 | 极高 | 需要全量回归测试，涉及性能/安全/兼容性等多维度测试 |

**评估要点**：
- 新增测试用例数量估算
- 回归测试范围（模块级/系统级）
- 是否涉及非功能测试（性能、安全、兼容性）
- 测试环境准备需求
- 测试数据准备需求

### 4. 排期影响（权重：0.20）

**评估目标**：衡量变更对项目排期和里程碑的影响。

| 评分 | 等级 | 判定标准 |
|------|------|----------|
| 1 | 极低 | 0.5 人天以内，不影响当前迭代排期 |
| 2 | 低 | 0.5-2 人天，在当前迭代缓冲期内可消化 |
| 3 | 中 | 2-5 人天，需要调整迭代内任务优先级 |
| 4 | 高 | 5-10 人天，影响迭代交付时间，需要协商排期 |
| 5 | 极高 | 10+ 人天，影响项目里程碑，需要重新规划迭代 |

**评估要点**：
- 各环节新增工作量估算（开发/测试/文档）
- 是否在迭代缓冲期内
- 对关键路径的影响
- 里程碑偏移天数
- 是否需要插单或替换其他需求

### 5. 资源影响（权重：0.10）

**评估目标**：衡量变更对人力资源和团队协作的影响。

| 评分 | 等级 | 判定标准 |
|------|------|----------|
| 1 | 极低 | 单人即可完成，无跨团队协作需求 |
| 2 | 低 | 涉及 1 个团队内的 2-3 人协作 |
| 3 | 中 | 需要 2 个团队协作，涉及 3-5 人 |
| 4 | 高 | 需要 3 个以上团队协作，涉及 5 人以上 |
| 5 | 极高 | 需要跨部门协调，可能需要借调外部资源 |

**评估要点**：
- 涉及团队数量
- 涉及人员数量
- 是否需要跨团队协调
- 是否存在资源冲突
- 是否需要外部资源支持

### 6. 文档影响（权重：0.10）

**评估目标**：衡量变更对文档更新工作量的影响。

| 评分 | 等级 | 判定标准 |
|------|------|----------|
| 1 | 极低 | 无需更新文档，或仅更新 1 处简单描述 |
| 2 | 低 | 需要更新 1-2 个文档的局部章节 |
| 3 | 中 | 需要更新 3-5 个文档，涉及多处修改 |
| 4 | 高 | 需要更新 5 个以上文档，包含核心文档重写 |
| 5 | 极高 | 需要全面更新所有项目文档，包括培训材料 |

**评估要点**：
- 需要更新的文档类型和数量
- PRD/设计文档/接口文档/用户手册/运维文档
- 文档更新工作量
- 是否需要更新培训材料

## 二、综合评分计算

### 计算公式
```
综合评分 = (功能影响 x 0.25) + (技术影响 x 0.20) + (测试影响 x 0.15)
         + (排期影响 x 0.20) + (资源影响 x 0.10) + (文档影响 x 0.10)
```

### 评分范围
- 最低分：1.0（所有维度均为 1）
- 最高分：5.0（所有维度均为 5）

### 风险等级判定

| 综合评分 | 风险等级 | 标识 | 审批层级 | 典型场景 |
|----------|----------|------|----------|----------|
| 1.0 - 2.0 | 低 | L1 | 项目经理 | UI文案调整、配置项修改 |
| 2.1 - 3.0 | 中 | L2 | PM + 技术负责人 | 新增非核心页面、接口扩展 |
| 3.1 - 4.0 | 高 | L3 | 变更控制委员会 | 核心流程变更、权限体系调整 |
| 4.1 - 5.0 | 极高 | L4 | CCB + 高层审批 | 业务模型重构、架构级变更 |

## 四、快速评估速查表

当时间紧急时，可使用以下快速判定规则：

| 变更特征 | 直接判定 |
|----------|----------|
| 仅修改文案/颜色/图标 | L1，跳过详细分析 |
| 新增一个展示页面 | L1-L2，快速评估 |
| 新增一个带交互的页面 | L2，标准分析 |
| 修改已有接口参数 | L2-L3，重点关注兼容性 |
| 新增核心业务流程 | L3，全面分析 |
| 修改数据库表结构 | L3-L4，全面分析 + 兼容方案 |
| 更换核心技术组件 | L4，全面分析 + 架构评审 |
| 业务模型重构 | L4，全面分析 + 专家评审 |

## 五、使用指南

### 何时使用
1. 每次需求变更申请时
2. 项目迭代规划阶段评估新需求
3. 变更评审会议前准备材料
4. 风险回顾时重新评估已执行变更

### 注意事项
1. 评分应基于客观事实，避免主观偏好
2. 存在疑问时，宁可评高不评低（保守原则）
3. 同一变更的评分应由至少 2 人确认
4. 评估结果需要记录评分依据，便于追溯
5. 定期回顾评分准确性，校准评分标准
