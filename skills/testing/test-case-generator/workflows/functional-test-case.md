# Functional Test Case Workflow

> 从 PRD/详细设计生成功能测试用例

## 概览

| 项目 | 说明 |
|------|------|
| 输入 | PRD（Part 7 功能模块详细说明）/ 详细设计文档 / 验收标准 |
| 输出 | 测试用例集（Markdown 表格 / Excel）+ 需求追溯矩阵 |
| 设计方法 | 6 种：等价类/边界值/场景法/判定表/正交实验/状态迁移 |

## Stage 2: 选择设计方法

### 方法选择决策树

```
功能点特征分析 → 匹配最优设计方法：

IF 输入为数值/字符串/日期类型
  → 等价类划分 + 边界值分析（组合使用）

IF 涉及多步骤业务流程
  → 场景法

IF 包含复杂条件判断（IF-THEN-ELSE）
  → 判定表

IF 多个因素组合影响结果（且因素 >= 3）
  → 正交实验法

IF 涉及状态流转（待审核→审核中→通过/驳回）
  → 状态迁移测试

默认组合：
  大多数功能点 → 等价类 + 边界值（基础方法）
```

### 6 种设计方法详解

#### 方法 1: 等价类划分

```
原理：将输入域划分为有效等价类和无效等价类，每类取一个代表值

示例（密码输入）：
  有效等价类：6-20位字母数字组合
  无效等价类：
    - 少于6位
    - 超过20位
    - 纯数字
    - 包含特殊字符（如不允许）
    - 为空

用例数 = 有效等价类数 + 无效等价类数（每条用例只覆盖一个无效等价类）
```

#### 方法 2: 边界值分析

```
原理：在等价类边界及其附近取值测试

示例（年龄输入 18-65）：
  边界值：17, 18, 19, 64, 65, 66
  典型值：30（中间值）

适用：数值范围、字符串长度、日期范围、数组索引
```

#### 方法 3: 场景法

```
原理：从业务流程出发，设计端到端测试场景

场景类型：
  - 基本流程（Happy Path）：正常操作路径
  - 替代流程：合法但非主要的操作路径
  - 异常流程：非法操作或错误条件

示例（下单流程）：
  场景1：正常下单 → 选择商品 → 填地址 → 支付 → 成功
  场景2：库存不足 → 提示缺货
  场景3：支付超时 → 订单保留 → 重新支付
  场景4：优惠券过期 → 提示不可用 → 按原价支付
```

#### 方法 4: 判定表

```
原理：列出所有条件组合，确保每种组合都有测试

适用：多条件组合判断（如折扣计算）

示例（订单折扣）：
  | 条件1：VIP用户 | Y | Y | Y | Y | N | N | N | N |
  | 条件2：满200元 | Y | Y | N | N | Y | Y | N | N |
  | 条件3：节假日  | Y | N | Y | N | Y | N | Y | N |
  | 结果：折扣    | 8折| 85 |85 | 9折| 9折| 95 | 95| 无 |

用例数 = 条件组合数（化简后）
```

#### 方法 5: 正交实验法

```
原理：使用正交表从全面组合中选取代表性子集

适用：多因素、多水平，全面组合数量爆炸

示例（浏览器兼容性测试）：
  因素：浏览器(Chrome/Firefox/Safari) × 系统(Win/Mac) × 分辨率(1920/1366/768)
  全面组合：3×2×3 = 18
  正交表缩减：9 组即可覆盖所有因素对

正交表：L9(3^4) 或使用 Pairwise 工具
```

#### 方法 6: 状态迁移测试

```
原理：基于状态机模型，测试所有状态转换

示例（订单状态）：
  状态：待支付 → 已支付 → 待发货 → 已发货 → 已完成
        ↘ 已取消        ↘ 退款中 → 已退款

  测试转换：
    待支付 → 已支付（正向）
    待支付 → 已取消（正向）
    已支付 → 待发货（正向）
    已支付 → 退款中（正向）
    已完成 → 已支付（非法转换，应拒绝）
    已取消 → 待支付（非法转换，应拒绝）
```

## Stage 3: 生成测试用例

### 用例格式模板

```markdown
| 用例ID | 模块 | 用例标题 | 前置条件 | 操作步骤 | 预期结果 | 优先级 | 设计方法 | 需求追溯 |
|--------|------|---------|---------|---------|---------|--------|---------|---------|
| TC-F01-001 | 用户管理 | 正确账号密码登录 | 用户已注册 | 1.输入正确账号 2.输入正确密码 3.点击登录 | 登录成功，跳转首页 | P0 | 等价类 | PRD-F01 |
| TC-F01-002 | 用户管理 | 密码为空登录 | 用户已注册 | 1.输入正确账号 2.密码留空 3.点击登录 | 提示"请输入密码" | P1 | 等价类 | PRD-F01 |
```

### 用例编号规则

```
TC-{功能编号}-{3位序号}

示例：
  TC-F01-001  ~ TC-F01-050  （用户管理-登录）
  TC-F02-001  ~ TC-F02-030  （用户管理-注册）
```

### 优先级分配

```
P0（阻塞性）：核心流程正向 + 关键安全项
P1（严重）：  核心流程逆向 + 重要边界值 + 关键异常
P2（一般）：  非核心功能 + 一般边界值 + 一般异常
P3（轻微）：  UI 细节 + 友好性 + 罕见场景
```

## Stage 4: 覆盖率检查

### 4.1 生成追溯矩阵

```markdown
| 需求编号 | 需求描述 | 用例编号 | 覆盖状态 |
|---------|---------|---------|---------|
| PRD-F01-BR01 | 密码长度6-20位 | TC-F01-003, TC-F01-004 | 已覆盖 |
| PRD-F01-BR02 | 连续错误5次锁定 | TC-F01-015 | 未覆盖 → 建议补充 |
```

### 4.2 覆盖率计算

```
需求覆盖率 = 已覆盖需求数 / 总需求数 × 100%
目标：P0/P1 需求 100% 覆盖
```

### 4.3 补充建议

```
IF 存在未覆盖的需求：
  1. 列出未覆盖项
  2. 自动生成补充用例
  3. 更新追溯矩阵
```

## 质量检查清单

完成用例生成后，逐项自检：

- [ ] 每个 P0 功能至少 3 条用例（正向+逆向+边界）
- [ ] 每条验收标准至少 1 条对应用例
- [ ] 所有边界值已覆盖
- [ ] 异常场景数量 >= 正向场景
- [ ] 需求追溯矩阵无"未覆盖"项（P0/P1）
- [ ] 用例可独立执行（前置条件完整）
- [ ] 预期结果可验证（具体/可量化）
