# API Test Case Workflow

> 从接口规范生成 API 测试用例

## 概览

| 项目 | 说明 |
|------|------|
| 输入 | 详细设计中的接口定义 / API 文档 / Swagger/OpenAPI |
| 输出 | API 测试用例集 + 接口测试矩阵 |
| 覆盖维度 | 正常/异常/边界/安全/性能 |

---

## Stage 1: 解析接口规范

### 1.1 提取接口信息

```
从详细设计提取：
  - 接口路径（URL）
  - 请求方法（GET/POST/PUT/DELETE）
  - 请求参数（Path/Query/Body/Header）
  - 参数类型和约束（必填/选填、长度、格式、枚举值）
  - 响应结构（成功/失败）
  - 业务规则（参数间依赖、权限要求）
```

### 1.2 输出：接口清单

```markdown
| 序号 | 接口路径 | 方法 | 说明 | 参数数 | 业务规则 |
|------|---------|------|------|--------|---------|
| API-01 | /api/users/login | POST | 用户登录 | 2 | 密码错误5次锁定 |
| API-02 | /api/users | POST | 用户注册 | 4 | 手机号唯一 |
```

## Stage 2: 逐接口生成用例

### 用例维度

每个接口生成以下 5 类用例：

#### 2.1 正常用例（Happy Path）

```
覆盖：所有必填参数正确填写
预期：返回成功状态码 + 正确数据结构
数量：1-2 条
```

#### 2.2 异常用例

```
覆盖维度：
  - 必填参数缺失（每个必填参数 1 条）
  - 参数类型错误（字符串传数字、数字传字符串）
  - 参数格式错误（邮箱格式、手机号格式）
  - 参数长度超限（超长字符串）
  - 非法值（负数、空格、特殊字符、SQL注入）
预期：返回对应错误码 + 明确错误信息
数量：5-10 条/接口
```

#### 2.3 边界值用例

```
覆盖维度：
  - 数值边界（最小值/最大值/最小-1/最大+1）
  - 字符串边界（空字符串/最小长度/最大长度/超长）
  - 分页边界（page=0/page=1/page=最大页）
预期：边界值正确处理
数量：3-5 条/接口
```

#### 2.4 安全用例

```
覆盖维度：
  - SQL 注入（' OR 1=1 --）
  - XSS 攻击（<script>alert(1)</script>）
  - 未授权访问（不带 Token / 过期 Token）
  - 越权访问（普通用户访问管理员接口）
  - 重复提交
预期：被安全机制拦截
数量：3-5 条/接口
```

#### 2.5 性能用例（可选）

```
覆盖维度：
  - 大数据量请求（批量操作 1000+ 条）
  - 并发请求
  - 超时处理
预期：在性能阈值内正确处理
数量：2-3 条/接口
```

---

### 用例格式

```markdown
| 用例ID | 接口 | 方法 | 用例标题 | 请求参数 | 预期状态码 | 预期响应 | 优先级 |
|--------|------|------|---------|---------|-----------|---------|--------|
| API-01-001 | /api/users/login | POST | 正确密码登录 | {"username":"admin","password":"123456"} | 200 | {"token":"xxx"} | P0 |
| API-01-002 | /api/users/login | POST | 密码为空 | {"username":"admin","password":""} | 400 | {"error":"密码不能为空"} | P1 |
| API-01-003 | /api/users/login | POST | SQL注入 | {"username":"admin' OR 1=1--","password":"x"} | 400 | {"error":"参数非法"} | P0 |
```

## Stage 3: 组合场景用例

### 3.1 接口依赖场景

```
场景设计：多接口串联的业务流程

示例（注册→登录→下单→支付）：
  1. POST /api/users → 注册（获取 userId）
  2. POST /api/users/login → 登录（获取 token）
  3. POST /api/orders → 创建订单（依赖 token + userId）
  4. POST /api/payments → 支付（依赖 orderId）
```

### 3.2 幂等性测试

```
覆盖：重复请求的处理
  - 重复创建（应返回已存在或幂等成功）
  - 重复删除（应返回 404 或幂等成功）
  - 重复更新（应保持一致）
```
