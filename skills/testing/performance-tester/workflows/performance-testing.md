# 性能测试工作流

## 工作流概览

```
Phase 1: 需求分析 → Phase 2: 场景设计 → Phase 3: 脚本生成 → Phase 4: 执行监控 → Phase 5: 分析定位 → Phase 6: 报告输出
```

## Phase 1: 需求分析

### 输入
- 系统架构文档 / 部署拓扑
- 性能需求指标（TPS、响应时间、并发用户数）
- 业务场景描述（核心交易链路、高峰时段特征）
- 测试环境配置信息

### 活动
1. **收集性能指标**
   - 确认目标 TPS（每秒事务数）
   - 确认响应时间要求（P50 / P90 / P99）
   - 确认并发用户数（在线用户 vs 活跃用户）
   - 确认成功率要求（>= 99.9%）

2. **分析系统架构**
   - 梳理部署拓扑（应用服务器/数据库/缓存/消息队列）
   - 识别核心交易链路
   - 确认技术栈和中间件版本
   - 评估系统薄弱环节

3. **确认测试范围**
   - 核心业务场景列表
   - 需要排除的场景
   - 数据敏感度评估

### 输出
- 性能测试需求分析表
- 核心交易链路清单
- 测试范围确认书

### 检查点
- [ ] 所有性能指标已量化
- [ ] 系统架构信息完整
- [ ] 测试环境已确认
- [ ] 数据准备方案已明确

## Phase 2: 场景设计

### 输入
- Phase 1 输出的需求分析结果

### 活动
1. **设计压测场景**
   - 基准测试（Baseline）：单用户/低负载，确认基础性能
   - 负载测试（Load）：逐步加压至目标负载，确认系统在预期负载下的表现
   - 压力测试（Stress）：超过目标负载，找到系统极限/拐点
   - 稳定性测试（Endurance）：目标负载持续运行（通常 2-24 小时），检查内存泄漏等
   - 容量测试（Capacity）：确定系统最大承载能力

2. **确定数据策略**
   - 参数化数据量 = 并发数 x 每用户请求数 x 2（余量）
   - 数据多样性要求（不同地区/金额/类型）
   - 数据清理/重置方案

3. **规划执行顺序**
   - 先基准 → 再负载 → 后压力 → 最后稳定性
   - 每个场景间隔预留系统恢复时间

### 输出
- 压测场景设计文档
- 测试数据准备方案
- 执行计划时间表

### 检查点
- [ ] 场景覆盖所有核心业务
- [ ] 每个场景有明确的预热策略
- [ ] 数据量满足参数化需求
- [ ] 执行顺序合理

## Phase 3: 脚本生成

### 输入
- Phase 2 的场景设计文档
- 接口文档 / API 规格

### 活动
1. **选择压测工具**
   - JMeter：GUI 操作、协议支持广、适合传统 HTTP/API 测试
   - Gatling：高性能、代码化脚本、适合 CI/CD 集成
   - Locust：Python 编写、灵活、适合自定义协议

2. **编写压测脚本**
   - HTTP 请求模板（含请求头/参数化/断言）
   - API 链路脚本（多步骤事务、关联提取）
   - 数据库直连脚本（JDBC 请求模板）

3. **配置监听器**
   - 聚合报告（Aggregate Report）
   - 响应时间图（Response Times Graph）
   - 错误日志收集

4. **数据参数化**
   - CSV 数据文件设置
   - 随机变量/函数助手
   - 正则表达式提取器

### 输出
- 压测脚本文件（.jmx / .scala / .py）
- 参数化数据文件
- 脚本使用说明

### 检查点
- [ ] 脚本覆盖所有场景
- [ ] 参数化数据已就绪
- [ ] 断言规则已配置
- [ ] 脚本可重复执行

## Phase 4: 执行监控

### 输入
- Phase 3 的压测脚本
- 测试环境已就绪

### 活动
1. **环境准备**
   - 确认测试环境配置与生产环境比例关系
   - 部署监控工具（系统监控 + APM）
   - 准备数据重置脚本

2. **执行压测**
   - 预热阶段：低负载运行 3-5 分钟，让 JIT 编译/缓存预热生效
   - 正式施压：按场景设计逐步加压
   - 实时观察：监控各项指标，记录异常

3. **监控采集**
   - 系统层：CPU / 内存 / 磁盘 IO / 网络 IO
   - 应用层：JVM GC / 线程池 / 连接池 / 请求队列
   - 中间件层：Redis 命中率 / MQ 堆积 / Nginx 连接数
   - 数据库层：慢查询 / 连接数 / 锁等待 / 缓冲池命中率

4. **异常处理**
   - 错误率 > 5% → 暂停压测，分析原因
   - 系统崩溃 → 立即停止，保留现场日志
   - 监控数据丢失 → 降级为基本指标采集

### 输出
- 原始测试数据（.jtl / .csv）
- 监控指标快照
- 异常记录日志

### 检查点
- [ ] 预热阶段已完成
- [ ] 监控工具运行正常
- [ ] 数据采集完整
- [ ] 异常已记录

## Phase 5: 分析定位

### 输入
- Phase 4 的测试数据和监控指标

### 活动
1. **数据整理**
   - 提取关键指标（TPS / RT / 错误率 / 并发数）
   - 绘制性能曲线图（TPS vs 并发数 / RT vs 并发数）
   - 统计百分位响应时间（P50 / P90 / P95 / P99）

2. **瓶颈定位**
   - CPU 瓶颈：用户态/内核态占比，热点方法分析
   - 内存瓶颈：GC 频率/时长，内存泄漏检测
   - IO 瓶颈：磁盘读写延迟，网络带宽利用率
   - 数据库瓶颈：慢查询分析，锁等待分析，索引命中率
   - 中间件瓶颈：连接池耗尽，队列堆积，缓存命中率

3. **优化建议**
   - 短期优化：配置调整（线程池/连接池/缓存策略）
   - 中期优化：代码优化/SQL 优化/索引优化
   - 长期优化：架构调整/分库分表/读写分离

### 输出
- 性能分析报告
- 瓶颈定位清单
- 优化建议列表（按优先级排序）

### 检查点
- [ ] 所有关键指标已量化
- [ ] 瓶颈已定位到具体组件
- [ ] 优化建议可落地
- [ ] 给出预期优化效果

## Phase 6: 报告输出

### 输入
- Phase 5 的分析结果

### 活动
1. **编写性能测试报告**
   - 测试概述（目的/范围/环境/工具）
   - 测试结果汇总（TPS/RT/错误率/并发数对比表）
   - 性能曲线图（TPS/RT 随并发变化的趋势图）
   - 瓶颈分析与优化建议
   - 通过/不通过判定

2. **通过判定标准**
   - TPS 达标：实际 TPS >= 目标 TPS x 100%
   - 响应时间达标：P99 RT <= 目标 RT
   - 错误率达标：Error Rate <= 0.1%
   - 资源利用率：CPU <= 80%，内存 <= 80%
   - 稳定性：24h 运行无内存泄漏、TPS 无明显衰减

3. **输出格式**
   - 如果 docx 可用 → 输出 .docx 格式
   - 否则 → 输出 Markdown 格式
   - 附带原始数据文件

### 输出
- 性能测试报告文档
- 原始测试数据
- 性能曲线图

### 检查点
- [ ] 报告包含所有必需章节
- [ ] 通过/不通过判定明确
- [ ] 优化建议有优先级
- [ ] 数据可追溯
