# 自带工具适配指南

> **定位**：把 [01-标准层/](../01-标准层/) + [02-产物层/](../02-产物层/) 的契约落地到**用户自带的任意 AI 工具**（含自研 Agent、WorkBuddy、通义灵码、文心快码、Copilot Chat、Dify、扣子、自研 RAG 等）。
>
> 本体系**不绑定具体工具**——只要你的工具能「读 markdown + 执行 prompt + 生成产物」，就能接入。

---

## 一、工具中立的核心承诺

[01-标准层/](../01-标准层/) + [02-产物层/](../02-产物层/) + [03-执行层/](../03-执行层/) 是纯 markdown：

- **不依赖**任何具体工具的 API
- **不依赖**任何具体工具的运行时
- **不依赖**任何具体工具的 skill/插件格式

体系只约定 4 类契约：

| 契约类型 | 形态 | 自带工具如何遵守 |
|---------|------|----------------|
| **DSBL 阶段定义** | [01-标准层/01](../01-标准层/01-DSBL五阶段定义.md) | 把 5 阶段写进工具的 prompt 模板 |
| **质量门禁 checklist** | [01-标准层/03](../01-标准层/03-质量门禁QG-D至QG-Ship.md) | 把 checklist 作为工具的输出校验规则 |
| **交接契约 YAML** | [01-标准层/04](../01-标准层/04-阶段交接契约Schema.md) | 工具按 schema 生成 / 解析 yaml |
| **HITL 模式** | [03-执行层/03-HITL规则表.md](../03-执行层/03-HITL规则表.md) | L3/L4 节点工具必须暂停等人审 |

## 二、自带工具接入的 3 种形态

### 形态 A：Prompt 模板派（最轻量）

适用：通义灵码、文心快码、Copilot Chat、ChatGPT、Claude.ai 等对话型工具。

**做法**：
1. 把体系 [02-产物层/](../02-产物层/) 的模板复制到工具的自定义 prompt 库
2. 在对话中手动加载模板：「按 [需求分析报告模板] 起草」
3. 人工执行 Loop：Plan（让人审大纲）→ Act（AI 填充）→ Observe（贴 Eval 结果）→ Reflect（人校验）→ Exit（写 handoff）

```bash
./install.sh --adapter custom --templates-only
# 把 02-产物层/ 模板 + 01-标准层/ schema 部署到项目目录
```

### 形态 B：Agent 编排派（中等）

适用：Dify、扣子（Coze）、自研 LangChain Agent、WorkBuddy 等。

**做法**：
1. 按体系 5 角色建 5 个 Agent（或 1 个 Agent 内切角色）
2. 每个 Agent 加载对应 Playbook（[03-执行层/01-角色Playbook/](../03-执行层/01-角色Playbook/)）
3. Agent 间用 handoff.yaml 传递（文件系统或 KV 存储皆可）
4. QG checklist 作为 Agent 的 Output Parser 校验规则

### 形态 C：IDE 集成派（深度）

适用：自研 IDE 插件、自研 Copilot、企业内部开发平台。

**做法**：
1. 体系标准层 + 产物层作为 RAG 知识库
2. 角色路由用语义匹配（embedding + 阈值）或显式按钮
3. HITL-In 节点强制阻塞（UI 弹审批框）
4. handoff.yaml 自动持久化到平台数据库

不管你的工具是什么，至少实现这 5 条：

| # | 必备项 | 验证方法 |
|---|-------|---------|
| 1 | 能读 [02-产物层/](../02-产物层/) 模板 markdown | 让工具「读模板并填字段」 |
| 2 | 能按 [01-标准层/04](../01-标准层/04-阶段交接契约Schema.md) 生成 handoff.yaml | yaml 能通过 `validate-handoff.sh` |

| 5 | 能解析上游 handoff.yaml 加载上下文 | 阶段切换不丢产物 |

## 四、自带工具的 handoff.yaml 模板

不管工具是什么，handoff.yaml 字段固定（schema 见 [01-标准层/04](../01-标准层/04-阶段交接契约Schema.md)）：

```yaml
handoff:
  schema_version: "1.0"
  project: "{项目名}"
  from_stage: D                    # D / S / B / Ship / L
  to_stage: S
  quality_gate: QG-D
  gate_status: passed              # passed / failed / escalated

  output_artifacts:                # 产物清单，路径中立
    - name: "需求分析报告"
      path: "项目文档/{项目}/D-Discover/需求分析报告-v1.0.md"
      version: "v1.0"

  loop_signs:                      # 阶段内 Loop 签名
    - stage: D
      iterations: 3
      final_eval: {requirement_completeness: 0.92}
      reflect_passed: true
      exit_met: true

  handoff:
    to_role: "Builder"             # 五角色之一
    from_role: "Spec-Writer"

  tool_used:                       # 工具中立：记录但 schema 不依赖
    primary: "{你的工具名}"         # 例：WorkBuddy / 自研Agent / 通义灵码
    adapter: "custom"              # 对应 05-适配层/本指南
    notes: "..."

  hitl_signature:
    mode: "In"                     # In / On / Fallback
    irreversibility: L3            # L1-L4
    approved_by:
      - {role: "客户代表", name: "张三", timestamp: "..."}

  risk_flags: []
```

> **关键**：`tool_used.primary` 字段写什么工具名都行——schema 不依赖它，只用于审计。

## 五、5 角色 Playbook 在自带工具中的实现

体系提供 5 份 Playbook（[03-执行层/01-角色Playbook/](../03-执行层/01-角色Playbook/)）：

| Playbook | 自带工具如何用 |
|---------|--------------|
| Spec-Writer-Playbook.md | 复制到工具的「产品/需求 Agent」prompt |
| Builder-Playbook.md | 复制到工具的「研发 Agent」prompt |
| Reviewer-Playbook.md | 作为「质检 Agent」或人工评审 checklist |
| Shipper-Playbook.md | 复制到工具的「测试/部署 Agent」prompt |
| Keeper-Playbook.md | 作为「项目管理 Agent」prompt 或人 keeper 手册 |

**关键**：Playbook 是 markdown，工具不需要支持特殊格式，直接喂给 LLM 即可。

## 六、典型场景示例：自研 Agent 接入

假设你的团队自研了一个 LangChain Agent，要接入本体系：

```python
# 1. Agent 系统提示注入体系契约
SYSTEM_PROMPT = """
你是 {role} 角色（见 ../../03-执行层/01-角色Playbook/{role}-Playbook.md）。
执行 DSBL {stage} 阶段任务。
- 阶段定义见 01-标准层/01-DSBL五阶段定义.md
- Loop 微循环见 01-标准层/02-Loop微循环规范.md
- 质量门禁见 01-标准层/03-质量门禁QG-D至QG-Ship.md

输出前必须：
1. 跑 QG-{stage} checklist
2. 写 handoff.yaml（schema 见 01-标准层/04）
3. L3/L4 节点等用户审批
"""

# 2. 加载上游 handoff.yaml
upstream_handoff = yaml.safe_load(open("handoff.yaml"))
artifacts = upstream_handoff["output_artifacts"]

# 3. 执行 Loop
plan = agent.plan(artifacts)        # Plan
if is_l3_or_l4(stage):             # HITL-In 强制
    human_approve(plan)             # 人审
output = agent.act(plan)            # Act
eval_scores = run_eval(output)      # Observe
agent.reflect(output, eval_scores)  # Reflect
if exit_met(eval_scores):           # Exit
    write_handoff_yaml(...)
```

## 七、常见自带工具适配速查

| 工具类型 | 推荐形态 | 关键注意 |
|---------|---------|---------|
| **通义灵码 / 文心快码** | A（Prompt 模板） | 无原生 Plan Mode，靠人审 git diff |
| **Copilot Chat** | A 或 B | 读 AGENTS.md，但 skill 概念弱 |
| **Dify / 扣子** | B（Agent 编排） | 把 Playbook 喂给 Agent，QG 作为 Output Parser |
| **WorkBuddy / 自研 Copilot** | C（IDE 集成） | RAG 加载标准层，UI 强制 HITL-In |
| **纯 ChatGPT / Claude.ai** | A | 手工管理 handoff.yaml + 手工跑 QG |
| **企业内部开发平台** | C | 平台数据库存 handoff，平台 UI 强制审批 |

## 八、常见问题

**Q：我的工具没有 Plan Mode，怎么实现 HITL-In？**
A：约定「AI 起草 → 人 review → AI 执行」的双步流程，或工具 UI 加审批按钮。HITL-In 是契约，不是工具特性。

**Q：我的工具不支持读 markdown 模板？**
A：所有主流 LLM 工具都能读 markdown（GPT/Claude/Gemini/通义/文心都支持）。若工具不支持，换工具或改用纯文本贴 prompt。

**Q：自研 Agent 接入是否必须实现所有 QG checklist？**
A：最小化实现 QG-D + QG-B 两关（最关键）。QG-S/QG-Ship 可人工 checklist 兜底。

**Q：能否只用 02-产物层 模板，不接入 01-标准层 schema？**
A：可以（轻量化）。但会失去阶段间自动校验能力，依赖人盯交接。建议至少部署 handoff.yaml schema。

## 九、自带工具适配的验收标准

你的工具若满足以下全部，视为已成功接入本体系：

- [ ] 能加载 [02-产物层/](../02-产物层/) 的任意模板并填字段
- [ ] 能按 [01-标准层/04](../01-标准层/04-阶段交接契约Schema.md) 生成 handoff.yaml 且通过 `validate-handoff.sh`
- [ ] L3/L4 节点（D 共识 / S 方案 / Ship 上线）能阻塞等人审
- [ ] 阶段切换时能解析上游 handoff.yaml 加载产物
- [ ] QG checklist 不通过时不放行下游
