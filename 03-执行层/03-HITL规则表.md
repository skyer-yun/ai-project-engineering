# HITL 规则表

> **定位**：本文件是「HITL × 不可逆 × 工种」交叉权威表。结合 [00-理论层/03-HITL模式与不可逆性矩阵.md](../00-理论层/03-HITL模式与不可逆性矩阵.md)（原理）和 [01-标准层/01-五阶段定义.md](../01-标准层/01-五阶段定义.md)（阶段定义），给出落地查表。
>
> **用途**：项目启动时按此表为每个阶段分配 HITL 模式 + 不可逆等级 + 主责工种。
>
> **术语对照**：主责工种按 6 工种给（售前/产品/研发/测试/交付/PM）；括号内是**方法论逻辑角色**（仅用于阶段交接契约签字），映射详见 [01-标准层/01-五阶段定义.md](../01-标准层/01-五阶段定义.md)。

| **开发阶段·一般模块/CRUD** | 研发（构建师（Builder）） | — | **Fallback** | L1 | 推荐 | atomic commit | 审查师（Reviewer） 抽检 |

| **交付阶段·测试执行** | 测试 + 交付（交付师（Shipper）） | 测试/研发交叉（审查师（Reviewer）） | **On + Fallback**（自动 Fallback，手动 On） | L1 | — | 测试报告版本 | 交付师（Shipper） |
| **交付阶段·部署（生产）** | 交付（交付师（Shipper）） | 测试/研发交叉（审查师（Reviewer）） + 客户 | **In** | **L4** | **强制**（步骤+回滚预案） | **完整快照** | 交付师（Shipper） + 审查师（Reviewer） + **客户签字** |
| **交付阶段·验收交付** | 交付（交付师（Shipper）） | 客户 + PM（统筹师（Keeper）） | **In** | **L4** | 推荐 | 验收报告版本 | 交付师（Shipper） + **客户签字** + 统筹师（Keeper） |
| **交付阶段·培训移交** | 交付（交付师（Shipper）） | 客户 | **On** | L2 | — | 培训材料版本 | 交付师（Shipper） + 客户反馈 |
| **复盘阶段** | PM（统筹师（Keeper）） | 全工种 | **In** | L3 | 推荐 | 复盘报告版本 | 统筹师（Keeper） + 各工种代表 |

## 二、查表规则

### 2.1 怎么用这张表

1. **识别当前阶段**：五阶段之一（需求/设计/开发/交付/复盘）。
2. **看子任务**：如开发阶段要区分"关键模块"还是"CRUD"。
3. **取 HITL 模式**：In / On / Fallback 之一。
4. **取不可逆等级**：L1-L4，决定回滚成本。
5. **取必签角色**：阶段 Exit 时必须有这些逻辑角色的签名。

### 2.2 HITL 模式决策树

```
任务进入
   ↓
是客户面向或不可逆？ ──── 是 ──→ In（必须审批）
   │ 否
   ↓
是中风险可回滚？ ──────── 是 ──→ On（监督可回滚）
   │ 否
   ↓
是低风险完全可逆？ ────── 是 ──→ Fallback（自动+兜底）
   │ 否
   ↓
不确定 → 默认 In（保守原则）
```

### 2.3 Plan Mode 强制场景汇总

- 需求阶段：需求面访大纲
- 设计阶段前半：PRD 12 部分大纲 + 用户故事
- 设计阶段后半：架构章节 + 详细设计章节
- 开发阶段关键模块：文件改动 + 单测计划
- 交付阶段部署：步骤 + 回滚预案
- 复盘阶段：复盘维度大纲

## 三、按工种视角的 HITL 速查

### 售前 + 产品（对应逻辑角色：需求规范师（Spec-Writer））

| 阶段 | HITL | 关键动作 |
|------|------|---------|
| 需求阶段（主） | In | 面访 / 整理 / 客户确认 |
| 设计阶段·前半（主） | In | 方案 / PRD 评审 |

### 研发（对应逻辑角色：构建师（Builder））

| 阶段 | HITL | 关键动作 |
|------|------|---------|
| 设计阶段·后半（主） | In | 架构 / 详设评审 |
| 开发阶段·关键模块 | In | Plan Mode + atomic commit |
| 开发阶段·一般模块 | Fallback | AI 自动 + 抽检 |

### 测试/研发交叉（对应逻辑角色：审查师（Reviewer））

| 阶段 | HITL | 关键动作 |
|------|------|---------|
| 设计阶段 | In | 方案/架构/详设评审会签 |
| 开发阶段 | In | PR Review diff |
| 交付阶段 | In | 测试评审 / 部署审批 |

### 测试 + 交付（对应逻辑角色：交付师（Shipper））

| 阶段 | HITL | 关键动作 |
|------|------|---------|
| 交付阶段·测试 | On + Fallback | 自动+手动 |
| 交付阶段·部署 | **In（L4）** | 完整快照 + 业务签字 |
| 交付阶段·验收 | **In（L4）** | 客户签字 |

### PM（对应逻辑角色：统筹师（Keeper））

| 阶段 | HITL | 关键动作 |
|------|------|---------|
| 全程 | 监督 | 契约守护 + 上下文治理 |
| 复盘阶段（主） | In | 复盘报告 + 改进项录入 |

## 四、违反规则的常见错误

| 错误 | 后果 | 正解 |
|------|------|------|
| 用 Fallback 跑交付阶段·部署 | 生产事故无人审 | 交付阶段·部署强制 In + 完整快照 |
| 用 On 跑设计阶段·架构评审 | 架构定稿后发现方向错 | 设计阶段·后半强制 In + 评审会签字 |
| 不打 Checkpoint 就改开发阶段代码 | AI 写错无法回滚 | 开发阶段每次 atomic commit 前 snapshot |
| 复盘阶段用 Fallback 自动生成复盘 | 复盘流于形式 | 复盘阶段强制 In + 多角色参与 |
| 一个工种全程用同一 HITL 模式 | 关键点失守或低效 | 按阶段/子任务切换模式 |
