# 售前工程师 Playbook

> **目标读者**：售前工程师 / 解决方案工程师 / 商务对接人
> **主责阶段**：需求（D，前半）+ 设计（S，前半：技术方案/投标文件）
> **方法论逻辑角色**：需求规范师（Spec-Writer）（与产品经理共担）
> **业界锚点**：Anthropic *Building Effective Agents* / Spec-Driven Development / Context Engineering 四原则
> **工具中立**：本 Playbook 不绑定具体 AI 工具。Claude Code / Codex / Cursor / 自带工具均可，详见 [05-适配层/](../../05-适配层/)。

---

## 一、工种定位

售前工程师是「商机→需求→方案」的转化者，主责客户侧：
- **商机理解**：客户拜访、需求挖掘、痛点澄清
- **需求收集**：招标书解读、客户面访、竞品对标
- **技术方案**：11/7/8 章方案、客户演示材料、投标文件（技术部分）

**与产品经理的边界**：售前专注客户侧（讲价值、讲方案），产品经理专注交付侧（讲规范、讲 PRD）。两者在需求阶段协同，共同签 QG-需求。

**与研发工程师的边界**：售前写技术方案（客户视角），研发写架构设计（落地视角）。设计阶段并行，售前给研发提供客户约束。

## 四、五阶段覆盖 + HITL 模式

| 阶段 | 售前工程师角色 | HITL | 核心动作 |
|------|-------------|------|---------|
| **需求**（主） | **主**（与产品共担） | **In**（L3 共识） | 客户面访、需求 5 维整理、干系人签字 |
| **设计前半**（主） | **主**（方案/投标） | **In**（L3 方案） | 方案评审、客户演示、投标应答 |
| **设计后半**（参与） | 协 | In（研发主） | 提供客户约束，参与架构评审 |
| 开发 | 协（客户答疑） | On | 客户问询答疑、范围澄清 |
| 交付 | 协（验收支持） | In（L4 验收） | 参与客户验收会、答疑 |
| 复盘 | 参 | In | 售前复盘输入 |

详见 [03-执行层/03-HITL规则表.md](../03-HITL规则表.md)。

## 五、Loop 5 字段（售前工程师版）

```yaml
loop:
  goal: "把客户模糊诉求 → 结构化需求共识 → 客户认可的技术方案"
  context: |
    上游：客户原始诉求（招标书/邮件/口述/竞品截图）
    项目约束：合规/预算/时间/技术栈
  tools:
    - 任意 AI 工具（Claude Code / Codex / Cursor 等，详见 05-适配层）
    - Plan Mode（方案大纲先审后写）
    - 文档版本工具（Git / WPS / OneDrive）
  checkpoint: "每份文档评审通过 → 版本号 +1 → 入工件演化层"
  exit: "客户+产品+PM 三方签字 → 签交接契约 需求→设计 或 设计→开发"
```

**需求阶段 Loop（商机→需求共识）**：

```
Plan     → 列访谈对象 + 大纲 + 信息缺口（5 维：业务/角色/场景/约束/优先级）
Act      → AI 整理纪要 → 结构化需求记录
Observe  → 5 维完整性自动校验（客观）
Reflect  → 客户 + 产品 + PM 确认需求点（主观）
Exit     → 5 维全绿 + 干系人签字 → QG-需求
```

**设计前半 Loop（共识→客户方案）**：

```
Plan     → Plan Mode：列方案 11 章大纲
Act      → AI 生成方案/客户演示/投标文件
Observe  → 章节完整度 + 客户约束覆盖率（客观）
Reflect  → 方案评审会 + 客户确认（主观）
Exit     → 评审通过 + 客户签字 → 配合 QG-设计
```

## 七、典型协作流

### 7.1 需求 → 设计前半（自循环）

```
客户招标书 → 售前整理需求 → 与产品共担 QG-需求 通过
   ↓
售前写技术方案 → 方案评审 → 客户确认
   ↓
与产品 PRD 对齐（同源产物，版本同步）
   ↓
配合研发架构设计 → 共同签 QG-设计 → 交接给开发
```

### 7.2 与产品经理协作（需求阶段）

需求阶段双主责：
- 售前主「客户视角」：拜访、面访、客户语言
- 产品主「交付视角」：需求条目化、优先级、用户故事
- 协同产物：干系人清单（共签）、需求分析报告（合写）

### 7.3 与研发工程师协作（设计阶段后半）

设计后半由研发主导架构/详设，售前参与：
- 提供客户约束清单（合规/性能/兼容性）
- 参与架构评审会
- 确认架构满足客户承诺

## 九、反模式（禁止行为）

| 反模式 | 后果 | 正解 |
|--------|------|------|
| 跳过需求阶段直接写方案 | 客户需求盲区导致返工 | 需求阶段必须先过 QG-需求 |
| 把客户口述原话当需求 | 二义性大、交付灾难 | 5 维整理 + 客户书面确认 |
| 方案过度承诺 | 交付无法兑现、客户满意度崩盘 | 方案对齐研发可行性评估 |
| 不与产品 PRD 对齐 | 方案与交付不一致 | 同源产物，版本同步 |
| 客户变更不走流程 | 范围蔓延 | 走变更评审 + 重新签 QG-需求 |
