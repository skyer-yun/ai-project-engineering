# 产品经理 Playbook

> **目标读者**：产品经理 / 需求分析师 / 业务分析师
> **主责阶段**：需求（D，后半）+ 设计（S，前半：产品方案/原型四件套/PRD/验收标准/UI-UX）
> **方法论逻辑角色**：需求规范师（Spec-Writer）（与售前工程师共担）
> **业界锚点**：Anthropic *Spec-Driven Development* / Context Engineering 四原则 / PRD 12 部分结构
> **工具中立**：本 Playbook 不绑定具体 AI 工具。Claude Code / Codex / Cursor / 自带工具均可，详见 [05-适配层/](../../05-适配层/)。

---

## 一、工种定位

产品经理是「客户诉求→交付规范」的转化者，主责交付侧：
- **需求条目化**：把售前收集的客户诉求落成结构化需求条目（REQ-NNN 台账，每条可溯源到调研素材 SRC-NNN）
- **优先级排序**：MoSCoW / Kano 模型，区分 Must/Should/Could/Won't
- **产品方案**：需求-方案覆盖矩阵（每条 REQ 有方案项，无镀金项）
- **原型四件套**：页面树（YAML）/ 高保真原型包（HTML）/ 标注数据（ANN-NNN→REQ-NNN）/ 原型说明（覆盖矩阵）
- **PRD 编写**：12 部分完整 PRD，反向引用原型页面 ID 与 ANN 编号
- **验收标准**：AC-NNN 清单（Given-When-Then，测试用例派生源）

**与售前工程师的边界**：售前讲客户语言（价值/方案/投标），产品讲交付语言（规范/PRD/验收）。两者在需求阶段双主责，共同签 QG-需求。

**与研发工程师的边界**：产品写 PRD（What/Why），研发写架构设计（How）。设计阶段并行，产品给研发提供验收标准。

## 四、五阶段覆盖 + HITL 模式

| 阶段 | 产品经理角色 | HITL | 核心动作 |
|------|-------------|------|---------|
| **需求**（主） | **主**（与售前共担） | **In**（L3 共识） | 需求条目化、优先级、需求基线 |
| **设计前半**（主） | **主**（PRD/UI-UX） | **In**（L3 评审） | PRD 编写、原型设计、UI-UX 规范 |
| **设计后半**（参与） | 协 | In（研发主） | 提供验收标准，参与架构评审 |
| 开发 | 协（需求澄清） | On | 需求答疑、范围确认 |
| 交付 | 协（验收支持） | In（L4 验收） | 参与验收会、需求确认 |
| 复盘 | 参 | In | 需求偏差复盘输入 |

详见 [03-执行层/03-HITL规则表.md](../03-HITL规则表.md)。

## 五、Loop 5 字段（产品经理版）

```yaml
loop:
  goal: "把客户模糊诉求 → 结构化需求条目 → 可执行的 PRD"
  context: |
    上游：客户访谈纪要 / 招标书要点 / 售前整理的需求记录
    约束：业务目标/用户角色/场景/优先级/验收标准
  tools:
    - 任意 AI 工具（Claude Code / Codex / Cursor 等，详见 05-适配层）
    - Plan Mode（PRD 大纲先审后写）
    - 文档版本工具（Git / WPS / OneDrive）
  checkpoint: "PRD 评审通过 → 版本号 +1 → 入工件演化层"
  exit: "PRD 12 部分齐全 + 验收标准可测试 → 签交接契约 设计→开发"
```

**需求阶段 Loop（诉求→需求基线）**：

```
Plan     → 列干系人 + 业务目标 + 信息缺口（5 维）
Act      → AI 整理需求条目 + 优先级排序
Observe  → 5 维完整性 + 优先级覆盖率（客观）
Reflect  → 客户 + 售前 + PM 确认需求点（主观）
Exit     → 需求基线 + 干系人签字 → QG-需求
```

**设计前半 Loop（基线→PRD）**：

```
Plan     → Plan Mode：列 PRD 12 部分大纲
Act      → AI 生成 PRD + 原型 + 验收标准
Observe  → 12 部分完整度 + 验收标准可测试率（客观）
Reflect  → PRD 评审会 + 研发可行性确认（主观）
Exit     → 评审通过 + 签字 → 配合 QG-设计
```

## 七、典型协作流

### 7.1 需求 → 设计前半（自循环）

```
售前整理客户诉求 → 产品条目化 → 与售前共担 QG-需求 通过
   ↓
产品写 PRD + 原型 → PRD 评审 → 研发可行性确认
   ↓
与售前技术方案对齐（同源产物，版本同步）
   ↓
配合研发架构设计 → 共同签 QG-设计 → 交接给开发
```

### 7.2 与售前工程师协作（需求阶段）

需求阶段双主责：
- 售前主「客户视角」：拜访、面访、客户语言
- 产品主「交付视角」：需求条目化、优先级、用户故事
- 协同产物：需求分析报告（合写）、干系人清单（共签）

### 7.3 与研发工程师协作（设计阶段）

设计阶段前半产品主 PRD，后半研发主架构：
- 产品交付 PRD + 验收标准 + 原型
- 研发反馈可行性 + 技术约束
- 协同产物：PRD 评审纪要、需求变更记录

## 九、反模式（禁止行为）

| 反模式 | 后果 | 正解 |
|--------|------|------|
| PRD 写功能不写验收标准 | 测试无依据、交付扯皮 | 每个功能点必带可测试验收标准（AC-NNN） |
| 跳过优先级直接写 PRD | 资源错配、Must 没做做了 Could | MoSCoW 排序后再写 PRD |
| 不与售前方案对齐 | 方案承诺与 PRD 不一致 | 同源产物、版本同步 |
| 需求变更不走流程 | 范围蔓延、基线失效 | 走变更评审 + 重新签 QG-需求 |
| 把原型当 PRD | 缺少 Why/验收/边界 | 原型是 PRD 的图示，PRD 12 部分不可省 |
| 需求无来源（臆造需求） | 无法向客户交代、范围失控 | 每条 REQ 引用 ≥1 个 SRC 素材（QG-需求.9） |
| 原型只画页面不做标注 | PRD 写不下去、研发反复问 | 每条 P0 需求 ≥1 条 ANN 标注挂接到页面元素（QG-设计.12） |
| 原型包混入演示/调试代码 | 原型不可交付、复用脏 | 原型包保持纯净，增强版由合成生成 |
