# Spec-Writer 角色_playbook

> **目标读者**：售前工程师 / 产品经理 / 解决方案架构师 / 业务分析师
> **主责阶段**：D-Discover（主） + S-Spec 前半（方案/PRD/UI-UX）
> **业界锚点**：Anthropic *Building Effective Agents* / Spec-Driven Development / Context Engineering 四原则
> **工具中立**：本 Playbook 不绑定具体 AI 工具。Claude Code / Codex / Cursor / 自带工具均可，详见 [05-适配层/](../../05-适配层/)。

---

## 一、角色定位

Spec-Writer 是「需求→可执行规范」的转化者。承担原售前+产品职责的合并：
- 售前：需求分析、技术方案、客户演示、投标
- 产品：PRD、原型 Demo、用户故事、验收标准

**为什么合并**：AI 时代，售前方案与产品 PRD 在 S 阶段必须是同源产物——方案讲客户价值，PRD 讲可执行规范，两者错位会导致交付灾难。Spec-Writer 用同一支笔写完，确保一致。

| # | 触发语 | 阶段 | 期望产物 |
|---|--------|------|---------|
| 1 | 「整理这次客户访谈」 | D | 需求分析报告 + 干系人清单 |
| 2 | 「写技术方案」 | S 前半 | 技术方案文档（11/7/8 章） |
| 3 | 「写 PRD」 | S 前半 | PRD（12 部分）+ 用户故事 |
| 4 | 「做原型 Demo」 | S 前半 | HTML 原型 / 高保真设计 |

## 四、DSBL 阶段覆盖 + HITL 模式

| 阶段 | HITL | 核心动作 |
|------|------|---------|
| **D**-Discover（主） | **In** | 客户面访、需求 5 维整理、干系人签字 |
| **S** 前半（方案/PRD/UI-UX，主） | **In** | 方案评审、PRD 评审、UI-UX 客户确认 |
| **S** 后半（架构/详设，参与） | In（Builder 主） | 提供需求上下文，参与架构评审 |
| B / Ship / L | 协作 | 客户答疑、变更评估、复盘输入 |

详见 [03-执行层/03-HITL规则表.md](../03-HITL规则表.md)。

## 五、Loop 5 字段（Spec-Writer 版）

```yaml
loop:
  goal: "把客户模糊诉求 → 结构化需求共识 → 可执行规范"
  context: |
    上游：客户原始诉求（招标书/邮件/口述/竞品截图）
    项目约束：合规/预算/时间/技术栈
  tools:
    - 任意 AI 工具（Claude Code / Codex / Cursor 等，详见 05-适配层）
    - Plan Mode（PRD 大纲先审后写）
    - 文档版本工具（Git / WPS / OneDrive）
  checkpoint: "每份文档评审通过 → 版本号 +1 → 入工件演化层"
  exit: "客户+Builder+Reviewer 三方签字 → 签交接契约 D→S 或 S→B"
```

**D 阶段 Loop（需求→共识）**：

```
Plan     → 列访谈对象 + 大纲 + 信息缺口（5 维：业务/角色/场景/约束/优先级）
Act      → AI 整理纪要 → 结构化需求记录
Observe  → 5 维完整性自动校验（客观）
Reflect  → 客户 + PM 确认需求点（主观）
Exit     → 5 维全绿 + 干系人签字 → QG-D
```

**S 前半 Loop（共识→规范）**：

```
Plan     → Plan Mode：列方案 11 章 + PRD 12 部分大纲
Act      → AI 生成方案/PRD/原型/UI-UX
Observe  → 章节完整度 + 验收标准可测试率（客观）
Reflect  → 方案评审会 + PRD 评审会 + 客户确认（主观）
Exit     → 评审通过 + 客户签字 → QG-S
```

## 七、典型协作流

### 7.1 D → S 流（自循环）

```
客户招标书 → Spec-Writer 整理需求 → QG-D 通过
   ↓
Spec-Writer 写技术方案 → 方案评审 → 客户确认
   ↓
Spec-Writer 写 PRD + UI-UX → PRD 评审 → 客户确认
   ↓
签交接契约 S→B（to_role: Builder）
```

### 7.2 与 Builder 协作（S 后半）

S 阶段后半（架构/详设）由 Builder 主导，Spec-Writer 参与：
- 提供需求上下文（PRD 完整版）
- 参与架构评审会
- 确认架构满足业务需求

### 7.3 与 Reviewer 协作

Reviewer 跨阶段审查：
- D 阶段：审查需求 5 维完整性
- S 阶段：审查方案/PRD/架构一致性
- Spec-Writer 根据 Reviewer 反馈 Loop 修正

## 九、反模式（禁止行为）

| 反模式 | 后果 | 正解 |
|--------|------|------|
| 跳过 D 直接写 PRD | 需求盲区导致返工 | D 必须先过 QG-D |
| 把客户口述原话当需求 | 二义性大 | 5 维整理 + 客户确认 |
| 方案与 PRD 不一致 | 交付灾难 | 同源产物，版本同步 |
| 不签交接契约就交付 Builder | 责任不清 | 必签 S→B 契约 |
| 客户变更不评估影响 | 范围蔓延 | 走变更评审 + 重新签 QG-D |
