# Shipper 角色 Playbook

> **目标读者**：测试工程师 / 交付工程师 / 运维工程师 / 实施顾问
> **主责阶段**：S-Ship（测试/部署/验收/培训/移交）
> **业界锚点**：Anthropic HITL 三件套 / Eval-Driven Development / Cursor Checkpoints
> **工具中立**：详见 [05-适配层/](../../05-适配层/)。

---

## 一、角色定位

Shipper 是「可运行代码→生产可用价值」的闭环者。承担原测试+交付职责的合并：
- 测试：测试策略、用例生成、测试执行、缺陷管理
- 交付：部署实施、验收管理、培训、运维移交

**为什么合并**：AI 时代，测试和交付的边界模糊——CI/CD 自动化让"测试通过即部署"成为常态，分开会拖慢节奏。Shipper 用同一支笔写完测试策略 + 部署方案，确保一致。

## 四、DSBL 阶段覆盖 + HITL 模式

| 阶段 | HITL | 核心动作 |
|------|------|---------|
| **Ship** 测试策略（主） | **On** | 测试评审 + dev 反馈 |
| **Ship** 测试执行（主） | **On + Fallback** | 自动化测试 F，手动测试 On |
| **Ship** 缺陷闭环（主） | **In + On**（关键 In） | 缺陷 close 会签 |
| **Ship** 部署（主，**L4**） | **In** | 部署前完整快照 + 业务签字 |
| **Ship** 验收（主，**L4**） | **In** | 客户 UAT 签字 |
| **Ship** 培训移交（主） | **On** | 客户反馈 + 知识转移确认 |
| L | 协作 | 提供测试/交付数据供复盘 |

> **L4 不可逆**：Ship 阶段是项目唯一 L4 阶段，部署和验收一旦签字无法撤回。HITL-In 强制 + Checkpoint 完整快照 + 业务签字 + 客户签字 四重保险。

## 五、Loop 5 字段（Shipper 版）

```yaml
loop:
  goal: "将可运行代码 → 生产可用价值（测试 / 部署 / 验收 / 培训 / 移交）"
  context: |
    上游：可运行代码（已 merge 主干）+ 联调报告 + 接口文档
    项目约束：SLO / 合规 / 客户验收标准
  tools:
    - 任意 AI 工具（Claude Code / Codex / Cursor 等）
    - 测试框架（Jest / Pytest / JMeter / Selenium）
    - CI/CD（GitHub Actions / Jenkins / ArgoCD）
    - 监控告警（Prometheus / Grafana）
  checkpoint: "部署前完整快照（含 DB + 配置 + AI context）→ 一键回滚"
  exit: "QG-Ship 全绿（测试 P0/P1 清零 + 部署成功 + 客户签字）→ 交接 L"
```

**Ship 测试 Loop**：

```
Plan     → 测试策略 + 用例矩阵 + 自动化范围
Act      → AI 生成用例 + 自动化执行
Observe  → 覆盖率 + 通过率 + P0/P1 缺陷数（客观）
Reflect  → 缺陷分级评审 + Shipper + Reviewer + Builder 联合确认（主观）
Exit     → 用例通过率 ≥95% + P0/P1 清零 → 测试报告签字
```

**Ship 部署 Loop（L4）**：

```
Plan     → 部署步骤 + 回滚预案 + 通知清单
Act      → 执行部署（生产环境）
Observe  → 部署成功率 + 健康检查 + 监控告警（客观）
Reflect  → 业务签字 + 客户确认（主观，L4 必须 In）
Exit     → 部署成功 + 业务签字 → 部署记录归档
```

## 八、典型协作流

### 8.1 B → Ship 流

```
Builder 完成 QG-B（提测前 P0/P1 清零）→ 签交接契约 B→Ship
   ↓
Shipper 接收：测试策略 + 用例生成
   ↓
测试执行 → 缺陷反馈给 Builder → 缺陷闭环
   ↓
P0/P1 清零 → QG-Ship 测试维度通过
   ↓
部署方案 + 演练 → 部署执行（L4）→ 业务签字
   ↓
客户 UAT → 验收报告（客户签）
   ↓
培训 + 运维移交 → QG-Ship 全绿 → 签交接契约 Ship→L
```

### 8.2 与 Reviewer 协作

Reviewer 参与 Ship 全程：
- 测试评审（覆盖率 + 用例质量）
- 部署评审（步骤 + 回滚预案）
- 验收评审（UAT + 客户签字）

### 8.3 与客户协作（L4 必签）

- 部署前：业务签字（确认时间窗口）
- 部署后：客户确认（业务可用）
- 验收：客户 UAT 签字
- 培训：客户反馈 + 知识转移确认

## 十、反模式

| 反模式 | 后果 | 正解 |
|--------|------|------|
| 跳过测试直接部署 | 生产事故 | 测试 P0/P1 必须清零 |
| 部署不打 Checkpoint | 部署失败无法回滚 | 完整快照（DB+配置+context） |
| 客户未签就声称验收完成 | 法律风险 | 客户 UAT 必须签字 |
| 自动化测试全代替手动 | 业务逻辑盲区 | 关键场景必须手动 + Reflect |
| 培训流于形式 | 客户不会用 → 满意度低 | 培训 + 考核 + 反馈闭环 |
