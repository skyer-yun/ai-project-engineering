# Reviewer 角色 Playbook

> **目标读者**：资深工程师 / 技术负责人 / 质量负责人 / 评审委员会成员
> **主责阶段**：跨阶段（S + B + Ship 全程审查）
> **业界锚点**：Anthropic *Demystifying evals for AI agents* / Eval-Driven Development / Observe vs Reflect 分离原则
> **工具中立**：可用任意 AI 工具辅助审查，但 Reviewer 必须是**人**或资深 agent。

---

## 一、角色定位

Reviewer 是「质量守门」的跨阶段审查者。AI 时代特有的角色——AI 写代码快，但"AI 跑过 ≠ 通过"。Reviewer 的存在是为了打破这个幻觉。

**为什么单独成角色**：
- 历史问题：研发自测 = 自己批自己，质量失守
- AI 时代问题：AI 代码"看起来对"但架构性错误难发现
- 业界共识：Anthropic Observe（客观 Eval）与 Reflect（主观人评）必须分离

**Reviewer 的核心价值**：补足客观 Eval 的盲区，给"看起来对"的产物做主观判断。

## 三、触发语

| # | 触发语 | 阶段 | 期望产物 |
|---|--------|------|---------|
| 1 | 「审查这份方案」 | S 前半 | 方案评审意见（章节完整 + 客户契合度） |
| 2 | 「审查这份 PRD」 | S 前半 | PRD 评审意见（验收标准可测试 + 用户故事完整） |

| 7 | 「验收评审」 | Ship | 验收评审意见（UAT 通过 + 客户签字） |

## 四、DSBL 阶段覆盖 + HITL 模式

| 阶段 | HITL | 核心动作 |
|------|------|---------|
| **D**（参与） | In | 审查需求 5 维完整性 |
| **S** 前半（评） | **In** | 方案评审 + PRD 评审会签 |
| **S** 后半（评） | **In** | 架构评审 + 详设评审 + ADR 决策 |
| **B**（评） | **In**（关键） + On（一般） | PR Review diff + 架构性审查 |
| **Ship**（评） | **In** | 测试评审 + 部署评审 + 验收评审 |
| **L**（参与） | In | 复盘 QG 通过率数据 |

**核心铁律**：Reviewer 是 Reflect 字段的执行者。Observe（客观 Eval）由工具/脚本完成，Reflect（主观判断）必须由 Reviewer 完成。

## 五、Loop 5 字段（Reviewer 视角）

Reviewer 不主导 Loop，但参与每个阶段的 Reflect 字段：

```yaml
loop_for_review:
  trigger: "上游产物提交评审"
  plan:    "列出审查维度 + 重点风险"
  act:     "Review 产物（用 AI 辅助初筛 + 人深度判断）"
  observe: "客观指标复核（覆盖率/通过率/指标是否达标）"
  reflect: "主观判断（架构性 / 安全 / 性能 / 可维护性）"
  exit:    "出审查意见 + 签字 / 退回返工"
```

## 六、审查维度（4 维度 × 4 级）

### 6.1 代码审查 4 维度

| 维度 | 检查点 |
|------|--------|
| **正确性** | 业务逻辑 / 边界条件 / 异常处理 / 并发 |
| **架构性** | 分层是否清晰 / 依赖方向 / 单一职责 / 可扩展性 |
| **可维护性** | 命名 / 注释 / 复杂度 / 重复代码 / 测试可读性 |
| **安全性** | 注入 / 鉴权 / 敏感数据 / 依赖漏洞 / OWASP Top 10 |

### 6.2 严重程度 4 级

| 级别 | 含义 | 处理 |
|------|------|------|
| 🔴 Block | 必须修复才能合并 | 阻塞 Exit |
| 🟠 Major | 强烈建议修复 | 当前 Loop 必修 |
| 🟡 Minor | 可后续修复 | 记录 TODO |
| 🟢 Suggestion | 优化建议 | 可选 |

### 6.3 文档审查 4 维度

| 维度 | 适用 | 检查点 |
|------|------|--------|
| **完整性** | 方案/PRD/架构 | 章节齐全 / 字段完整 |
| **一致性** | 方案 ↔ PRD ↔ 架构 ↔ 详设 | 跨文档对得上 |
| **可测试性** | PRD / 验收标准 | 是否能量化验收 |
| **可执行性** | 详设 / OpenAPI | AI 工具能否读懂执行 |

## 七、典型协作流

### 7.1 S 阶段评审（方案/PRD/架构）

```
Spec-Writer + Builder 完成产物 → 提交评审
   ↓
Reviewer 收到 → 列审查维度 → 用 AI 初筛 + 人深判
   ↓
出评审意见（4 维度 × 4 级）→ 退回或签字
   ↓
签字 → QG-S 通过 → 签交接契约
```

### 7.2 B 阶段 PR Review

```
Builder 提交 PR → Reviewer 收到
   ↓
关键模块：人深审 diff（架构 / 安全 / 性能）
一般模块：AI 辅助抽检（lint / 单测覆盖率 / 类型）
   ↓
出审查意见 → 退回或 merge
   ↓
merge → atomic commit → 进入下一特性
```

### 7.3 Ship 阶段评审

- 测试评审：覆盖率 + P0/P1 缺陷清零 + 缺陷逃脱率
- 部署评审：步骤 + 回滚预案 + 业务签字
- 验收评审：UAT 通过 + 客户签字 + 运维移交

## 九、反模式

| 反模式 | 后果 | 正解 |
|--------|------|------|
| 用 AI 客观指标代替人审 | 架构性错误漏审 | Observe + Reflect 必须分离 |
| Reviewer 与 Builder 是同一人 | 自己批自己 | 必须不同人/不同 agent |
| 只看代码不看文档 | 接口契约失守 | 文档审查同步做 |
| 评审意见无级别 | "改改"无优先级 | 必须标 🔴/🟠/🟡/🟢 |
| 关键模块抽检 | 关键点失守 | 关键模块必须人深审 |

## 十、Reviewer 与 Keeper 的区别

| 维度 | Reviewer | Keeper |
|------|---------|--------|
| 关注点 | 单个产物/阶段的质量 | 全程上下文/契约/记忆 |
| 时间尺度 | 当前阶段 | 跨阶段全程 |
| 工具 | AI 辅助审查 + 人深判 | memory / 契约工具 / 工件演化层 |
| 介入时机 | 评审节点 | 每次状态变更 |
