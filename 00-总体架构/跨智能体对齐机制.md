# 跨智能体对齐机制

## 统一设计范式

### 统一目录结构

每个智能体遵循相同的目录规范：

```
{agent-name}/
├── skill.md                    # 主入口：YAML 头 + 9 节正文
├── README.md                   # 安装/使用/版本说明
├── config/
│   ├── dependencies.md         # 依赖定义（核心/增强/降级）
│   ├── triggers.md             # 触发规则（工作流/技能/组合）
│   └── roles.md                # 角色定义（如有）
├── workflows/
│   └── {workflow-name}.md      # 各工作流详细定义
├── knowledge/
│   └── {topic}/                # 按主题组织的知识库
│       └── README.md
└── memory/
    └── preferences.md          # 用户偏好模板
```

### skill.md 统一 9 节结构

| 节号 | 标题 | 内容要求 |
|------|------|----------|
| 1 | 角色定义 | 能力边界、角色切换规则、不负责事项 |
| 2 | 意图识别 | LLM 语义优先 + triggers 兜底 + 置信度三档路由 |
| 3 | 依赖检查 | 核心/增强分级、检测方法、降级策略 |
| 4 | 工作流路由 | 各工作流定义、触发条件、产物清单 |
| 5 | 知识库 | 知识主题列表、加载策略（每次 2-3 个） |
| 6 | 记忆系统 | 写入条件、存储位置、合并策略 |
| 7 | 核心规则 | 智能体特有的行为约束（10-15 条） |
| 8 | 启动流程 | 动态问候模板、交接提示、初始化检查 |
| 9 | 错误处理 | 异常场景、回退方案、用户引导 |

### YAML 头部约束

```yaml
---
name: {agent-name}
version: {semver}
description: {一句话定位，含覆盖阶段和核心能力}
dependencies:
  core: [必须依赖的技能列表]
  enhanced: [增强体验的技能列表]
triggers:
  workflows: [工作流名称列表]
  keywords: [触发关键词列表]
---
```

- name 使用 kebab-case
- version 遵循 semver
- description 不超过 100 字，包含阶段标记（如 N1-N4）
- dependencies 分 core（缺失则核心功能不可用）和 enhanced（缺失则降级）
- triggers 的 keywords 仅作兜底，LLM 语义路由优先

## 统一记忆策略

### 记忆分流规则

| 内容类型 | 存储位置 | 说明 |
|----------|----------|------|
| 用户偏好（语言/风格/习惯） | `{agent}/memory/preferences.md` | 保留在 skill 内部 |
| 项目决策（技术选型/方案确认） | 原生 memory（MEMORY.md） | 合并到全局记忆 |
| 上下文信息（客户/需求细节） | 对话上下文 | 不持久化 |
| 跨智能体信息（交接产物） | 原生 memory + 项目目录 | 双写 |

### 记忆写入条件

1. 完成一个完整交付物
2. 用户明确表达"记住这个""下次这样"
3. 发现用户重复询问同一类信息
4. 对话超过 20 轮
5. 创建或修改项目文件时

### 记忆合并原则

- 偏好信息不合并到原生 memory，保留在 skill 专属 memory/
- 项目决策合并时追加到 MEMORY.md 对应分类
- 详细内容拆到独立文件，MEMORY.md 保持索引角色
- 跨智能体信息标注来源智能体

## 统一产物标准

### 命名规范

```
{日期}-{类型描述}-{版本}.{扩展名}
例：2026-05-22-技术方案-v1.docx
    2026-05-22-PRD-v2.md
    2026-05-22-测试报告-v1.docx
```

### 归档路径

```
项目文档/{客户名}-{项目名}/
├── 01-需求/
│   ├── 需求分析报告
│   └── 竞品分析
├── 02-产品/
│   ├── PRD
│   └── 原型
├── 03-设计/
│   ├── 架构设计
│   └── 详细设计
├── 04-开发/
│   └── 代码
├── 05-测试/
│   ├── 测试用例
│   └── 测试报告
├── 06-交付/
│   ├── 部署文档
│   ├── 验收报告
│   └── 培训材料
└── 07-管理/
    ├── 项目计划
    └── 会议纪要
```

### 产物质量标准

| 产物 | 质量维度 | 量化标准 |
|------|----------|----------|
| PRD | 完整性/可测试性 | 12 部分完整、功能点有验收标准 |
| 技术方案 | 可行性/完整性 | 11 章完整、架构图+时序图 |
| 测试报告 | 覆盖率/准确性 | 用例通过率 >= 95% |
| 交付文档 | 完整性/可操作性 | 部署步骤可复现、运维手册可执行 |

## 统一依赖检查

### 检查流程

```
启动 → 扫描 ~/.claude/skills/ → 比对 dependencies.md
  → core 全部满足 → 正常运行
  → core 缺失 → 提示安装 + 降级运行
  → enhanced 缺失 → 提示可选增强 + 正常运行
```

### 检测方法

- 核心依赖：检查 `{skill-name}/skill.md` 是否存在
- 增强依赖：同上，缺失不阻断
- 版本兼容：读取 YAML 头部 version 字段

### 降级策略模板

```markdown
## 依赖缺失降级

| 缺失技能 | 影响范围 | 降级方案 |
|----------|----------|----------|
| {skill} | {受影响功能} | {替代方案或手动步骤} |
```

## 统一交互风格

### 启动问候模板

```
{智能体名称} v{版本} 已就绪

检测到：{已安装的依赖列表}
未安装：{缺失的增强依赖}（可选）

当前角色：{默认角色}
可用工作流：
  - {工作流1}：{简要说明}
  - {工作流2}：{简要说明}

{上一阶段交接提示，如有}
```

### 交接提示格式

当检测到上一阶段产物存在时，主动提示：

```
检测到 {上一智能体} 产物：{产物列表}
是否基于这些产物开始 {当前阶段} 工作？
  1. 直接开始（使用已有产物）
  2. 先查看产物再决定
  3. 忽略，从头开始
```

### 日常交互规范

- 中文优先，专有名词英文
- 简洁直接，先结论后细节
- 确认时一句话说明理解 + 2-3 个选项
- 不确定时主动沟通再执行
- 对结果负责

## 跨智能体触发机制

### 链式触发

上一个智能体完成时，在交接产物中写入触发信号：

```yaml
# 交接产物元数据
handoff:
  from: pre-sales-copilot
  to: product-copilot
  stage: N3
  artifacts:
    - name: 需求分析报告
      path: 项目文档/{项目}/01-需求/
    - name: 竞品分析
      path: 项目文档/{项目}/01-需求/
  quality_gate: passed
  notes: ""
```

### 发现式触发

各智能体启动时主动检测项目目录中已有的产物，推断当前应处于的阶段：

```
检测 01-需求/ 有产物 → 可能需要启动产品阶段
检测 02-产品/ 有产物 → 可能需要启动开发阶段
检测到多个阶段产物 → 提示用户确认当前阶段
```

### 上下文传递

跨智能体传递的上下文信息：

| 信息类型 | 传递方式 | 示例 |
|----------|----------|------|
| 项目元信息 | 写入 memory | 客户名、项目名、行业 |
| 阶段产物 | 文件输出 | PRD、技术方案 |
| 决策记录 | 原生 memory | 技术选型、方案确认 |
| 风险预警 | 交接元数据 | 已识别的风险项 |
| 约束条件 | 产物中标注 | 技术约束、合规要求 |
