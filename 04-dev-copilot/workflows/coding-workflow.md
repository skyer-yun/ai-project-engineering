# 编码开发工作流

> 本文件描述编码开发的完整流程，覆盖 N8（编码开发）和部分 N10（联调集成）。

## 依赖技能

| 技能 | 用途 | 降级 |
|------|------|------|
| 无额外依赖 | 编码使用 Claude Code 原生能力 | — |
| `code-reviewer` | 编码后审查 | 使用 review-workflow 内置审查 |

---

## 工作流步骤

### Stage 1：确认

**输入**：
- 详细设计文档（来自 detailed-design-workflow）或架构设计文档
- 用户口述的开发需求
- 已有代码库（如有）

**动作**：
1. 确认开发范围：
   - 本次要实现哪些模块/功能？
   - 优先级是什么？
2. 确认技术栈：
   - 读取 `memory/preferences.md` 获取默认技术栈
   - 如与项目要求不一致，以项目要求为准
3. 确认编码规范：
   - 代码风格（ESLint/Prettier 配置）
   - 命名规范（变量/函数/类/文件）
   - 目录结构规范
   - Git 提交规范（Conventional Commits 或自定义）
4. 确认环境：
   - 已有项目？→ 先读取现有代码结构
   - 新项目？→ 确认项目初始化方式

**输出**：开发计划（模块清单 + 开发顺序 + 预估工作量）

---

### Stage 2：编码

**输入**：Stage 1 开发计划

**动作**：按模块/功能逐个实现

#### 2.1 编码原则

- **遵循详细设计**：接口签名、数据模型、业务逻辑按设计文档实现
- **先骨架后填充**：先完成模块结构和接口，再实现内部逻辑
- **边写边注释**：关键逻辑加注释，复杂算法加说明
- **错误处理完整**：不忽略异常，每个可能的错误路径都有处理
- **安全意识**：输入校验、SQL 注入防护、XSS 防护、敏感数据处理

#### 2.2 编码顺序建议

```
1. 项目初始化（新项目）
   - 目录结构
   - 配置文件（tsconfig/eslint/prettier）
   - 依赖安装

2. 基础层
   - 数据库连接/配置
   - 中间件（认证/日志/错误处理）
   - 公共工具函数

3. 数据层
   - 数据模型定义（ORM Entity / Schema）
   - 数据访问层（Repository / DAO）
   - 数据库迁移脚本

4. 业务层
   - 核心业务逻辑（Service）
   - 业务规则实现
   - 事务管理

5. 接口层
   - API 路由定义
   - 请求/响应 DTO
   - 参数校验
   - 接口文档注解

6. 前端（如需要）
   - 页面组件
   - API 调用封装
   - 状态管理
   - 样式实现
```

#### 2.3 代码提交规范

```
提交信息格式（Conventional Commits）：
  <type>(<scope>): <subject>

type:
  feat:     新功能
  fix:      修复 bug
  docs:     文档变更
  style:    代码格式（不影响功能）
  refactor: 重构（不增加功能、不修复 bug）
  perf:     性能优化
  test:     测试
  chore:    构建/工具变更

scope: 模块名（可选）

subject: 简短描述（不超过 50 字符）

示例：
  feat(auth): 添加 JWT 认证中间件
  fix(order): 修复订单金额计算精度问题
  refactor(user): 重构用户查询逻辑
```

**输出**：可编译/运行的代码

---

### Stage 3：自测

**输入**：Stage 2 编码产物

**动作**：

#### 3.1 单元测试

- 为核心业务逻辑编写单元测试
- 覆盖正常路径 + 异常路径
- 边界条件测试
- 使用项目已选定的测试框架

#### 3.2 手动验证

- 核心功能流程走通
- 接口调用验证（Postman / curl）
- 错误场景验证
- 前端页面交互验证（如适用）

#### 3.3 自检清单

```
自检项：
  [ ] 代码编译通过，无语法错误
  [ ] 核心功能自测通过
  [ ] 错误处理完整，无未捕获异常
  [ ] 输入校验到位
  [ ] 日志输出合理
  [ ] 无硬编码的密钥/密码
  [ ] 代码风格符合规范
  [ ] 单元测试覆盖核心逻辑
```

**输出**：自测通过的代码

---

### Stage 4：提交与联调

**输入**：Stage 3 自测通过的代码

**动作**：

#### 4.1 代码提交

```bash
# 查看变更
git status
git diff

# 暂存
git add {具体文件}

# 提交（遵循 Conventional Commits）
git commit -m "feat(module): 简短描述"

# 推送（如需要）
git push origin {branch}
```

#### 4.2 联调扩展（N10 覆盖）

编码完成后，可启动联调检查：

**联调检查清单**：

```
接口联调：
  [ ] 前后端接口对齐（路径/方法/参数/响应）
  [ ] 数据格式一致（JSON 字段名/类型/嵌套结构）
  [ ] 错误码统一处理
  [ ] 鉴权机制一致
  [ ] 跨域（CORS）配置正确

数据联调：
  [ ] 数据库表结构与代码 Entity 一致
  [ ] 初始数据/种子数据准备
  [ ] 数据迁移脚本可执行

集成验证：
  [ ] 完整业务流程端到端走通
  [ ] 多模块交互正确
  [ ] 消息队列（如有）收发正常
  [ ] 缓存（如有）命中和失效正确
```

**联调报告模板**：

```markdown
# 联调报告

## 基本信息
- 模块：{模块名}
- 联调人：{姓名}
- 日期：{日期}

## 联调结果
| 接口 | 状态 | 备注 |
|------|------|------|
| POST /api/v1/xxx | 通过 | — |
| GET /api/v1/xxx | 失败 | 返回 500，原因：... |

## 问题清单
| 编号 | 描述 | 严重程度 | 状态 |
|------|------|---------|------|
| 1 | ... | Critical/Major/Minor | 待修复 |

## 结论
- [ ] 联调通过，可进入测试
- [ ] 存在阻塞问题，需修复后重新联调
```

**输出**：已提交的代码 + 联调报告（如有）

## 决策速查

```
用户要写代码
  ├─ 有详细设计文档 → 按设计实现 → Stage 2
  ├─ 有架构设计文档 → 补充接口/数据模型 → Stage 2
  ├─ 有 PRD → 建议先做架构设计（architecture-workflow）
  └─ 只需修改/修复 → 确认范围 → 直接编码

新项目初始化：
  ├─ React → create-react-app / Vite / Next.js
  ├─ Vue → create-vue / Nuxt.js
  ├─ Node.js → Express / NestJS / Fastify
  └─ Python → FastAPI / Django / Flask

编码完成 → 自测 → 提交 → 可选联调 → 可选代码审查
```
