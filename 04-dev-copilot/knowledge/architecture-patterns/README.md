# 架构模式速查

> 常见架构模式参考 + 选型决策树 + 演进路径。仅在当前任务相关时加载。

---

## 单体架构（Monolithic）

```
描述：所有功能在一个应用中，单一部署单元
适用：小型项目、MVP、团队 < 5 人
优势：
  - 开发简单，部署方便
  - 调试容易，事务管理简单
  - 前期开发速度快
劣势：
  - 随规模增长，代码复杂度上升
  - 局部修改需整体部署
  - 技术栈锁定
  - 扩展只能整体扩展

典型结构：
  src/
  ├── modules/
  │   ├── user/        # 用户模块
  │   ├── order/       # 订单模块
  │   └── product/     # 商品模块
  ├── shared/          # 公共代码
  ├── config/          # 配置
  └── app.ts           # 入口

何时选择：
  - 项目初期 / MVP 阶段
  - 团队小，沟通成本低
  - 业务领域相对简单
  - 预算和时间有限
```

### 模块化单体（Modular Monolithic）

```
描述：单体架构 + 严格模块边界，模块间通过定义好的接口通信
适用：中型项目、团队 5-10 人、有微服务演进计划
优势：
  - 保持单体部署的简单性
  - 模块边界清晰，未来可拆分为微服务
  - 团队可按模块分工
劣势：
  - 模块边界维护需要纪律
  - 仍共享数据库（需严格隔离）

典型结构：
  src/
  ├── modules/
  │   ├── user/
  │   │   ├── api/         # 对外接口
  │   │   ├── domain/      # 领域逻辑
  │   │   ├── infra/       # 基础设施
  │   │   └── module.ts    # 模块注册
  │   ├── order/
  │   └── product/
  ├── shared/              # 真正的公共代码（极少）
  └── app.ts

关键原则：
  - 模块间禁止直接引用内部实现
  - 通过模块公开的 API 接口通信
  - 每个模块有自己的数据表（逻辑隔离）
```

## 微服务架构（Microservices）

```
描述：按业务能力拆分为独立服务，独立部署、独立数据库
适用：大型项目、团队 > 10 人、高 QPS、复杂业务
优势：
  - 独立部署和扩展
  - 技术栈可异构
  - 故障隔离
  - 团队独立自治
劣势：
  - 分布式复杂度（网络延迟、数据一致性、调试）
  - 运维成本高
  - 服务间通信开销
  - 需要成熟的 DevOps

典型结构：
  services/
  ├── user-service/        # 用户服务
  │   ├── src/
  │   ├── Dockerfile
  │   └── package.json
  ├── order-service/       # 订单服务
  ├── product-service/     # 商品服务
  ├── api-gateway/         # API 网关
  └── shared-libs/         # 共享库（谨慎使用）

基础设施需求：
  - 服务注册与发现（Consul / Nacos）
  - API 网关（Kong / APISIX / Spring Cloud Gateway）
  - 配置中心（Apollo / Nacos）
  - 链路追踪（Jaeger / Zipkin）
  - 消息队列（RabbitMQ / Kafka）

何时选择：
  - 单体已无法支撑业务规模
  - 团队规模需要独立自治
  - 不同模块有不同的扩展需求
  - 有成熟的 DevOps 团队和工具链
```

## Serverless 架构

```
描述：函数即服务（FaaS）+ 后端即服务（BaaS），无需管理服务器
适用：事件驱动、流量波动大、API 网关+BFF、数据处理
优势：
  - 按用量付费，成本可控
  - 自动扩缩容
  - 无需管理基础设施
  - 开发者只关注业务逻辑
劣势：
  - 冷启动延迟
  - 调试和本地测试困难
  - 供应商锁定
  - 不适合长时间运行任务

典型结构：
  functions/
  ├── api/
  │   ├── create-order.ts
  │   ├── get-order.ts
  │   └── list-orders.ts
  ├── triggers/
  │   ├── on-payment.ts
  │   └── on-order-created.ts
  └── shared/

平台选择：
  AWS Lambda + API Gateway
  Vercel Functions / Next.js API Routes
  Cloudflare Workers
  阿里云函数计算

何时选择：
  - 流量波动大，有明显的波峰波谷
  - API 请求量不大但需要高可用
  - 事件驱动型处理（文件上传、定时任务）
  - 快速原型验证
```

## 事件驱动架构（Event-Driven）

```
描述：通过事件进行异步通信，生产者发布事件，消费者订阅处理
适用：实时数据处理、工作流引擎、解耦系统、审计日志
优势：
  - 高度解耦
  - 异步处理，响应快
  - 易于扩展消费者
  - 事件溯源可重放
劣势：
  - 调试复杂
  - 事件顺序和一致性挑战
  - 演进中的 Schema 兼容性
  - 需要消息中间件

典型结构：
  services/
  ├── order-service/
  │   ├── handlers/       # 事件处理器
  │   ├── events/         # 事件定义
  │   └── commands/       # 命令（同步）
  ├── payment-service/
  ├── notification-service/
  └── event-bus/          # 事件总线

事件模式：
  Event Sourcing：
    - 所有状态变更以事件形式记录
    - 可重放恢复状态
    - 适合审计、合规场景

  CQRS：
    - 命令（写）和查询（读）分离
    - 写模型和读模型可以独立优化
    - 常与 Event Sourcing 搭配

消息中间件：
  Kafka：高吞吐、持久化、事件流
  RabbitMQ：灵活路由、确认机制
  Redis Streams：轻量级

何时选择：
  - 业务流程涉及多个步骤/系统
  - 需要异步解耦
  - 有实时数据处理需求
  - 需要审计追踪
```

## 选型决策树

```
架构模式选择：

项目规模？
├─ 小型 / MVP / 团队 < 5 人
│  └─ 单体架构
│
├─ 中型 / 团队 5-15 人
│  ├─ 业务领域复杂？→ 模块化单体（准备微服务演进）
│  ├─ 实时处理需求？→ 事件驱动 + 单体
│  └─ 通用 → 模块化单体
│
└─ 大型 / 团队 > 15 人 / 高 QPS
   ├─ 不同模块扩展需求差异大？→ 微服务架构
   ├─ 事件驱动型业务？→ 事件驱动 + 微服务
   └─ 通用 → 微服务架构

特殊场景：
├─ 流量波动大 / API 为主 → Serverless
├─ 内部工具 / 管理后台 → 单体（足够）
└─ 数据平台 / 实时分析 → 事件驱动 + 微服务
```

## 演进路径

```
推荐演进路线：单体 → 模块化单体 → 微服务

不要一开始就微服务。原因：
  - 分布式复杂度是真实的成本
  - 业务边界在初期不清晰
  - 过早拆分导致频繁重构

演进信号（该从单体迁移到微服务的标志）：
  1. 部署瓶颈：一个模块的变更需要整个系统重新部署
  2. 扩展瓶颈：不同模块需要不同的扩展策略
  3. 团队瓶颈：多个团队在同一个代码库频繁冲突
  4. 技术栈瓶颈：某些模块需要不同的技术栈
  5. 故障影响：一个模块的问题影响整个系统

迁移步骤：
  1. 先做模块化重构（模块化单体）
  2. 识别最需要独立的模块（最高 QPS / 最频繁变更）
  3. 逐个模块拆分为独立服务
  4. 每次拆分后稳定运行再拆下一个

反向演进（微服务 → 单体）：
  - 有些公司发现微服务复杂度不值得
  - 团队小但系统过度拆分
  - 合并交互频繁的服务为一个模块化单体
```
