# 缺陷管理工作流

> 覆盖阶段：N10-N12（贯穿测试全过程）
> 对应角色：测试工程师 + 开发协作

---

## 适用场景

在测试执行过程中发现缺陷，需要记录、分析、跟踪修复和验证时使用。

- 测试执行中发现 Bug
- 缺陷根因分析
- 修复验证与回归
- 缺陷统计分析
- 发版前缺陷确认

## 前置条件

```
必须：
  [x] 缺陷已被发现并可复现

建议：
  [ ] 测试用例已基线化（关联用例）
  [ ] 缺陷跟踪系统已配置
```

## 阶段

### Stage 1: 缺陷记录

- **输入**：缺陷现象描述 + 复现步骤
- **动作**：
  1. 记录缺陷基本信息
     - 标题：简洁描述问题（"什么情况下，发生了什么"）
     - 复现步骤：1-2-3...可精确复现
     - 预期结果：根据需求/用例的正确行为
     - 实际结果：观察到的错误行为
     - 环境：浏览器/OS/版本/设备
     - 附件：截图/录屏/日志
  2. 缺陷分级（P0-P3）

     | 等级 | 定义 | 示例 |
     |------|------|------|
     | P0 致命 | 系统崩溃/数据丢失/安全漏洞 | 支付金额篡改、数据库泄漏 |
     | P1 严重 | 核心功能不可用/性能严重下降 | 登录失败、下单流程阻断 |
     | P2 一般 | 非核心功能异常/体验问题 | 搜索结果排序不准、提示文案错误 |
     | P3 轻微 | UI 瑕疵/文案错误/优化建议 | 按钮间距不统一、错别字 |

  3. 关联信息
     - 关联测试用例（TC-XXX）
     - 关联需求（REQ-XXX）
     - 关联模块/功能点
  4. 指派处理人（开发负责人）
- **输出**：缺陷工单
  ```
  缺陷ID：BUG-{模块}-{序号}
  标题：[P{级别}] {简要描述}
  报告人：{测试人员}
  报告时间：{日期}
  模块：{所属模块}
  级别：P0/P1/P2/P3

  复现步骤：
    1. ...
    2. ...
    3. ...

  预期结果：...
  实际结果：...

  环境信息：
    浏览器：Chrome 120
    操作系统：Windows 11
    版本：v1.2.0

  附件：截图/录屏/日志
  关联用例：TC-XXX
  关联需求：REQ-XXX
  ```
- **技能调用**：`defect-analyzer`（如已安装，辅助分级和关联分析）

### Stage 2: 缺陷分析

- **输入**：缺陷工单 + 源码（如有）+ 日志
- **动作**：
  1. 根因分析
     - 定位缺陷产生的直接原因
     - 分析是否为设计问题/编码问题/环境问题/数据问题
     - 评估影响范围（是否影响其他功能）
  2. 关联分析
     - 是否与已知缺陷重复
     - 是否与已修复缺陷回归相关
     - 是否影响其他模块
  3. 修复建议
     - 推荐修复方案
     - 评估修复风险（是否引入新问题）
     - 建议回归范围
- **输出**：缺陷分析报告
  ```
  根因：{直接原因}
  类型：{设计/编码/环境/数据}
  影响范围：{受影响的功能/模块}
  关联缺陷：{BUG-XXX}（如有重复/相关）
  修复建议：{推荐方案}
  回归范围：{需要回归验证的用例列表}
  ```
- **技能调用**：`defect-analyzer`（如已安装，辅助根因分析）

### Stage 3: 修复跟踪

- **输入**：缺陷分析报告 + 开发修复
- **动作**：
  1. 分配修复任务（开发负责人）
  2. 跟踪修复进度
     - P0：24h 内修复
     - P1：48h 内修复
     - P2：本迭代内修复
     - P3：下版本修复
  3. 修复验证
     - 验证缺陷已修复
     - 验证未引入新问题
     - 代码审查（如适用）
  4. 更新缺陷状态
     - 新建 → 已确认 → 修复中 → 已修复 → 验证中 → 已关闭
     - 如验证不通过 → 重新打开
- **输出**：修复确认记录
  - 修复人/修复时间
  - 修复方案描述
  - 代码变更范围
  - 自测结果

### Stage 4: 验证回归

- **输入**：已修复缺陷 + 回归范围
- **动作**：
  1. 验证修复
     - 按原始复现步骤验证缺陷已修复
     - 检查预期结果与实际结果一致
  2. 回归测试
     - 执行关联用例
     - 执行修复建议的回归范围
     - 检查是否引入新缺陷
  3. 关闭缺陷
     - 验证通过 → 关闭
     - 验证不通过 → 重新打开 + 补充说明
  4. 更新缺陷统计
- **输出**：验证记录
  ```
  验证人：{测试人员}
  验证时间：{日期}
  验证结果：通过/不通过
  回归用例：{执行的用例列表}
  回归结果：{全部通过/N条失败}
  新发现问题：{无/BUG-XXX}
  ```

## 缺陷状态流转

```
新建(New) → 已确认(Confirmed) → 修复中(In Progress) → 已修复(Fixed)
                                                              ↓
验证中(Verifying) → 已关闭(Closed)
       ↓
  重新打开(Reopened) → 修复中(In Progress)

特殊状态：
  延期(Deferred) — 下版本处理
  重复(Duplicate) — 与已有缺陷重复
  不是Bug(Not a Bug) — 经确认非缺陷
  无法复现(Cannot Reproduce) — 需补充信息
```

## 缺陷度量指标

```
缺陷密度 = 总缺陷数 / 功能点数（个/功能点）
缺陷修复率 = 已关闭缺陷数 / 总缺陷数 × 100%
P0/P1 修复率 = P0/P1 已关闭数 / P0/P1 总数 × 100%（发布前需 100%）
缺陷存活时间 = 关闭时间 - 创建时间（按级别统计平均）
缺陷重开率 = 重新打开次数 / 总修复次数 × 100%
```

## 产物归档

```
项目文档/测试管理/
├── 缺陷清单.md（或 .xlsx）
├── 缺陷分析报告/
│   ├── BUG-{模块}-001-分析.md
│   └── ...
└── 缺陷统计/
    └── 缺陷度量报告.md
```

## 降级策略

| 缺失资源 | 降级行为 |
|----------|----------|
| defect-analyzer 未安装 | 人工分析根因，提供分析框架 |
| 缺陷跟踪系统未配置 | 使用 Markdown 表格跟踪 |
| xlsx 未安装 | 缺陷清单输出 Markdown |
| 源码不可访问 | 仅基于现象分析，标注"需开发确认" |

## P0/P1 清零检查清单

```
发版前 P0/P1 清零确认：
  [ ] 所有 P0 缺陷已关闭（0 Open）
  [ ] 所有 P1 缺陷已关闭（0 Open）
  [ ] 所有 P0/P1 修复已通过回归验证
  [ ] 回归测试未发现新的 P0/P1 缺陷
  [ ] 测试结论为 All Pass 或条件通过
  [ ] 遗留问题已记录并评估风险

如有 P0/P1 未关闭：
  → 不建议发布
  → 输出阻塞清单
  → 通知 project-copilot 调整排期
```
