# 代码审查工作流

> 本文件描述代码审查的完整流程。增强依赖 code-reviewer 已安装时调用其技能，否则使用本文件内置审查流程。

## 依赖技能

| 技能 | 用途 | 降级 |
|------|------|------|
| `code-reviewer` | 自动化代码审查 | 本文件内置审查流程 |

---

## 审查维度

### 维度 1：安全

| 检查项 | 说明 | 严重程度 |
|--------|------|---------|
| SQL 注入 | 是否使用参数化查询 | Critical |
| XSS 跨站脚本 | 是否对用户输入进行转义 | Critical |
| CSRF 跨站请求伪造 | 是否有 CSRF 防护 | Major |
| 敏感信息泄露 | 日志/响应中是否暴露密钥、密码 | Critical |
| 认证/授权 | 接口是否有权限校验 | Critical |
| 输入校验 | 是否对所有外部输入进行校验 | Major |
| 加密传输 | 敏感数据是否使用 HTTPS | Major |
| 文件上传 | 是否限制文件类型和大小 | Major |

### 维度 2：性能

| 检查项 | 说明 | 严重程度 |
|--------|------|---------|
| N+1 查询 | 是否存在循环内查询数据库 | Major |
| 缺少索引 | 查询条件字段是否有索引 | Major |
| 内存泄漏 | 是否有未释放的资源 | Major |
| 大数据量处理 | 是否有分页/流式处理 | Minor |
| 缓存策略 | 高频读取是否使用缓存 | Minor |
| 异步处理 | 耗时操作是否异步执行 | Minor |
| 连接池 | 数据库/HTTP 连接是否复用 | Minor |

### 维度 3：规范

| 检查项 | 说明 | 严重程度 |
|--------|------|---------|
| 命名规范 | 变量/函数/类命名是否规范 | Minor |
| 代码结构 | 目录结构/文件组织是否合理 | Minor |
| 注释质量 | 关键逻辑是否有注释 | Minor |
| 错误处理 | 异常是否完整捕获和处理 | Major |
| 日志规范 | 日志级别和格式是否统一 | Minor |
| API 规范 | 接口命名/参数/响应是否规范 | Minor |
| 类型安全 | TypeScript 类型是否完整 | Minor |

### 维度 4：最佳实践

| 检查项 | 说明 | 严重程度 |
|--------|------|---------|
| 设计模式 | 是否合理使用设计模式 | Suggestion |
| DRY 原则 | 是否有重复代码可抽取 | Minor |
| SOLID 原则 | 单一职责/开闭/依赖反转 | Minor |
| 可测试性 | 代码是否易于编写单元测试 | Minor |
| 可维护性 | 代码是否易于理解和修改 | Suggestion |
| 错误码体系 | 错误码是否统一和有文档 | Minor |
| 幂等设计 | 关键操作是否支持幂等 | Major |

---

## 问题分级

| 级别 | 定义 | 处理方式 | 示例 |
|------|------|---------|------|
| **Critical** | 安全漏洞或会导致数据丢失/系统崩溃的严重问题 | 必须立即修复，阻塞发布 | SQL 注入、未鉴权接口、密码明文存储 |
| **Major** | 影响功能正确性或性能的重要问题 | 本迭代内修复 | N+1 查询、缺少错误处理、内存泄漏 |
| **Minor** | 不影响功能但违反规范的代码质量问题 | 建议修复，可排入后续迭代 | 命名不规范、缺少注释、日志不完整 |
| **Suggestion** | 改进建议，提升代码质量 | 参考，不强制 | 设计模式优化、可测试性改进 |

## 工作流步骤

### Stage 1：范围确定

**输入**：
- 用户指定的审查范围（文件/模块/全量）
- 或最近的代码提交（git diff）

**动作**：
1. 确定审查范围：
   - 指定文件/目录？
   - 最近 N 次提交？
   - 指定分支 diff？
2. 排除无需审查的文件：
   - 自动生成文件（node_modules/、dist/、build/）
   - 第三方库代码
   - 配置文件（仅检查敏感信息）
3. 读取相关的设计文档（如有），作为审查依据

**输出**：审查文件清单

---

### Stage 2：审查执行

**输入**：Stage 1 审查文件清单

**动作**：逐文件、逐维度进行审查

#### 审查流程

```
FOR each 文件 in 审查清单:
  1. 读取文件内容
  2. 识别文件类型（前端/后端/配置/测试）
  3. 按对应维度清单检查
  4. 记录发现的问题（级别 + 位置 + 说明）
  5. 给出修复建议（具体代码示例）
```

#### 审查重点按文件类型

| 文件类型 | 重点审查维度 |
|---------|------------|
| API 路由/控制器 | 安全 + 规范 + 最佳实践 |
| 业务逻辑/Service | 性能 + 规范 + 最佳实践 |
| 数据访问层 | 安全（SQL 注入） + 性能（索引） |
| 前端组件 | 安全（XSS） + 性能 + 规范 |
| 配置文件 | 安全（敏感信息） |
| 测试文件 | 规范 + 最佳实践 |

---

### Stage 3：问题整理

**输入**：Stage 2 审查发现

**动作**：
1. 按级别排序（Critical → Major → Minor → Suggestion）
2. 同类问题合并
3. 为每个问题生成修复建议
4. 统计各级别数量

**输出**：问题清单

---

### 后续衔接

**产出完成后，向用户建议可选的后续步骤**：

| 后续动作 | 工作流/技能 | 说明 |
|----------|-----------|------|
| 修复问题 | coding-workflow | 按优先级修复 Critical → Major → Minor |
| 重新审查 | review-workflow | 修复后重新审查确认 |
| 交接给 testing-copilot | testing-copilot | 审查通过后进入测试阶段 |

## 决策速查

```
用户要审查代码
  ├─ 指定文件 → 审查指定文件 → Stage 2
  ├─ 指定模块 → 审查模块目录 → Stage 2
  ├─ 最近提交 → git diff → Stage 2
  └─ 全量审查 → 全项目扫描 → Stage 2（分批执行）

问题分级：
  Critical → 必须立即修复
  Major → 本迭代内修复
  Minor → 建议修复
  Suggestion → 参考

审查完成 → 报告 → 可选修复 → 可选重新审查
```
