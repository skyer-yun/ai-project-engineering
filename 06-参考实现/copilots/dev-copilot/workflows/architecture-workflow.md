# 架构设计工作流

> 本文件描述架构设计的完整流程。核心依赖 architecture-designer 已安装时调用其技能，否则使用本文件内置流程。

## 依赖技能

| 技能 | 用途 | 降级 |
|------|------|------|
| `architecture-designer` | 架构设计主技能 | 本文件内置流程 |
| `product-copilot` | 前置，提供 PRD 输入 | 通过需求澄清补充 |
| `tech-stack-selector` | 技术栈选型辅助 | 参考 knowledge/tech-stacks/ |
| `brainstorming` | 架构方案探索 | 使用内置澄清清单 |

---

## 工作流步骤

### Stage 1：需求分析

**输入**：
- PRD 文档（来自 product-copilot）或用户口述需求
- 已有系统代码（如有）

**动作**：
1. 读取 PRD 文档，提取以下关键信息：
   - Part 2：产品概述（背景、目标用户、核心场景）
   - Part 3：功能范围与优先级（P0/P1/P2 功能清单）
   - Part 7：功能模块详细说明（核心功能点的业务规则、数据流向）
   - Part 8：数据模型（已有实体和关系）
   - Part 9：接口规范（已有 API 设计）
   - Part 10：非功能需求（性能、安全、可用性指标）
2. 无 PRD 时，通过需求澄清补充：
   - 系统目标是什么？
   - 目标用户规模？
   - 核心功能有哪些？
   - 是否有性能/安全/可用性要求？
   - 是否有技术约束（预算、团队技能、已有系统）？

**输出**：需求摘要（功能需求 + 非功能需求 + 约束条件）

---

### Stage 2：架构设计

**输入**：Stage 1 需求摘要

**动作**：

#### 2.1 架构模式选择

参考 `knowledge/architecture-patterns/README.md`，根据以下维度选择：

| 维度 | 问题 | 影响选择 |
|------|------|---------|
| 规模 | 用户量级？QPS 预期？ | 单体 vs 微服务 |
| 团队 | 团队规模？技术栈统一？ | 单体 vs 微服务 |
| 复杂度 | 业务领域复杂度？ | 是否需要 DDD |
| 迭代速度 | 发布频率？ | 单体 vs 微服务 / Serverless |
| 成本 | 预算约束？ | 单体 vs Serverless |

#### 2.2 模块划分

根据 PRD 功能清单，按以下原则划分模块：
- 高内聚、低耦合
- 单一职责
- 按业务领域划分（而非技术层）
- 识别限界上下文（如适用 DDD）

#### 2.3 架构图

使用 Mermaid 绘制：
- 系统上下文图（System Context）
- 容器图（Container Diagram）
- 模块依赖图

---

### Stage 3：技术选型

**输入**：Stage 2 架构设计结果

**动作**：逐层选型，每层给出选型理由

| 层次 | 选型维度 | 常见选项 |
|------|---------|---------|
| 前端 | 框架 / UI 库 / 状态管理 / 构建工具 | React / Vue / Angular |
| 后端 | 语言 / 框架 / API 风格 / 认证方式 | Node.js / Java / Python / Go |
| 数据库 | 关系型 / NoSQL / 缓存 | MySQL / PostgreSQL / MongoDB / Redis |
| 中间件 | 消息队列 / 搜索 / 任务调度 | RabbitMQ / Kafka / Elasticsearch |
| 部署 | 容器 / 编排 / CI/CD / 监控 | Docker / K8s / GitHub Actions |

每个选型输出：
- 选项名称
- 选择理由（1-2 句）
- 备选方案
- 注意事项

参考 `knowledge/tech-stacks/README.md` 的选型决策树。

---

### Stage 4：文档输出

**输出**：架构设计文档（7 标准章节）

#### 文档模板

```markdown
# {项目名称} 架构设计文档

## 1. 项目概述与背景
- 项目背景与目标
- 目标用户与使用场景
- 核心业务价值

## 2. 架构设计原则
- 列出 3-5 条核心设计原则
- 每条原则附带理由

## 3. 系统架构总览
- 架构模式说明（为什么选择这种模式）
- 系统上下文图（Mermaid）
- 容器图（Mermaid）
- 核心数据流向

## 4. 模块划分与职责
- 模块清单（名称/职责/核心功能/依赖关系）
- 模块依赖图（Mermaid）
- 模块间通信方式

## 5. 技术选型与理由
- 逐层选型表（层次/选择/理由/备选）
- 技术栈总览图

## 6. 非功能性设计
- 性能设计（目标指标 + 实现方式）
- 安全设计（认证/授权/数据加密/输入校验）
- 可用性设计（容错/降级/限流）
- 扩展性设计（水平扩展/垂直扩展）
- 可观测性设计（日志/监控/链路追踪）

## 7. 部署架构与运维考量
- 部署拓扑图
- CI/CD 流程
- 环境策略（开发/测试/预发/生产）
- 运维考量（备份/容灾/扩缩容）
```

**格式转换（按需）**：
- Word 格式 → 调用 `docx` 技能
- 飞书文档 → 调用 `lark-mcp`

---

### Stage 5：后续衔接

**产出完成后，向用户建议可选的后续步骤**：

| 后续动作 | 工作流/技能 | 说明 |
|----------|-----------|------|
| 进入详细设计 | detailed-design-workflow | 接口设计 + 数据模型 + 时序图 |
| 直接编码 | coding-workflow | 基于架构设计直接开始编码 |
| 技术调研 | web-access | 深入了解某项技术 |
| 架构评审 | review-workflow | 对架构方案进行评审 |

**交接给 testing-copilot 的准备**：
- 架构文档归档到 `项目文档/{项目名}/架构设计文档.md`
- 通知 testing-copilot 非功能性设计中的测试目标

## 决策速查

```
用户要做架构设计
  ├─ 有 PRD → 从 PRD 提取需求 → 进入 Stage 2
  ├─ 无 PRD → 需求澄清 → 补充需求摘要 → 进入 Stage 2
  └─ 已有架构需要调整 → 分析现有架构 → 定位问题 → 进入 Stage 2

架构模式选择：
  ├─ 小型项目 / 团队 < 5 人 / MVP → 单体架构
  ├─ 中型项目 / 团队 5-15 人 → 模块化单体 或 有限微服务
  ├─ 大型项目 / 团队 > 15 人 / 高 QPS → 微服务架构
  └─ 事件驱动 / 实时处理 → 事件驱动架构

技术选型 → 参考 knowledge/tech-stacks/README.md 决策树
```
