# 触发规则

## 工作流触发

### requirement-workflow（需求收集与分析）

| 触发方式 | 匹配规则 |
|----------|----------|
| 关键词 | 需求、收集需求、分析需求、需求分析、整理需求、客户需求 |
| 语义 | 用户提供了客户原始材料，需要整理分析 |
| 组合 | "分析需求并做竞品调研" → requirement + 竞品分支 |

### proposal-workflow（技术方案编写）

| 触发方式 | 匹配规则 |
|----------|----------|
| 关键词 | 写方案、技术方案、建设方案、解决方案、出方案、出一份方案 |
| 语义 | 基于已有需求编写技术文档 |
| 组合 | "写方案+架构图" → proposal + 架构图生成 |

### bid-workflow（投标文件）

| 触发方式 | 匹配规则 |
|----------|----------|
| 关键词 | 投标、招标、应标、标书、技术标、商务标、投标文件 |
| 语义 | 基于招标文件准备响应材料 |
| 组合 | "投标+演示" → bid + demo-presentation |

### demo-presentation-workflow（客户演示）

| 触发方式 | 匹配规则 |
|----------|----------|
| 关键词 | 演示、PPT、汇报、客户交流、路演、演示材料、汇报材料 |
| 语义 | 准备面向客户的演示或汇报 |
| 组合 | "方案+演示" → proposal + demo-presentation |

## 技能直接触发

当用户直接引用已安装的底层技能时，不经过工作流路由，直接透传：

| 输入 | 透传到 |
|------|--------|
| "用 technical-proposal-writer..." | technical-proposal-writer |
| "搜索一下..." | web-access |
| "头脑风暴..." | brainstorming |

## 角色切换触发

| 输入关键词 | 切换角色 |
|-----------|----------|
| 竞品、市场、对标、对比、行业分析 | 市场分析师 |
| 投标、招标、应标、标书 | 商务顾问 |
| 演示、PPT、汇报、路演、客户演示 | 演示工程师 |
| 方案、技术方案、建设方案（默认） | 售前方案工程师 |

## 组合场景触发

| 用户输入示例 | 匹配工作流 | 处理策略 |
|-------------|-----------|----------|
| "分析需求然后写方案" | requirement → proposal | 串行执行 |
| "分析竞品后出方案" | requirement（竞品分支）→ proposal | 竞品分析作为方案输入 |
| "写方案并准备演示" | proposal → demo-presentation | 方案完成后启动演示 |
| "准备投标全套" | bid | 投标工作流内串行处理 |
| "投标+演示" | bid + demo-presentation | 投标完成后启动演示 |

## 匹配规则优先级

```
1. 直接技能引用（最高）— 用户明确指定技能名
2. LLM 语义匹配 — 理解用户意图
3. 关键词精确匹配 — triggers 中的关键词
4. 关键词模糊匹配 — 包含关键词子串
5. 日常路由（兜底）— 不匹配任何规则时的默认处理
```

## LLM 语义优先路由说明

triggers.md 中的关键词仅作为 LLM 语义路由的兜底机制。当 LLM 无法确定用户意图时（置信度 < 0.5），才使用关键词匹配。

正常情况下，LLM 应能通过语义理解正确路由以下场景：
- "帮我整理一下客户提的那些要求" → requirement-workflow
- "这个项目的技术路线怎么选" → proposal-workflow（技术选型章节）
- "明天要去客户那做汇报" → demo-presentation-workflow
- "这个标我们怎么响应" → bid-workflow
