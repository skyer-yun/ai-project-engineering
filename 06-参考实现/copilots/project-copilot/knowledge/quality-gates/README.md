# 质量门禁

> 4 个质量门禁（QG-D/S/B/Ship），共 48 个检查项
> 每个门禁对应一个阶段交接点，未通过不允许进入下一阶段

---

## QG-D: 项目规划完成度（N3 → N4）

**交接点**：项目规划完成 → 进入产品/需求阶段
**检查目的**：确认项目规划充分，可以进入需求确认和产品设计

### 检查项（10 项）

```
规划完整性：
  [ ] 1. 项目章程已编写并确认
  [ ] 2. 项目目标已明确（SMART 原则）
  [ ] 3. 项目范围已定义（包含/排除）
  [ ] 4. 干系人已识别并登记

计划完整性：
  [ ] 5. WBS 已分解到工作包级别（8-80小时粒度）
  [ ] 6. 工作量估算已完成（至少使用 1 种估算方法）
  [ ] 7. 甘特图已生成（含关键路径和里程碑）
  [ ] 8. 资源分配已完成

风险与质量：
  [ ] 9. 初始风险登记册已创建（至少 3 条风险）
  [ ] 10. 质量门禁标准已确认
```

### 交接产物

| 产物 | 来源 | 交付给 |
|------|------|--------|
| 项目章程 | project-copilot | pre-sales/product-copilot |
| WBS + 甘特图 | project-copilot | 全体 |
| 风险登记册 | project-copilot | 全体 |

### 通过条件
- 10 项中至少 8 项通过
- 第 1-4 项（规划完整性）必须全部通过
- 第 5-8 项中至少 3 项通过

---

## QG-S: 需求/设计就绪度（N7 → N8）

**交接点**：产品设计完成 → 进入开发阶段
**检查目的**：确认需求和设计充分，可以进入编码开发

### 检查项（12 项）

```
需求完整性：
  [ ] 1. PRD 已编写（12 部分结构完整）
  [ ] 2. PRD Part 7 功能模块详细说明已达到深度要求
  [ ] 3. 功能优先级已确定（P0/P1/P2）
  [ ] 4. 非功能需求已明确（性能/安全/兼容性）
  [ ] 5. 数据模型已设计（ER 图/状态码）
  [ ] 6. 接口规范已定义

设计就绪度：
  [ ] 7. Demo/原型已确认（与客户/产品对齐）
  [ ] 8. 技术方案已评审
  [ ] 9. 设计系统已选择
  [ ] 10. 前端页面结构已定义

评审与确认：
  [ ] 11. PRD 已通过评审
  [ ] 12. 客户/业务方已确认需求
```

### 交接产物

| 产物 | 来源 | 交付给 |
|------|------|--------|
| PRD | product-copilot | dev-copilot |
| Demo 页面 | product-copilot | dev-copilot |
| 设计规范 | product-copilot | dev-copilot |
| 接口文档 | product-copilot | dev-copilot |

### 通过条件
- 12 项中至少 10 项通过
- 第 1-6 项（需求完整性）至少 5 项通过
- 第 11-12 项（评审确认）必须全部通过

---

## QG-B: 开发完成度（N10 → N11）

**交接点**：开发完成 → 进入测试阶段
**检查目的**：确认开发工作完成，可以进入系统测试

### 检查项（8 项）

```
代码质量：
  [ ] 1. 代码已冻结（feature freeze）
  [ ] 2. 代码审查已完成
  [ ] 3. 无编译错误/构建失败

功能完整性：
  [ ] 4. 所有 P0 功能已实现
  [ ] 5. 所有 P1 功能已实现（或已确认延期）
  [ ] 6. 自测通过（开发人员冒烟测试）

文档完整性：
  [ ] 7. 接口文档已更新（与实现一致）
  [ ] 8. 联调报告已完成（联调通过）
```

### 交接产物

| 产物 | 来源 | 交付给 |
|------|------|--------|
| 源码（已打Tag） | dev-copilot | testing-copilot |
| 接口文档 | dev-copilot | testing-copilot |
| 联调报告 | dev-copilot | testing-copilot |

### 通过条件
- 8 项必须全部通过
- 第 1 项（代码冻结）和第 4 项（P0 功能完成）为硬性条件

---

## QG-Ship: 测试通过度（N12 → N13）

**交接点**：测试完成 → 进入部署/交付阶段
**检查目的**：确认测试通过，系统可以部署上线

### 检查项（10 项）

```
测试完成度：
  [ ] 1. 测试策略已制定并评审
  [ ] 2. 测试用例已编写并基线化
  [ ] 3. 用例执行率 100%（P0/P1）
  [ ] 4. 用例通过率 >= 95%

缺陷管理：
  [ ] 5. P0 缺陷已清零（0 Open）
  [ ] 6. P1 缺陷已清零（0 Open）
  [ ] 7. P2 缺陷修复率 >= 80%（或已确认下版本）
  [ ] 8. 遗留问题已记录并评估风险

测试报告：
  [ ] 9. 测试报告已输出（含结论）
  [ ] 10. 性能测试报告已输出（如适用）
```

### 交接产物

| 产物 | 来源 | 交付给 |
|------|------|--------|
| 测试报告 | testing-copilot | delivery-copilot |
| 缺陷清单 | testing-copilot | delivery-copilot |
| 性能报告 | testing-copilot | delivery-copilot |
| 源码（已打Tag） | dev-copilot | delivery-copilot |

### 通过条件
- 10 项必须全部通过
- 第 5-6 项（P0/P1 清零）为硬性条件，无例外
- 第 3-4 项（执行率/通过率）为硬性条件

---

## QG-Ship: 交付完成度（N15 → N16）

**交接点**：交付完成 → 项目结项
**检查目的**：确认所有交付物完成，可以关闭项目

### 检查项（8 项）

```
部署验收：
  [ ] 1. 部署方案已制定并执行
  [ ] 2. 生产环境部署验证通过
  [ ] 3. 验收测试已完成（按 PRD Part 11）

文档交付：
  [ ] 4. 用户手册已交付并确认
  [ ] 5. 运维手册已交付并确认
  [ ] 6. 培训已完成（或培训材料已交付）

项目收尾：
  [ ] 7. 验收报告已签署
  [ ] 8. 客户满意度已确认
```

### 交接产物

| 产物 | 来源 | 交付给 |
|------|------|--------|
| 交付文档包 | delivery-copilot | project-copilot |
| 验收报告 | delivery-copilot | project-copilot |
| 运维手册 | delivery-copilot | 客户运维团队 |

### 通过条件
- 8 项必须全部通过
- 第 7 项（验收报告签署）为硬性条件

## 门禁执行规则

### 执行方式

```
1. 到达门禁时间点时，自动触发门禁检查
2. 逐项检查，记录每项通过/未通过状态
3. 统计通过率，判断是否满足通过条件
4. 输出门禁报告

通过 → 允许进入下一阶段，通知下一智能体
未通过 → 阻塞项目推进，列出未通过项 + 修复建议
```

### 门禁报告模板

```
质量门禁报告：QG{N} - {门禁名称}

检查时间：{日期}
检查人：{姓名}

检查结果：
  | 序号 | 检查项 | 结果 | 备注 |
  |------|--------|------|------|
  | 1 | {描述} | 通过 | — |
  | 2 | {描述} | 未通过 | {原因} |
  | ...

统计：
  通过：{N}/{M} ({%})
  结论：[通过 / 未通过]

未通过项修复建议：
  - {检查项}：{建议}

下一步：
  [通过] → 进入 {下一阶段}，通知 {智能体}
  [未通过] → 修复未通过项后重新检查
```

### 门禁例外处理

```
特殊情况下需要跳过或降低门禁标准时：
  1. 必须由项目经理审批
  2. 记录例外原因和风险评估
  3. 制定补偿措施
  4. 通知所有干系人

注意：
  QG-Ship 的 P0/P1 清零原则不可例外
  QG-Ship 的验收报告签署不可例外
```
